## b1-1(止める)DEFINITIONS.md が scenes.py と食い違っていた

**根本原因**: `v3-precision-cap` の期待値が、要件文(「時刻はUTCのint64ナノ秒」)からではなく、
新実装の内部契約 `src/bot/bt/core/contract.py` の `CORE_CONTRACT['time']` のキー名
(`unit`/`timezone`)をそのまま写して作られていた(場面集の規則2「場面は振る舞いを試し、
作りの形を試さない」違反)。作業ツリーには監査役の指摘を受けて `scenes.py` 側を
`distinguishable=True`(1ナノ秒差の2時刻を区別できるかという、要件文だけから閉じた式で
導ける値の場面)に直したコードが既にあったが、`gen_definitions.py` を再実行していなかった
ため、コミット済みの `DEFINITIONS.md` は旧版のまま残っていた。

**変えた作り**: `python3 tests/bt/battery/item_0/gen_definitions.py` を再実行し、
`DEFINITIONS.md` を `scenes.py` の現状と一致させた。再実行を2回繰り返しても差分が出ない
(`md5sum` 一致)ことを実測で確認した。

## b1-4(止める)段(機構)が空欄の候補を「段が低い」でスキップしていた(34件以上)

**根本原因(この回に判明。単なる文言違反ではなく、判定の軸そのものが間違っていた)**:
`docs/DATA/tools_catalog.tsv` の列10・11(`段(機構)`/`段(既定)`)は、列9
(`市場影響と約定の模型`)に○が付いた候補だけが埋まる、**項目3専用**の列である
(`REQUIREMENTS.md`§3.2.1 が既に「この観点には段(機構)/段(既定)の列が無い…その2列は
区分1-市場影響と約定の模型(項目3の観点)専用」と明記していた)。実測で確認: 候補61
`barter-rs` は `段(機構)` が空欄だが、`市場影響と約定の模型` 列も空欄/×であり、これは
「段が測れていない」のではなく「項目3の話(市場影響の模型)がそもそも無い」ことを意味する。
旧版の検討表は、この列を観点1・観点2-足・観点2-ティック・(削除した)観点2-板の待ち行列
の強弱判定に流用しており、無関係な軸で「弱い」と決めつけていた(委任文§3

**変えた作り**: §1の3表(観点1・観点2-足・観点2-ティック)を、`段(機構)` を一切使わない
形に作り直した。判定の軸は「その観点で確認できる能力(台帳の足/ティック/イベント駆動などの
○列、または実際の実行結果)」に統一し、スキップの理由は全行「上位互換」(実際に再現した
候補がその能力を実行で確認済み、という論拠)に揃えた。あわせて、観点2-板の待ち行列の表
そのものを項目0の範囲外として削除した(§1のリード文・削除ノート参照。理由は項目0の
P0-1〜P0-7のどれにも「板の待ち行列」という軸が無いため)。

## b1-10(聞く)観点1・足・ティック・板の待ち行列で「本当の最強候補」抜きの比較になっている

**指摘の内容**: 各観点の段(機構)最高位候補(Basana・ThePredictiveDev・homerunなど)は
「この周は未導入」として全て比較対象から外れ、実際に比較できているのは常にZiplime/
zipline-reloaded/PyBroker/qf-libの4候補に限られていた。この収斂が時間予算の制約として
避けられないものか、リードに確認する必要があるのではないか。

**場面係の回答(この場で答える)**: **一部は避けられなかったが、一部はこの回に解消した。**
候補1 `Basana` は「言語がGo」という誤判定(b1-4の訂正と同時に発見)のせいで未導入に
分類されていただけで、実際にはPyPI配布のPythonパッケージであり、`pip install basana` で
問題なく導入できた(§3導入ログ)。この回、実際に導入し、`basana.backtesting_dispatcher()` +
`FifoQueueEventSource` + `BarEvent` で**実際にイベントを流して**観点1(v1-event_driven-cap/
known: 両方一致)・観点2-足(v2-bar-cap/known: 両方一致)を実行で確認した。段(機構)最高位
候補のうち、少なくとも1件(Basana)は「時間予算の制約」ではなく「分類の誤り」で外れていた
ことになる。

残る `ThePredictiveDev`・`homerun`(いずれもGitHub限定配布でPyPIに無い)は、この回も導入・
実行できていない。`homerun` は板の写真の順次再生+自分の注文のFIFO内位置追跡という、この
バッテリーの4候補のどれも実行で確認していない機構を一次資料(SCAN 7818/7820行)で持って
いるため、**「板の待ち行列」観点があれば最強候補になりえた**が、その観点自体を項目0の範囲
外として削除した(b1-4)ため、item0の残りの観点(観点1のみ該当)では「上位互換」の対象に
なる(homerunの観点1での確認可能な能力はイベント駆動=○のみで、Basana/Ziplime/
zipline-reloaded/qf-libが実行で確認済み)。よって、**項目0の範囲では「本当の最強候補」抜きの
比較にはなっていない**という結論に至った(homerun/ThePredictiveDevの真の強みである板の
待ち行列の機構は、項目3の観点であって項目0の観点ではないため)。

ただし、観点2-ティック(約定)の候補プールが台帳の`ティック`列を流用したままである点
(§4の食い違い6)は未解消で、この点は「時間予算の制約」ではなく「候補プールの軸が本当に
正しいかをこの周は洗い直していない」という限界として、そのままリードに報告する
(迷ったときに「出さない」を選ばない。CLAUDE.md §0.2 A-18)。
