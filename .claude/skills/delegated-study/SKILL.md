# 研究・実装の委任

## 1. 分業

| 役 | 担当 | モデル |
|---|---|---|
| リード | 仮説選定・事前登録・判定・採用可否・**コミット** | — |
| データ収集 | 取得・整形・スナップショット保存 | Sonnet |
| 研究・実装 | 検証スクリプト作成・実装変更 | Opus |

**下位エージェントはコミット・プッシュしない。** 判定と採用はリードだけが行う。
事前登録(`research-protocol` skill)はリードが書き、エージェントには「逸脱禁止」として渡す。

## 2. 研究委任プロンプトの雛形

```
あなたは本リポジトリの研究エージェントです。以下を事前登録どおりに実行し報告してください。

【データ】
- <path>(<期間・行数>)。既存の <scripts/xxx.py> のローダ/RestingLimit を
  そのまま import して再利用すること(判定ロジックの乖離を構造的に排除する)。

【事前登録 — 逸脱禁止】
- 分割: <時系列60/40 の境界>
- 構成ファミリー: <列挙>。**追加禁止**
- 採用基準: 判定区間で <n>取引以上 かつ ネット<+X>bps/取引以上 かつ クラスタt≥2.0
  かつ 台地条件(隣接構成が2bps以内)
- 判定区間は一度だけ実行し、そのまま報告する
- コスト: taker 3.96bps(激動)/2.93bps(calm感度)、maker 0bps・print単位traded-through

【必須報告】
1. 探索区間の全構成表(n・ネットbps・t)
2. 判定区間の結果(構成の乗り換わりがあれば明記)
3. 逆選択の反実仮想(取り逃しをtakerで入った場合 vs 実約定)
4. アブレーション(条件を1つずつ外した寄与分解)
5. サニティ(ルックアヘッド0・ポジション重複0・再実行決定性・epoch変換クロスチェック)
6. 注意点・限界(サンプル不足、in-sample選択、近似の方向バイアス)

【制約】
- スクリプトは read-only・冪等・ネットワークなし・seed固定。docstring 冒頭に事前登録を書く
- 陰性結果をそのまま報告すること。基準未達を「惜しい」と書かない
- Do not commit. Do not push.
```

## 3. 実装委任の雛形

```
【読了必須】<対象ファイル群> を先頭から読んでから着手すること。
【変更範囲】<挙動変更の範囲>。既定値の変更は明示的に列挙し、理由を書く。
【テスト】既存スイートをフルで実行し全パスを確認。変更した挙動に対応する
  テストを新規追加する(件数を報告)。
【差分】最小diff。無関係な整形・リネーム・リファクタ禁止。
【禁止】コード・コメント・ログ・ドキュメントにモデル名(Claude/Opus/Sonnet 等)を書かない。
Do not commit. Do not push.
```

## 4. 長時間処理の規則

- **>10分の処理は切り離す**: `setsid nohup <cmd> > <scratchpad>/run.log 2>&1 < /dev/null &`
- ログは scratchpad へ。進捗は定期的に1行flushして、途中確認できる形にする
- **冪等な再開設計**: 出力を chunk 単位で書き、既存 chunk があればスキップ。途中で落ちても再実行で続きから
- `pgrep -f "<pattern>"` は**自分のコマンド文字列に自己一致する罠**がある(監視コマンド自体がマッチする)。`pgrep -f` の結果から自PIDと親を除外するか、PIDファイルで管理する

## 5. データの鉄則

- **bitFlyer の公開約定履歴は31日で消滅する**。取得可能上限は常に「直近30日」
- 検証に使ったイベントデータは必ず `backtest_data/<name>_<YYYYMMDD>/` に **gzipスナップショット**で恒久保存する(例 `storm_events_20260820/`、`burst_events_20260820/`)
- 履歴APIが提供しないもの(OKX OI、L-S比、DVOL)は `scripts/record_oi.py` 型の定期スナップショットで**自前で履歴を構築**し、数週間後に判定する
- 新鮮データ待ちの仮説は「係属(ウォッチリスト)」として事前登録だけ済ませておく

## 6. 検収(リードの仕事)

エージェントの報告をそのまま採用しない。以下を検算してから判断する。

1. **再現ゲート**: 新スクリプトの基準線が既存結果を **trade-for-trade** で再現するか(第11報 E0 で実施)
2. 事前登録との一致: 構成ファミリーが増えていないか、判定区間が複数回走っていないか
3. サニティの実在確認: ルックアヘッド0・epoch変換・決定性の出力を目視
4. サンプル数と候補数: 「n候補中m通過」を確認し、偶然で説明できないかを問う
5. 陰性なら `docs/RESEARCH_REPORT_*.md` に落とし、`KNOWLEDGE.md` の索引を更新してリードがコミットする
