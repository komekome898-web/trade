# 調査班(research-squad)

## 0. 位置づけ

**このプロジェクトは外部データを自発的に調査する仕組みが弱かった**(L-107、オーナー指摘)。
`docs/DELEGATION.md` §3 の調達票規則(経路3つ以上・到達確認日)は既にあったが、リードが実行していな
かった。調査班はこれを常設の委任役にする: 単位の着手前と週次に必ず走らせる。

**hyperresearch(jordan-gibbs/hyperresearch, MIT)から借りたもの**(ファイルではなく構造):
width-sweep(検索幅を変えて3回撃つ)探索計画、引用・要約の一致確認、有料/閲覧不能ソースの代替経路
(open-access recovery)、ブロック済み取得を捨てずに記録する escalation queue → 本skillでは
「プローブの生ログ」として実装。**settings.json の PreToolUse hook は導入しない**
(`hyperresearch install` が入れる Glob/Grep/WebSearch/WebFetch 全体への副作用フックで、この
リポジトリの「`.claude/` への無審査の変更を避ける」方針と衝突するため)。

## 1. 分業とモデル

| 役 | 担当 | 備考 |
|---|---|---|
| リード | 需要の確定・監査(検収)・`DATA.md`/`STRATEGY_IDEAS.md`/`SCAN_*.md` へのマージ判断 | コミットはリードのみ |
| 調査班(下位モデル) | プローブ実行・ログ保存・テンプレートどおりの報告 | 下位モデル。**コミット・プッシュしない** |

## 2. 3モードの共通ルール

- **到達不能は「この環境から不可(方法・HTTP コード)」と書く。** それだけで終わらせず、
  第2経路(オーナー PC)を必ず挙げる。オーナー PC は常に「2番目の経路」として列挙する
  (この環境が塞がれていても、オーナー PC のネットワーク/地域/契約では通ることがある)。
- 各主張に **事実 / 推定 / 仮定** の印を付ける(`docs/DELEGATION.md` §3)。
- 予算: 1回の実行で調査班トークンの目安5万以内・実時間20分以内。超えたら中断し「未完了」で途中報告する。
- **禁止事項**:
  - 戦略・データの当否判定をしない(「使える/使えない」の最終判断はリード)
  - `research-protocol` の事前登録(PREREG.md)・判定を書き換えない
  - `docs/STRATEGY_IDEAS.md` / `docs/DATA.md` への直接マージ(候補を出すだけ。マージはリード)
  - リポジトリ・コミットメッセージにモデル名を書かない
  - 秘密情報(APIキー等)をログ・報告に書かない。有料APIは鍵の有無を書くだけで鍵そのものは書かない
  - 大きい一括ダウンロード(小さいプローブ = HEAD/GET数件のみ。本体取得は別途リードの承認を得た単位で行う)

## 3. モード1: 調達調査 `/research-squad procure <データ需要>`

### 手順
0. **範囲の列挙(L-141、KA-31)**: 需要が「取引所・市場・商品・経路」を含むなら、経路を調べる前に
   **対象になりうる全体集合を出典付きで列挙する**(規模の順位(建玉・出来高)、区分(CEX / DEX /
   国内)、出典 URL と取得日)。そのうえで調べる対象と**外す対象とその理由**を表にする。
   既存台帳(`docs/DATA.md`)にある名前をそのまま範囲にしてはならない。全体集合の無い調達票は
   範囲が「未確認」であり、リードは検収で差し戻す。
1. 需要ごとに **経路を3つ以上** 列挙する。固定カテゴリ: **この環境 / オーナーPC / 公開アーカイブ・API /
   第三者データ / 有料**(該当しないカテゴリは「該当なし」と明記して省略しない)。
2. **この環境からプローブ可能な経路は実際にプローブする**(`curl` は `$HTTPS_PROXY` 経由の
   HEAD/GET、または WebFetch)。小さいリクエストのみ(1件・数KB程度)。
3. 生ログを `docs/DATA/probes/<date>_<slug>.log` に保存する。各行に **方法・URL・HTTPステータス・
   バイト数・先頭200文字・取得日時(UTC)** を残す。
4. `docs/DATA.md` に資産ごとの行を追記する(直接マージはリードの検収後 — 調査班は追記案を報告に書く)。

### `DATA.md` 行の必須列
資産 / 所在 / 範囲 / 状態 / 最終確認日 / プローブのログ / 使った単位

状態 ∈ {**取得済**, **PC に未共有の可能性**, **未試行**, **試行して不可(範囲・方法)**}。
**「取れない」は 範囲・方法のセルとプローブのログパスの両方が埋まっていなければ書いてはならない**
(CLAUDE.md §5.2、否定的主張は射程を書く)。

### 委任プロンプトの雛形
```
あなたは本リポジトリの調査班です。次のデータ需要について調達調査を行い、報告してください。

【需要】<データ需要をそのまま>

【手順】
0. 需要が取引所・市場・経路を含むなら、まず対象になりうる全体集合を出典付きで列挙し(規模の順位・
   CEX/DEX の区分・出典URL・取得日)、調べる対象と外す対象の理由を表にする(既存台帳の名前を
   そのまま範囲にしない)
1. 経路を3つ以上、固定カテゴリ(この環境/オーナーPC/公開アーカイブ・API/第三者データ/有料)で列挙
2. この環境からプローブできる経路は実際に叩く(curl は $HTTPS_PROXY 経由、小さいHEAD/GETのみ。
   もしくは WebFetch)。オーナーPC 経路は「PCでの到達確認が必要」と明記するだけでよい(実行不可)
3. 生ログを docs/DATA/probes/<今日の日付>_<slug>.log に保存(方法・URL・HTTPコード・バイト数・
   先頭200文字・UTC時刻を1エントリずつ)
4. docs/DATA.md に追記する行の案(資産/所在/範囲/状態/最終確認日/プローブのログ/使った単位)を
   報告に書く(ファイルへの実際の追記はリードが検収してから行う)

【禁止】
- 大きい一括ダウンロード禁止。プローブは数件・小サイズのみ
- 「取れない」と書くなら範囲・方法とログパスを必ず添える
- データの当否・戦略への使えなさを判定しない
- モデル名を書かない。Do not commit. Do not push.
```

## 4. モード2: 市場・環境調査 `/research-squad scan [週次|<テーマ>]`

### 手順
1. **width-sweep 検索計画**: 検索幅を3段(狭い/中間/広い)× 日本語・英語 の**最大6クエリ**を先に
   書いてから実行する(検索してから幅を決めない — hyperresearch の width-sweep の借用点)。
2. 各出典は **URL + 取得方法(WebSearch/WebFetch) + 取得日** を記録する。
3. 各知見に **事実/推定/仮定** の印と、**「このプロジェクトへの含意」列**を付ける(無ければ「無し」
   と明記。憶測で含意を作らない)。
4. `docs/DATA/SCAN_<date>.md` に追記する(新規ファイル、日付ごと)。
5. `docs/STRATEGY_IDEAS.md` / `docs/DATA.md` 向けの**一行候補**を報告の末尾にまとめる
   (**提案のみ。自動マージしない** — リードが検収してから該当ファイルに反映)。

### 出力テンプレート(`SCAN_<date>.md` へ追記する形)
```
## <テーマ> — <日付>

### 検索計画
| 幅 | 日本語クエリ | 英語クエリ |
|---|---|---|
| 狭い | ... | ... |
| 中間 | ... | ... |
| 広い | ... | ... |

### 出典
| URL | 方法 | 取得日 |
|---|---|---|

### 知見
| 知見 | 印(事実/推定/仮定) | このプロジェクトへの含意 |
|---|---|---|

### STRATEGY_IDEAS.md 向け候補(提案。未マージ)
- ...

### DATA.md 向け候補(提案。未マージ)
- ...
```

### 委任プロンプトの雛形
```
あなたは本リポジトリの調査班です。次のテーマで市場・環境調査(scan)を行ってください。

【テーマ】<週次 または 具体テーマ>

【手順】
1. 検索幅3段(狭い/中間/広い)×日本語/英語で最大6クエリの検索計画を先に書く
2. 出典ごとに URL・取得方法・取得日を記録
3. 知見ごとに 事実/推定/仮定 の印と「このプロジェクトへの含意」列を付ける(無ければ「無し」)
4. docs/DATA/SCAN_<今日の日付>.md に追記する形で出力する(上のテンプレートに従う)
5. STRATEGY_IDEAS.md / DATA.md 向けの一行候補を提案としてまとめる(マージしない)

【禁止】戦略の当否判定・事前登録の変更・自動マージ・モデル名の記載。Do not commit. Do not push.
```

## 5. モード3: 一次資料の確認 `/research-squad verify <主張>`

### 手順
1. 主張の一次資料(取引所の公式ドキュメント・公式APIリファレンス・論文・規制文書)を特定する。
   **設定ファイルのコメントやモデル自身の記憶は一次資料として認めない。**
2. 該当箇所を**そのまま引用**し、URL と取得日を添える(引用は要約ではなく原文の抜粋)。
3. 判定を3値のいずれかに分類する:
   - **一次資料で確認**
   - **一次資料と矛盾**
   - **一次資料に到達できず(方法・コード)**
4. 引用と一致するかの検算(citation/quote integrity — hyperresearch の cite-check の借用点)を
   自分で1回やり直す: 引用箇所が実在のURL・実在のテキストと文字単位で一致するか確認する。
5. 有料・閲覧制限に当たった場合は、まず鍵不要の代替(取引所の別ドキュメント、archive.org 等)を
   1つ試してから「到達できず」と結論する(hyperresearch の open-access recovery の借用点)。

### 出力テンプレート
```
## 主張
<検証対象の主張をそのまま>

## 一次資料
- URL: ...
- 取得日: ...
- 取得方法: WebFetch / curl(方法を明記)

## 引用(原文そのまま)
> ...

## 引用の検算
一致 / 不一致(不一致なら差分を書く)

## 判定
一次資料で確認 / 一次資料と矛盾 / 一次資料に到達できず(方法: ..., コード: ...)

## 代替経路を試したか
はい(経路: ...) / いいえ(理由: ...)
```

### 委任プロンプトの雛形
```
あなたは本リポジトリの調査班です。次の主張を一次資料で確認してください。

【主張】<検証対象>

【手順】
1. 一次資料(取引所公式ドキュメント・公式APIリファレンス・論文)を特定する。
   設定ファイルのコメントやモデル自身の記憶は一次資料として使わない
2. 該当箇所を原文のまま引用し、URLと取得日を添える
3. 引用がURLの実在テキストと一致するか検算する(自分でやり直す)
4. 有料/閲覧制限に当たったら鍵不要の代替経路を1つ試してから結論する
5. 上のテンプレートで報告し、判定を3値のどれかに分類する

【禁止】主張の当否を戦略的に評価しない(一次資料と合っているかだけを見る)。
モデル名を書かない。Do not commit. Do not push.
```

## 6. リードの検収(委任の実行後、必ず行う)

1. プローブの生ログが実在し、報告の主張と一致するか(ログを開いて確認)。
2. `procure` の「試行して不可」に範囲・方法とログパスが付いているか。
3. `scan` の提案が `STRATEGY_IDEAS.md`/`DATA.md` に**無審査でマージされていない**か。
4. `verify` の引用が実在するURLの実在するテキストと一致するか(サンプルで再確認)。
5. 検収後、リードが `docs/DATA.md` / `docs/DATA/SCAN_*.md` / `docs/STRATEGY_IDEAS.md` への反映と
   コミットを行う(調査班自身はコミットしない)。
