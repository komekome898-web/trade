# 研究プロトコル(事前登録型検証)

報告12本を出して過学習採用ゼロを保った規律。**走らせる前に**このチェックリストを埋める。

## 0. 研究の形(2026-09-08 オーナー規定。**これが既定**)

```
(探索) → 案 → 検証 → なぜそうなるのかの理解 → 改良 → 再検証 → …
```

**判定は途中経過であって出口ではない。** 旧来の形は「案 → 検定 → 判定 → 終了」で、
ループが存在せず、59 本の報告のほぼ全部が判定で終わっていた。これを既定から外す。

### 0.0 探索段(2026-09-12 オーナー承認、L-144。**事前登録の前に置く**)

**仮説を作るためにデータを見てよい段**。これが無いと、仮説は手元の在庫と過去の枠組みからしか
出てこない(L-142 の診断、原因 3)。探索は**生成**であって判定ではないので、事前登録は要らない。

守る条件は 2 つだけ:

1. **探索で見た区間は事前登録に「探索済み」と書き、判定区間から外す。**
   見た区間で判定すると、自分が見つけた形を自分で確かめることになる(自己汚染、§8-3)。
2. **探索の結果を「陽性 / 陰性」と呼ばない。** 呼べるのは「観察」「気づき」「仮説の候補」まで。
   探索で出た数値を報告や NEGATIVE_FACTS に「効果があった / 無かった」として載せない。

出すもの: 観察と、そこから立てた仮説(機構の平文説明)。オーナーへは「視点の提示」の枠で出す
(`docs/DELEGATION.md` §5.1。判断を求めない)。

### 0.1 各段が出すもの

| 段 | 出すもの | 満たさなければ |
|---|---|---|
| **案** | `docs/STRATEGY_IDEAS.md` の 1 件。機構の平文説明(何が効くと主張しているのか) | — |
| **意図合わせ** | **`INTENT_MAP.md`(§0.5)。意図の 1 項ずつと実装の対応表** | **事前登録を書かない** |
| **検証** | 事前登録どおりの測定。MDE(§4.1)を先に書く | 実行しない |
| **なぜ** | **観測された結果を生んだ機構の説明**。数値ではなく因果。「どこで・何が・どう効いた/効かなかったか」 | **報告は不合格**(§0.2) |
| **改良** | 「なぜ」から**導かれる**設計変更。1 回につき 1 つの機構仮説に対応させる | §0.3 に反すれば禁止 |
| **再検証** | 改良後の設計を新しく事前登録して測り直す | 事前登録なしの再測定は禁止 |

### 0.2 「なぜ」を出さない報告は不合格(**差し戻す**)

棄却だけを返す報告、数表だけの報告、「基準に届かなかった」で終わる報告は受理しない。
最低限、次の 3 つに答える:
1. **どこで負けた/勝ったか** — 出口内訳・状態別・時間帯別など、損益の在り処を分解する
2. **その分解から言える機構は何か** — 「〜が〜を食っている」の形で書く
3. **その機構は設計のどこに触れば動くか** — 触れる場所が無いなら、無いと書く(それも「なぜ」である)

### 0.3 ループと総当たりの違い(**ここを外すと事前登録の意味が消える**)

改良の再検証は、放っておけば「通るまで試す」に堕落する。次で線を引く。

- **改良は「なぜ」から導かれていなければならない。** 機構の説明なしに水準を動かすのは
  パラメータ探し であって改良ではない。**禁止**(§8-3 の掘り出しと同じ扱い)。
- 1 回の改良は **1 つの機構仮説**に対応させる。同時に複数いじったら、どれが効いたか言えない。
- **ループ回数は台帳(`ITER.md`)に累積し、報告と帰無の多重性に必ず算入する。**
  「第 k 周で通った」は「k 回試した中の最良」であり、そのように評価する。
- ループが回るのは**開発側**。**判定(封印・新鮮データ)は設計ごとに一度だけ**。
  設計を変えたら判定窓も新しく用意する(使い回すなら候補数を合算する)。
- **収束しないループは止める**: 改良のたびに新しい機構仮説が出てくる(前の説明が持たない)なら、
  それは理解が進んでいない兆候。3 周続いたら止めて、理解できていないことを報告する。

### 0.4 ループの出口

- **陽性** → 次段(フレッシュデータ・ペーパー)へ。ループは続く(改良の対象が変わるだけ)。
- **陰性**(§5)→ 射程を書いて休止。**扉は閉じない**。「この機構は、この射程では効かない」で終える。
- **不明**(§5)→ 必要な n を書いて休止。データが増えたら再開する。
- どの出口でも、**得られた機構の理解を報告本文に残す**。それがループの本体の成果物である。

### 0.5 意図とロジックの突き合わせ(**事前登録より前。オーナー規定 2026-09-09、L-043**)

**なぜ必要か**: 結果が悪かったとき、原因は必ず次の 3 つのどれかである。

1. **機構にエッジが無い**
2. **機構の構築が戦略意図を反映していない**
3. **機構のバグ**

**検証を進めてからでは、この 3 つを分離できない。** 判定を見た後に「実装が意図と違ったのかも」と
言い出せる状態は、判定を無意味にする(どんな陰性も実装のせいにできてしまう)。
だから **2 と 3 は、測る前に潰す**。

**成果物**: `INTENT_MAP.md`(単位ディレクトリ直下)。書式は本skill §15(旧 `docs/PHASE2_TEMPLATES.md` §8)。
手本: `docs/legacy/KATSUO_INTENT_MAP.md`。

**書き方の規則**:

- **意図は先に、単独で、文章として固定する。** 出所を明記する(オーナーの発言なら
  `OWNER_LOG` の L 番号、リードの案なら `STRATEGY_IDEAS.md` の番号)。
  **実装を見てから意図を書いてはならない** — 実装に合う意図を書けてしまう。
- **意図を項目に割る。** 1 項 = 1 主張。「ヒゲが長いほど反発する」「弱いシグナルでは決済に留める」
  のように、**それ単独で実装の有無を判定できる粒度**まで割る。
- 各項に**実装の場所(行番号 / 関数名)と印**を付ける:

  | 印 | 意味 | 測る前にやること |
  |---|---|---|
  | **○** | 意図どおり実装されている | — |
  | **△ 代理** | 意図そのものではなく**代理変数**で実装されている | **代理が悪い可能性を別の測定で切り分ける**(できないなら射程に書く) |
  | **✕ 未実装** | 意図にあるが実装が無い | 実装するか、**射程外と明記**するか。黙って測らない |
  | **＋ 意図に無い** | 実装にあるが意図に無い | **第 1 周では外す**。残すなら理由を書く |

- **コード側からも走査する。** 意図の項から実装へ辿るだけでは、**＋(意図に無い実装)を見落とす**。
  実装の分岐・定数・注文の作り方を全部並べ、**どの意図項にも紐付かないものを ＋ として挙げる**。
- **バグは意図合わせの一部である。** 実装が意図と違って動く箇所(条件の反転・符号・
  状態の取り違え)を挙げ、**検証で直すのか原典のままにするのかを先に決めて書く**。
- **「代理で実装」(△)が 1 つでもあるなら、代理の妥当性を測る手段を事前登録に含める。**
  含められないなら、その単位の陰性は「機構が無い」ではなく「**代理では捉えられない**」までしか
  言えない。**それを射程に明記する**(§5)。

**外す作業の点検(2026-09-09、L-046 で追加。リードが自分で破った)**:
＋ を外したあと、**外した結果として ○ や △ が巻き添えになっていないか**を、
もう一度意図マップに突き合わせる。K1 では「意図に無い執行の工夫を外す」つもりで
主指標を固定保有にした結果、**意図に入っている決済ルール(○)を消していた**。
とくに **「測る対象の定義」を単純化するとき**に起きやすい —
単純化は実装を削るのではなく、**意図を削っていることがある**。

**検収**: `INTENT_MAP.md` の無い事前登録は受理しない。**意図がオーナー由来なら、
オーナーの確認を取ってから事前登録に進む**(CLAUDE.md §8 の枠組み事項)。

**報告での使い方**: 陰性を返すときは、**この表のどの行によって「2 と 3 ではない」と言えるのか**を
本文に書く。書けないなら、それは陰性ではなく**不明**である(§5)。

## 1. 事前登録 — 実行前に固定する

スクリプトのdocstring冒頭に以下を書き切ってから1行も実行しない。

- **`INTENT_MAP.md` へのパスと、その最終更新**(§0.5。無ければ実行しない)
- **各数値の出所を 3 分類で明記**(2026-09-09、I-004 で追加):
  **一次資料**(URL と取得日)/ **実測**(スクリプトと対象データ)/ **仮定**。
  **仮定にはさらに「誰の仮定か」**を書く — オーナーの発言 / **リードの記憶** / 業界慣行。
  **リードの記憶は「仮定」である。一次資料でも実測でもない。**
  同じセッション内で、モデルの記憶がベニューの重要事実(取引所の閉鎖)を取り違えた実例がある。
  出所の表示を後から**付け替えない**。誤っていたら**追跡表を残して撤回**する。
- **記号の一意性**(同上): **一度定義した記号を別の量に使い回さない。**
  量が変わったら**記号も変える**(例: `sd_all` / `sd_sig` / `sd_trade`)。
  訂正するときは**古い定義を消してから**新しい定義を書く。追記だけで済ませると、
  同じ文書に矛盾する定義が同居し、**どの主張も後から別の意味だったと言い直せる**ようになる。
- 対象データ(パス・期間・行数)
- 分割(探索/判定の境界日時)
- 構成ファミリー: **列挙する。後から追加しない**
- 採用基準(数値バー)と選択規則(どの指標でどう1つ選ぶか)
- 判定区間は**一度だけ実行し、そのまま報告**

例: `scripts/research_calm_range.py` / `scripts/research_exit_surface.py` のヘッダ。

### 1.1 **準備測定も測定である**(2026-09-09、I-005)

事前登録に載る数値(`sd`・MDE・n・保有分布・シグナル頻度)を作る測定は、
**本番の測定と同じ厳しさで扱う**。K1 では、この扱いを外したせいで
**事前登録が定義した決済ルールを実装していない準備測定**の値が事前登録に載り、
**オーナーの指示を覆す根拠にまでなっていた**。

1. **定義との条項ごとの突き合わせ。** 「この測定は事前登録の §いくつの、どの条項を
   実装しているか」を**1 行ずつ**照合する。K1 の事故は、§4.2 が
   「無効化 **または** 反対シグナルの早い方」と定めた決済の**片方の枝が実装から落ちていた**
   というもので、条項を 2 つ読むだけで見つかった。
2. **§8 のサニティのうち適用可能なものを通す。** 準備測定を §8 の外に置かない。
3. **決定を覆す測定は、独立に再現するまで根拠にしない。**
   別実装で測り直すか、**構成要素を分解した変種を並べて**、数字がどこから来ているかを示す。
   オーナーの指示や既存の合意を覆す測定なら、なおさら。
4. **網羅性を先に満たす。** 族の全水準について測る。一部だけ埋めて残りを「未測定」に
   したまま事前登録を完成と呼ばない — **MDE を書けない水準が残っていれば §4.1 違反**である。
   K1 の事故は、オーナーの「**なぜこの水準は外れているのか**」という**網羅性の問い**で
   発覚した。**正しさの検査ではなく、偶然だった。**

> **教訓の一般形**: 「準備」「下ごしらえ」と呼んだ瞬間、その作業は検査の外に出る。
> **出力が事前登録に載るなら、それは準備ではない。**

### 1.2 **数値は手で書かない。生成する**(2026-09-09 オーナー指摘、L-054)

**背景**: K1 は独立監査を 2 回受け、**29 件 → 37 件**(重大 10 → 18)と**増えた**。
しかも重大の少なくとも 5 件は、**1 回目で直したのと同じ型が、直しの過程で新しく書いた節に再発**した。

**族を小さくしても直らない。** リードは「族を 198 → 12 に減らす」と提案したが、
**その提案文の中で、2 つ前の返答で自分が否定したばかりの誤り**(`bigbeardline` を「門」と呼ぶ)
**を繰り返した**。オーナーの指摘: 「**族の多さと設計質に相関はなく、根本原因は別にある**」。正しい。

**根本原因**: **検証より速く断定を書き、断定ごとの検証を強制する仕組みが無い。**
実際の欠陥は、どれも**数秒から数分で確かめられた**ものだった —
掛け算を 1 回、逆関数を 1 回、表を 1 つ見る、自分が 2 つ前に書いた文を読む。

**欠陥は 2 種類あり、対処が違う**:

| 種類 | 例 | 対処 |
|---|---|---|
| **A 誤った断定** | 「全面差し替え」(実際は 3 列中 1 列)/「9 割減る」(実際は 55%)/「144 通り」(実際は 48)/「条件 2 が条件 1 を包含」(実際は逆) | **数値を書ける場所を無くす** + **計算を評価させる** |
| **B 抜け落ち** | 封印区間の判定規則が無い / 信頼区間の出し方が無い / 補助帰無が実行できない | **必須項目の存在検査** |

**A への対処 — 生成**:

- 事前登録は **`PREREG.md.tmpl`(手で書く)+ 測定出力 → `PREREG.md`(生成物)** の形にする
- テンプレートには `{{cell:15|s19/b24|both.sd_trade_bp}}` のような**参照**だけを書く。
  **参照がセル名を含むので、「どのセルの数字か書いていない」も起こせない**
- `scripts/render_prereg.py` が埋め、**出荷前検査(§1.3)の C8** が
  「生成し直した結果と現在の文書が一致するか」を見る
- **`PREREG.md` は手で編集しない。** 編集するのは `.tmpl` の方

**A への対処 — 計算の評価**:

- 計算を伴う断定は **`【計算: 式 = 値】`** と書く。**出荷前検査 C10 が式を評価して突き合わせる**
- 評価できない式に「計算した」と称せない。書けない主張は **`【未検証】`** と印を付け、
  **判定条件の変更根拠には使えない**

**B への対処 — 必須項目**:

- **出荷前検査 C9** が、事前登録に必ず要る項目の存在を見る
- **必須項目は「実際に抜けた実例」からだけ足す**(想像で増やさない)

> **未処理を隠さない**: 層 1 が指摘を返している間は、テストで「0 件」と主張しない。
> **既知の未処理の一覧と完全に一致すること**を主張する
> (`tests/test_preflight_prereg.py` の `KNOWN_OPEN`)。
> 新しい欠陥が入れば赤くなり、直したのに一覧から消し忘れても赤くなる。
> **「0 件」と書いた瞬間、直っていないものが直ったことになる。**

### 1.3 出荷前検査 — **実行の前に 3 層を通す**(2026-09-09 オーナー指示、L-050)

**背景**: 2026-09-09 の 1 日で、**オーナーの問い 9 回からリードの誤り 8 件**が出た。
同じ期間、**リードの自己点検では 0 件**。原因は注意力ではなく**視点**である
— 自分の文書を自分で読むと、書いたときと同じ視点で読むので矛盾が見えない。
だから「気をつける」ではなく、**成果物が出て落ちたら止まる仕組み**にする。
手本は `docs/PHASE2/K1/PREFLIGHT.md`。

| 層 | 中身 | 不合格条件 |
|---|---|---|
| **1 機械検査** | `PYTHONPATH=src python scripts/preflight_prereg.py <PREREG.md>` | **1 件でも出たら実行しない** |
| **2 3 つの読み** | 視点を宣言して読み、**表を出す**(下記) | ✕ が残れば実行しない |
| **3 独立監査** | 事前登録・意図マップ・原典・準備測定**だけ**を渡した下位モデルに「欠陥を挙げよ」 | **重大**が出たら実行しない |

**層 2 の 3 つの読み**(同じ視点で 3 回読んでも同じものしか見えない。**視点を先に宣言する**):

- **読み A(実装者)**: 事前登録の条項を**1 つずつ**、実装のどこが担うか指差す。
  **両方向で見る** — 条項にあって実装に無いもの(I-005)と、
  **条項に無いのに実装が黙って決めたもの**(K1 の A-1)。裏表で同じ事故である。
- **読み B(反対尋問)**: 各数値に 4 つの問いを当て、**表にする**。
  ①どこから来たか ②同じ言葉が前と同じ意味か ③**仮説から出たか都合から出たか**
  ④**この単位が答える問いの入力か**。
  ③で「都合」に分類された数値は、**それ自体が指摘候補**である
  (K1 では帰無 1,000 回がこれで拾われた)。
- **読み C(門外漢)**: 専門語と論理の飛躍。**式は検算できる形になっているか**。

**層 3 で渡してはいけないもの**: `docs/OWNER_LOG.md` / `docs/INCIDENTS.md` /
`docs/DISCUSSIONS/`。**「どこが処理済みか」を読むと、監査人がリードと同じ視点になる。**

> **検査の精度も検査の一部**: 誤検出を放置すると「どうせ誤検出」で本物を見逃す。
> **各検査には、実際に起きた欠陥を再現した文書で発火することを確かめるテストを付ける**
> (`tests/test_preflight_prereg.py`)。**何も検出しない検査は無いより悪い** —
> 「検査を通った」が「正しい」の代用品になるからである。

## 3. コスト・執行モデル(**定数は持たない。単位ごとに測る**)

2026-09-08 の全捨てで、この節にあった実測定数(taker 片道・スプレッド・逆選択の水準)は**すべて失効**した。
理由は CLAUDE.md §5.2 — 摩擦の見積りが 3〜20 倍過大で、それが全棄却の判定バーになっていた。

- **各単位は自分でコストを測り、事前登録にその測定方法と値を書く。** 他単位の値を流用しない。
- 制度の事実(手数料率・呼値・売買単位)だけは `config/constants.yaml` の
  `primary_document` 由来の項目を使ってよい。`status: discarded_2026-09-08` が付いた値は使えない。
- **摩擦の見積りにはバイアスの向きを書く。** 高めに見積もることは「安全」ではない —
  棄却方向のバイアスであり、採用方向のバイアスと同じだけ有害である。
- maker 約定判定は保守則(print 単位の traded-through、反対側の約定が指値を叩き抜けた時のみ約定)を既定とするが、
  **保守則を使ったこと自体を結果の解釈に明記する**(どちら向きにどれだけ歪むか)。
- **逆選択の反実仮想を必ず報告**: 「取り逃したシグナルを taker で入っていたら」vs「実際に約定した分」。
  水準は単位ごとに測る。

### 3.1 **その単位の位置に合うコストだけを扱う**(2026-09-09、オーナー指摘、L-048)

単位には**上流(現象が実在するか)と下流(実際に取れるか)**があり、
**上流の単位に下流の制約を持ち込むとノイズになる**。

- **上流の単位(シグナルの強度を測る)では、コストを引かない。水準を仮定もしない。**
  成果物は「**効果量(bp)+ 信頼区間 + MDE**」であって合否ではない。
- **下流の単位(執行を含む)で初めて、その執行先の実測コストと差し引く。**
- **判定バー(§4-2 のネット期待値バー)は下流の単位にだけ課す。**
  上流の単位では **MDE がそのまま陰性の射程**になる
  (「効果が無い」ではなく「**MDE を超える効果は不在**」)。

**なぜ上流でコストを引くと壊れるか**:

1. **上流の成果物は合否ではなく「なぜ」**(§0.2)。バーを下回った時点で「なぜ」を書く作業が止まり、
   **下流への入力が消える**。
2. **上流の効果量は改良前の値**である。改良前の値を、改良後に払うコストで足切りするのは順序が逆。
3. **測定したベニューと執行するベニューが違えば bp は移らない。** 移らない量どうしの引き算になる。

> **落とし穴(実際に踏んだ)**: 古いコストの仮定を外した直後に、
> **「代わりに現在の執行先のコストを MDE の床にする」と提案した。**
> これは**同じ誤りを 1 段ずらしただけ**である。**外すのは「その数字」ではなく「コストという入力」。**

**ただし消してはならない**: コストの検査を上流から外すときは、
**下流の単位の入口に「上流の効果量 vs 実測コスト」の突き合わせを関門として事前登録する**。
移す先を書かずに外すと、何ヶ月も進んでから「そもそも払えない」に気づく。

## 4. 採用基準の型

判定区間で以下を**すべて**満たすこと。

1. 最低取引数 **≥100**(イベント系は **≥30イベント**)
2. ネット期待値バー(単位ごとに事前登録する)。
   **上流の単位(執行を含まない = シグナル強度を測る単位)にはこのバーを課さない** — §3.1。
   代わりに効果量 + 信頼区間 + MDE を報告し、**MDE を陰性の射程として書く**
3. 日次 or イベントクラスタ **t ≥ 2.0**(ブートストラップCIがゼロを除外)
4. グリッド勝者は **台地条件**: 隣接構成(各軸±1ステップ)が候補から大きく劣化しない

### 4.1 検出力を先に書く(**必須**。これが無い事前登録は実行しない)

- 事前登録に **MDE**(この n・この分散で検出できる最小効果)を**走らせる前に**書く。
- **欲しい効果 < MDE なら、その単位は実行しない。** データを増やすか、設計を変える。
- 実行後、効果が MDE 未満だった場合の結論は「**不明**」であって「効かない」ではない。
- **MDE を書いていない測定を、陰性として引用してはならない。**

### 4.2 帰無の作り方(2026-09-13、I-009。**これが無い事前登録は実行しない**)

比較の相手(帰無)を間違えると、どんなに丁寧な検定も意味を失う。**当たり前のことを
「予測できた」と読んでしまう。**I-009 が実例(±20% に一様と仮定した帰無に対し、実際の清算の
99.4% は ±5% に集中していた)。

- **対照群が作れるなら、計算式の帰無ではなく対照群を使う。** 同じ手続きを、効かないはずの入力に
  当てて得た分布が帰無である(例: 帯を同じ幅のまま位置だけ乱択する / 規模を揃えた清算なしの窓)。
  **対照群は仮定を要求しないので、仮定を間違えようがない。**
- 対照群が作れず計算式で帰無を置くときは、**その式が含む分布の仮定を事前登録に 1 行で明記し、
  その仮定を実データで確かめた結果を併記する。** 確かめていない仮定の上に帰無を置かない。
  (「帯の幅 ÷ 範囲」は「その範囲に一様に起きる」を仮定している、という類の明示)
- 仮定の確認は**判定区間の外**で行う(探索段。§0.0)。
- **結果が全セル一様に同じ向きで出たら、まず帰無を疑う。** 機構が全条件で同じだけ効くことは稀で、
  一様な勝ちは多くの場合「比較の相手が弱い」ことの表れである。

## 5. 結果の三分類(**「再監査不可」という区分は廃止した**)

旧版には「機構不成立 = 再監査不可」という永久に扉を閉じる区分があった。**廃止する。**
それが偽陰性を蓄積させた装置だったため(CLAUDE.md §5.2)。結果は次の 3 つに分類する。

- **陰性**: 欲しい効果 > MDE の検定で、効果の不在を測った。**射程を必ず併記する**
  (何を測ったか / 何を測っていないか)。射程の外へ一般化して引用してはならない。
- **不明**: 測ったが検出力が足りなかった。**扉は開いたまま**。必要な n を書く。
- **陽性**: 次段(フレッシュデータ・ペーパー)へ。

どの分類でも、報告には **「なぜそうなるのか」** の節を置く。**判定だけの報告は不合格**(CLAUDE.md §5.2)。

**意図合わせ(§0.5)を通っていない陰性は、陰性ではなく不明である。**
「効果が無い」と言えるのは、**測ったものが意図した機構である**と示せたときだけ。
`INTENT_MAP.md` に **△(代理)や ✕(未実装)が残ったまま**出た陰性は、
「その実装では出なかった」までしか言えない。射程にそう書く。


## 6. 必須サニティ(全部通してから結果を読む)

- ルックアヘッド **ゼロ**(特徴量の窓が判定対象の窓と重ならないこと)
  - トートロジー検出: 過去の報告、嵐の定義窓(30分リターン)の内側を読んでいただけ。**定義窓を完全に外して再測**すると56%(コイントス)
- ポジション重複 **ゼロ**、クールダウン厳守
- 取引数の妥当性(指値設置数に対する約定率が桁で異常でないか)
- **再実行決定性**(ブートストラップはseed固定、ネットワークアクセスなし)
- **pandas datetime64 単位トラップ**: 秒への変換は必ず

  ```python
  EPOCH = pd.Timestamp("1970-01-01", tz="UTC")
  t = ((idx - EPOCH) / pd.Timedelta("1s")).to_numpy(dtype=float)
  ```

  `.astype("int64")` や `.view()` は us/ns/s を取り違える。過去にこれで**美しく間違った結果**が出た。変換直後にクロスチェック行を1本printする。
- 既存結果の再現ゲート: 新スクリプトの基準線(E0等)が既存結果を**trade-for-trade再現**することを検算してから差分を語る

## 7. 報告様式

- **陰性結果も第一級の成果**。`docs/RESEARCH_REPORT_<date><suffix>.md` に記録する
- 必須セクション: 事前登録 / **意図合わせの結論(§0.5。「エッジが無い / 意図を反映していない / バグ」のどれを消せたか)** / 探索区間の表 / 判定区間の結果 / **なぜそうなるのかの理解(§0.2。無ければ不合格)** / 逆選択の反実仮想 / アブレーション(要素別寄与) / **ループ台帳(周回数と各周の機構仮説)** / サニティ / 注意点・限界
- 数値は「n・ネットbps/取引・t or CI」を必ず併記。単独の平均は書かない
- 結果は報告本文に測定として書く(引用可能な「確立知識」の索引はもう作らない)
- 採用に至らなくても、機構の発見(例「指値が約定する0.86%は突き抜ける瞬間である」)は本文に残す

## 8. 禁止事項

1. **自己汚染**: 判定区間から仮説を生成 → 同じデータで検証。新鮮データが貯まるまで待ち、係属仮説として事前登録だけしておく(過去の報告)
2. 事前登録外の**診断結果を採用に格上げ**する(診断は診断のまま報告)
3. **掘り出し(fishing)**: 27候補をスクリーニングした後に3条件を通過する構成は**偶然でも出る**。候補数を明記し、台地条件とペア比較CIで潰す
4. in-sample選択構成の採用(過去の報告)
5. 「最良だから採用」ではなく「これより良いと言える構成が存在しないから維持」と書く(過去の報告)

## 9. 判断の型

エッジ採用と**分散改善**を分ける。過去の報告、中央値・勝率・sd・損失有界性で現行を支配したため「分散改善」として切替え、事前登録カウントは切替時点から**リスタート**した。基準未達のものをエッジとして採用しない。

## 10. 探索の深さ(2026-08-25 オーナー指示で追加)

事前登録の凍結が縛るのは**判定**(新鮮データ・一発勝負)であって、**探索の深さではない**。
「やってみた→ダメでした→次へ」は戦略候補の消費であり研究ではない。

- **汚染済みデータ上の探索は、点ではなく面を測る。** 単一構成の可否ではなく、
  パラメータ面(閾値×窓×遅延×地平)上のドリフト/損益の地図を作り、
  「エッジがどこに住み、どこで死ぬか」を機構として言えるまで掘る。
  旧botの開発が実際にそうであったように、試行錯誤はここで行う。
- **棄却レポートは棄却の水準を明記する**:
  - **機構水準の死**(符号法則・コスト床>ドリフト天井・頻度の壁など、
    どのパラメータでも越えられない算術)— その算術を明示して初めて主張できる
  - **点水準の死**(検証したセルが死んだだけ)— 「機構が死んだ」と書いてはならない。
    探索した方向と未探索の方向を列挙する
- **スケール規約**: 旧環境由来のパラメータは絶対値(円・BTC・秒)で持ち込まず、
  現行データの分布から相対的に再導出する(分位・ティック・中央値比)。
  時間スケールの転写も原典と一致させるか、差を適用範囲として明記する(過去の報告)。
- 深い探索は候補数を爆発させる。**掘った面の広さ(セル数)を必ず報告し**、
  そこから凍結するのは最大1〜2構成、採用判断は変わらず新鮮データの一発判定のみ。

## 11. 分母と反証者(2026-09-04 ポストモーテムで追加。`docs/DISCUSSIONS/2026-09-04_postmortem_tp_precursor.md`)

- **分母宣言**: 報告する全ての率(適合率・再現率・勝率・AUC・IC・t)に分母(母集団)を一文で明記する。
  分母が運用時に部品が動く母集団と異なるなら、その差を数字で示す。
- **整合性テスト**: 同じ効果を測る2指標(例: AUC と状態内 recall@閾値)が食い違ったら、報告せずにまず
  母集団・定義の差を探す。原因を特定するまで結論を書かない。
- **対照は仮説の反事実**: 対照を替える提案は「同じ問いへの答えか」を先に確かめる。全時刻無作為と状態内無作為の
  両方を計算して併記する。
- **撤回の手順**: 結論を動かすときは「前 → 後 → 誤りの型 → 変わったもの/変わらないもの」を1表で示す。
- **反証者レビュー(必須)**: 判定結果をオーナーへ報告する前に、リードの説明文を渡さない独立サブエージェントに
  PREREG・コード・数表だけを渡し、ポストモーテム §4 の10問(分母・対照・翻訳・相対/絶対・定義の副作用・
  データ妥当性・選択の汚染・ベンチマーク・一貫性・反証条件)に数値つきで答えさせる。致命が1つでもあれば保留。
- **標準手続き(2026-09-05 採用、既知正解テスト第 1 世代で 3 名とも判定 6/6・罠 4/4)**: 判定を「確定」と
  書けるのは、(削除済み文書) に従う**盲検再実装 2 名(下位 1 + 上位 1)**が判定クラスで一致した
  ときのみ。不一致なら**裁定 1 名**(両報告を読む)が決める。単独監査・未監査の判定は必ず「暫定」と表示し、
  実弾判断に使わない。maker 約定モデル(待ち行列・再クオート・上限 taker 決済)を含む判定は、その型の既知正解
  テストに合格するまで 2 名一致でも「暫定」。既知正解テストの合格基準は 感度・特異度・罠検出 ≥ 0.9
  ((削除済み文書))。手続き自体の改訂は、改訂後に既知正解テストを再実施してから有効。

## 12. エッジ推移(標準の副指標、2026-09-06 追加、オーナー提案)(旧 PHASE2_TEMPLATES.md より)

目的: 主指標の期待値が時間とともに拡大しているか縮小しているかを、**事前に決めた手順**で記述し、判定に使う場合はその使い方も事前登録する。
偶然の並びを「傾向」と読む誤りを避けるため、以下を一式で出す(どれか 1 つだけ出すことは禁止)。

1. **分解**: 費用後 = グロス − 費用。費用は算術(呼値・手数料 ÷ 元本)なので、まず費用の推移とグロスの推移を分けて示す。
   「成績の向上」の何割が費用の低下で、何割がグロスの変化かを表にする。
   **時間の刻み(単位ごとに事前登録、固定しない)**: 時間軸の単位 U(年・月・日・時間・標本番号など)、移動窓の長さ W(標本数)、
   集計表の区切り(暦年・暦月・日・時間帯)は、その単位の時間スケールとデータの並びに合わせて**事前登録で決める**。目安は
   「W ≈ 判定に意味のある 1 周期分の標本数」(日次で 250、5 分足で 1 か月 ≈ 1,300 本、ティックなら 1 日分など)。
   時間軸は暦時間か標本番号かも事前に選ぶ(休場またぎが不均一なら標本番号、制度日で区切るなら暦時間)。2026-09-06 オーナー指摘。
2. **移動窓**: W 標本の移動平均と、その 95% CI(ブロック・ブートストラップ、ブロック長も事前登録・2,000 回)。CI 付きで図示または表。
3. **区切り表**: 事前登録した区切り(暦年・暦月・日・時間帯)ごとの n・平均・CI。
4. **傾き**: 標本を時間軸(単位 U)に回帰した傾き(bps/U)と 95% CI(ブロック・ブートストラップ)。**傾きの MDE(bps/U)** を必ず併記する
   (単位は測る対象に合わせる — 日次なら bps/年、5 分足 1 年分なら bps/月)。MDE 未満の傾きは「見えない」と書く。
5. **前半/後半**: 期間を半分に分けた平均の差と CI。
6. **制度区切り**: 事前登録した制度変更日でのみ区分する(事後に見つけた区切りは使わない)。
7. **判定文(事前に固定)**: 「拡大」= 傾きの CI がゼロを含まず正、かつ直近 W 標本の CI が正。「縮小」= 傾きの CI がゼロを含まず負、
   または直近 W 標本の CI が負。それ以外は「判定不能(標本不足)」。**判定不能を「安定」と読み替えない**。
8. 探索面: U・W・ブロック長は事前登録で固定(変更は反復として N に加算)。移動窓の「最良の区間」や、事後に都合の良い U を選ぶことは禁止。

実装: `src/bot/research/overnight.py: edge_trend(dates, values, window=W, time_unit=U, time_axis=calendar|index, block=..., ...)`。
単位 U と窓 W は引数で、既定値を持たせない(事前登録値を明示的に渡す)。各単位の RESULTS.md に「エッジ推移」節として出力する。

## 13. 条件分析(戦略がより効く状況・不利な状況、2026-09-06 追加、オーナー指摘)(旧 PHASE2_TEMPLATES.md より)

目的: 全期間の平均だけでは「いつ効いて、いつ効かないか」が分からない。各単位は主検定(無条件)に加えて、**事前登録した状態変数**
ごとの効き方を CI 付きで報告し、差が大きい状態は次の単位(条件付き仮説)の材料にする。事後に状態を選んで主検定を変えることは禁止。

1. **状態変数の候補(事前登録で単位ごとに選ぶ。建玉時点で観測可能なものに限る)**:
   実現ボラ(20 標本)三分位 / 直前リターンの符号・大きさ三分位 / 海外市場の同日リターン(米国株・為替、時差で先に確定するもの)の符号 /
   SQ・月末までの日数 / 制度区分(事前登録した制度日) / 曜日・月 / 出来高三分位 / 建玉の泊数。
2. **出力(状態ごと)**: n、平均、95% CI(ブロック・ブートストラップ)、費用後平均、**状態間の差と CI と MDE**。
   状態ごとの MDE は無条件より大きい(n が 1/3 なら約 1.7 倍)ことを必ず併記し、「差が見えない」と「差が無い」を区別する。
3. **多重性**: 状態変数 K 個 × 水準数の全比較を「同時置換の帰無」(§5・P2-04 と同じ構成: 同じ置換世界から全統計量を計算して最大を取る)
   で扱い、最大差の帰無 95 点を併記する。これを超える差だけを「候補」と呼ぶ。
4. **判定への使い方(事前に固定)**: 条件分析は主検定の判定を変えない。差が候補水準に達した状態は、**条件付き仮説として新規単位を
   事前登録**し(探索面 N に加算)、封印が残っていれば封印で、無ければフォワードで検証する。
5. **反復の梯子(条件付き構造を持つ単位)**: 事前登録に「反復 k で追加する状態変数」の順序を書いておく(例: 1 = 実現ボラ、2 = 海外同日リターン、
   3 = SQ までの日数)。各反復は開発セットのみ、val の主指標の改善 < MDE が 3 回続けば停止(仕様 §4)。順序は変えない。
6. **記述の書式**: 状態 × 指標の表 1 枚と、「効く状況 / 効かない状況 / 判定不能な状況」の 3 行の平文要約。

実装: `src/bot/research/overnight.py: state_split(values, states, ...)`(2026-09-06 追加予定)。RESULTS.md に「条件分析」節として出力する。
