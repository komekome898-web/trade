# spread_backfill_20261002

オーナーの原文(L-532): 「何度かキルスイッチが発動してるので、抜けデータがあれば補完してください。」

bot の気配記録 `spread_FX_BTC_JPY.csv` の抜けの区間だけを、別プロセス(WebSocket)の tape から作った行で補う。
元の `spread_FX_BTC_JPY.csv` は変更しておらず、このディレクトリにもコピーしていない。

| 入力(オーナーの PC から共有・読み取り専用) | 内容 |

| `paper_logs/spread_FX_BTC_JPY.csv` | bot が REST で取った気配。529,691 行、2026-08-20T04:58:22Z〜2026-10-01T22:11:54Z。NUL バイト 196 個で壊れた箇所が 1 つ(2026-08-27 18:00〜08-28 04:19 の抜けの中)。NUL を除くと全行が 4 列で読めた(捨てた行 0) |

gaps.csv の列: `gap_id`・`start_utc`/`end_utc`(抜けの両端の bot の行の時刻)・`start_ts`/`end_ts`・`length_sec`・`kill_switch`(その区間の中に入った発動の時刻と detail、無ければ「発動なし」)・`restart_events`(区間の中の `paper_state_restored` の数)・`rows_expected`(5 秒刻みの行数)・`rows_made`・`rows_skipped`・`skipped_ticker_stale`(ticker が古くて作れなかった数)・`skipped_ltp_stale`(約定が古くて作れなかった数)・`tape_gaps_utc`(作れなかった連続区間の最初〜最後の時刻、`;` 区切り)・`note`。

## 手順(台本が行うこと)

1. bot の CSV の行間隔が閾値を超えた所を「抜け」とする。抜けの両端の bot の行は出力に含めない。
2. 抜けごとに、`bot.jsonl` の発動の時刻が [抜けの開始, 抜けの終了] に入るものを付ける。
3. 抜けの開始 + 5 秒から 5 秒刻みで、終了より前の各時刻 t について、best_bid / best_ask は ticker の「t 以前の最新の行」の値、ltp は executions の「t 以前の最新の約定の価格」。
4. 次のどちらかに当たる時刻は行を作らず、`tape_gaps_utc` に載せる: 最新の ticker が 60 秒より古い(または tape の開始前)、最新の約定が 608 秒より古い。
5. 抜けの外の bot の行について、同じ手順で tape の値を作り、REST の値との差を測る(突き合わせ)。

実行(同じ入力から同じ出力。乱数なし・ネットワークなし。gzip の時刻は 0 固定で、2 回実行して MD5 が一致することを確認した):

```
PYTHONPATH=src python3 scripts/backfill_spread_from_tape.py \
  --bot-csv  <paper_logs>/spread_FX_BTC_JPY.csv --bot-jsonl <paper_logs>/bot.jsonl \
  --tape-dir <paper_logs>/tape --out-dir backtest_data/spread_backfill_20261002
```

## 閾値と根拠

| 閾値 | 値 | 根拠(実測) |
|---|---|---|
| 抜け(`--gap-sec`) | 60 秒超 | bot の行間隔の分布は p50 = 5.068・p90 = 5.171・p99 = 7.975・p99.9 = 13.511・最大 693,875.756 秒。bot 自身の「データが古い」の定義 `config/config.yaml: market_data.max_staleness_sec: 60` に合わせた。行間隔が超えた件数は、6 秒超 17,987・10 秒超 1,486・30 秒超 167・**60 秒超 57**・180 秒超 17・600 秒超 11。分布は連続していて自然な切れ目は無い。60 秒は bot 側の定義に合わせた値である |
| 行の刻み(`--period-sec`) | 5 秒 | `config/config.yaml: poll.ticker_sec: 5`。実測の中央値 5.068 秒と整合 |

## 限界

- bot の CSV の最後の行(10-01T22:11:54Z)は tape の最後(20:29:45Z)より後。最後の bot の行の後ろの欠けは「抜け」の両端が無いので扱っていない。
- 作った行の ltp の古さは p50 = 4.1・p99 = 76.0 秒・最大 607.6 秒(300 秒超が 89 行)。約定が空いた間の ltp は「最後の約定の価格」で、REST の ltp も同じ意味だが、両者の一致は上の表のとおり約 88〜89%。
- 抜けの外の bot の行は一切変更していない。作った行を使う側は `source = tape_ws` の行を REST の行と区別して扱えること。
