## Judgment data ① (index-level, full window 2003-04〜) — NOT OBTAINED

The PREREG's primary judgment cell needs TSE REIT Index (指数, not the 1343 ETF) daily
open/close from index inception (2003-04) through 2026-09-03. This was **not obtainable
for free within this session**. Attempts made and why each failed:

1. **JPX quote.jpx.co.jp `hist_index`** (`https://quote.jpx.co.jp/jpxhp/main/index.aspx?F=hist_index&qcode=...`):
   renders a historical chart as a **PNG image** generated by `chart21.exe` — no numeric
   JSON/CSV endpoint behind it despite the URL parameter literally containing the string
   `DayIndexCSV` (that is a chart-rendering mode name, not a data format). The only JSON
   endpoint found (`../jcgi/wrap/qjsonp.aspx?F=ctl/index&qcode=`) returns current-quote
   metadata only, no time series.
2. **JPX TOPIX/REIT index pages** (`jpx.co.jp/markets/indices/topix/`,
   `/markets/indices/line-up/`): no downloadable daily index-level CSV/Excel found;
   JPX's real bulk historical index data is a paid product (JPXデータクラウド /
   JPXデータポータル, per `db-ec.jpx.co.jp/.../data_detail.pdf`).
3. **Yahoo Finance chart API, symbol `^TREIT`**: resolves but the series is empty
   (`meta` returned, no `timestamp`/`indicators` — a stale/delisted quote object, last
   `regularMarketTime` 2019-06-29). No usable data at any range.
4. **stooq.com** (`/q/d/l/?s=^treit&i=d`, also tried `1343.jp`): blocked by a
   JS proof-of-work challenge page (`/__verify`), not fetchable via plain HTTP request.
5. **investing.com** (`/indices/topix-reit-market-historical-data`): HTTP 403
   (bot-blocked).
6. **finance.matsui.co.jp** `.TREIT/daily-bar/index`: page loads but the data table is
   populated client-side via AJAX after JS execution; no data embedded in the static
   HTML and no discoverable public JSON endpoint.
7. **csvex.com (kabu.plus reseller)**: paid data product, no free bulk download found.
8. **Kabutan** (`kabutan.jp/stock/kabuka?code=0105&ashi=day&page=N`): **this one works**
   — server-rendered daily OHLC table for the real TSE REIT Index (code 0105), genuine
   index-level open/high/low/close. But the free (non-member) view is capped at 10
   pages of ~30 rows each ≈ **one year of history**, not back to 2003. Pulled pages
   1-10 (`kabutan_source_p1..p10.html`) → merged into `reit_index_daily.csv`
   (2025-06-16 .. 2026-09-03, 299 rows).

**Consequence, per PREREG §1's own built-in fallback** ("指数の四本値が入手不能なら、
判定は②のみで仮判定とし... 前進"): the script treats judgment ① (full-window,
index-level) as **unavailable in the pre-registered form** and the overall verdict is
computed as a **provisional (仮判定) call resting on judgment data ② only**, with the
partial `reit_index_daily.csv` used only for the required "ETF-vs-index same-date
comparison" report (which needs an overlap window, not the full history) and reported
separately as a diagnostic, not as a judgment-①/② pass bar. The era table ([2003-2008]
etc.) cannot be filled from index-level data and is reported as "unavailable" for all
eras except a same-date comparison over the 2025-06..2026-09 overlap.

## Judgment data ② and reference (ETF-level, 1343)

`etf_1343_daily.csv` — Yahoo Finance chart API
`https://query1.finance.yahoo.com/v8/finance/chart/1343.T?period1=915148800&period2=<now>&interval=1d&events=div`
(the `range=max` form silently degrades to monthly granularity for this symbol —
worked around by passing explicit `period1`/`period2` unix timestamps with
`interval=1d`).

Note: Yahoo's earliest daily bar for 1343.T is **2008-09-16**, not the PREREG's stated
listing date 2008-08-20 — a ~4-week gap Yahoo does not have data for (its own
`firstTradeDate` meta field agrees with 2008-09-16). Judgment data ② therefore runs
2008-09-16..2011-09-04 instead of the nominal 2008-08-20 start; reported as a data
limitation, not a protocol change. The first few 2008-09 bars have O=H=L=C and
volume=0 (illiquid/no-trade prints just after listing) — left in place; the script's
|log return|>0.10 glitch filter will drop any resulting outlier jumps and reports the
count.

`etf_1321_daily.csv` (Nikkei 225 ETF, for the correlation report) — same API/method,
`https://query1.finance.yahoo.com/v8/finance/chart/1321.T?period1=...&period2=...&interval=1d`.

## Facts to verify (§4 of the task)

- **kabu.com is blocked by this session's egress proxy** (`EGRESS_BLOCKED` for
  `kabu.com` / `www.jpx.co.jp` via the WebFetch tool specifically — plain `curl`
  through the proxy *does* reach `jpx.co.jp`, so this is a WebFetch-tool-level
  restriction, not a full network block). kabu.com pages themselves could not be
  read directly at all (any method); GitHub and web-search snippets were used
  instead.

**(a) tick size (呼値) for 1343 at ~¥1,900** — **VERIFIED**, directly from JPX's
official page `https://www.jpx.co.jp/equities/trading/domestic/07.html` (fetched
via `curl`, page dated 2026/08/06). 1343 is a "売買単位が１口のETF等" (ETF/ETN/
leverage product, 1-unit lot); at the ¥1,000〜3,000 price band the tick is
**¥1** (same as the "その他の銘柄" column at this band; only the TOPIX500 column
gets the finer ¥0.5 tick here).

**(b) SOR commission-free condition for 寄成/引成 auction orders, and whether the
1日定額 plan still exists** — **CONFLICTING EVIDENCE, reported as unresolved**:
  - Two kabu STATION API GitHub issues (`kabucom/kabusapi` #1179, #1186, read via
    WebFetch) describe the 2026-05-18 change as *expanding* which 執行条件 are
    SOR-eligible, explicitly naming 寄成/引成 as newly SOR-eligible (hence
    commission-free).
  - But kabu.com's own SOR rule page content, surfaced via a WebSearch snippet,
    states plainly: 「**SOR注文は寄付、引け、不成による注文時はご利用できません**」
    (SOR orders cannot be used for opening/closing-auction or 不成 orders) — and
    a further search shows this is the **general rule across brokers**
    (SMBC日興, Monex, similarly exclude 寄成/引成/逆指値 from SOR, because SOR's
    cross-venue quote comparison has no meaning for a single-venue auction
    order). kabu.com itself could not be fetched to resolve the discrepancy
    directly (blocked, see above).
  - **Net assessment: still 未確認, leaning toward "does NOT qualify"** — the
    industry-wide mechanical reason (SOR requires a live cross-market quote
    comparison at order time; an auction order has none) applies to kabu.com
    same as every other broker cited, and outweighs the two GitHub issue
    summaries (which may be describing a different order class, e.g. new
    stop/algo order types also mentioned in the same 2026-05 rollout, not
    literally 寄成/引成). This does not change PREREG §2 by itself (no
    substitution was performed) — it is flagged as an open item for the owner /
    for whoever implements the kabu order path.
  - On the flat-daily-fee plan: independently confirmed (via web search summary
    of kabu.com's 2026-03-24 press release, corroborated by GitHub issue #1186)
    that **the entire 手数料コース選択制度, including 1日定額, was abolished on
    2026-05-15**, superseded by the SOR-conditional zero-commission model from
    2026-05-18. If 寄成/引成 truly do not qualify for SOR, there is now **no
    flat-daily-fee fallback** — the fallback would be the per-order "ワンショット
    手数料®" model, as PREREG §2 already anticipates.
