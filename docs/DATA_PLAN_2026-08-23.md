# データ収集計画(2026-08-23、Round 17)

蓄積フェーズの収集を「何となく全部」ではなく**係属研究からの逆算**で決める。
原則: **今すぐ集めるべきデータ = 期限付きで消滅するデータだけ**。
消えないデータ(Binance 履歴等)は研究実行時に遡及取得すればよく、
先回りで貯めるのはストレージと共有帯域の無駄である。

## 3. 自宅PCで集めるもの — 今回の bot 修正

1. **WS レコーダ(継続)** — 修正: 出力ファイルをレイジーオープン化。
   bitFlyer 日次メンテ(19:00–19:10 JST)中の再接続リトライが 58 バイトの
   空 gz を毎日量産していた(実測: 19:02 前後に6個/日)。接続確立して最初の
   メッセージが来るまでファイルを作らない。
2. **ticker 抽出の追加**(`extract_tape.py`)— `data/tape/ticker_YYYYMMDD.csv.gz`
   (ts, best_bid, best_ask, best_bid_size, best_ask_size、気配変化行のみ)。
   `share_logs.bat` の既存 glob(`data\tape\*.csv.gz`)で自動共有される。
   これで S8 復活チェック・スプレッドMM f 実測・S10 スリッページ実測の3研究が
   **共有データだけで**実行可能になる。
3. **継続(変更なし)**: `record_oi.py`(15分 OI/L-S/DVOL)、スプレッド記録、
   資金調達率履歴、ペーパーログ、`extract_tape` の executions(fetch_all.bat 経由)。
4. **マルチベニュー公開データの常駐収集を追加**(`record_venues.py`、2026-08-27・Round 22)—
   bitbank / GMO / bitFlyer 現物の ticker・約定を `data/venues/` に日次 gz 追記
   (クロスベニュー・ベーシス再監査・リベート maker 判定用。GMO は 0.5 req/s 未満厳守)。

## 4. 集めない(理由つき)

- **Binance 秒データの常時収集** — 恒久アーカイブが公式提供されており遡及可能。先回り不要。
- **板 top-N の常時共有** — 20MB/日級で git 共有に過大。生 WS は PC に残るので、
  壁板研究の窓が確定した時点でオンデマンド抽出する。
- **Binance 先物(FR・OI・清算)** — HTTP 451 geo-block 実証済み (e)。OKX で代替中。
- **Deribit DVOL 拡充** — 時計の情報を超えない(リフトを下げる)と実証済み (h)。
- **現物(XRP_JPY 等)テープ** — 往復 0.55% のコスト壁で戦略空間が閉じている (BT)。
- **USDJPY 追加ティック** — FX 系はイベントライブラリ 2015–2026 構築済みで、
  bitFlyer CFD の執行対象でもない。

## 5. 運用サイクル(蓄積フェーズの定常形)

- PC: 常時記録(WS / OI / スプレッド / ペーパー)→ `fetch_all.bat` が日次で
  executions + ticker を抽出 → `share_logs.bat` で共有。
- VM: 共有を受けるセッションで判定(`judge_gates.py`)+ 31日物の期限付き
  スナップショットを取得して `backtest_data/` に積む。
- 判定可能になる順(現時点の見込み): 板7日(G7)→ S8 事前チェック+f 実測 →
  S10 探索(31日テープは確保済み)→ G1 チャンピオン30取引 → G6 OI 30日 → G8 63決済日。
