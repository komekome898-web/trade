## 2. 1 件目(価格帯の予測)— 何を測るかの設計

オーナーの原文: 「**価格毎の約定履歴の積み上げからどの価格帯で清算が起きるかの予測できるか**」。

**在庫はこの問いにそのまま対応している**: `aggTrades` が「価格毎の約定履歴」、
`liquidationSnapshot` の `price` が「清算が起きた価格」である。

**測る順序(いずれも封印の外。判定はしない)**:

1. **積み上げの作り方を決める。**約定を価格の帯(bin)ごとに積み上げる。
   帯の幅・遡る窓の長さ・出来高で重みを付けるかは**まだ決めていない。**
   **ここを決めるときに、根拠のない値を置かない**(A-12)。決め方そのものを先に書く。
2. **清算の価格が、積み上げのどこに落ちるかを見る。**帯ごとの出来高と、
   その帯で起きた清算の量の関係を出す。**これは相関であって予測ではない。**
3. **予測になるかを分ける。**「清算が起きた後に振り返ると、その価格帯に出来高があった」は
   後知恵である。**清算より前の時点だけで作った積み上げ**で、次に清算が起きる帯を当てられるかを見る。
   **ここを分けないと 09-13 と同じ型になる。**
4. **エントリー・利確に使えるか**は 3 が通ってから。使えるかどうかの判定は
   `research-protocol` に従って事前登録してから行う。**この文書では判定しない。**

**未確認と書くべきこと(いま測っていない)**:
- 清算の `price` が何を指すか(注文価格か約定価格か)。列には `price` と `average_price` の
  両方がある。**どちらを「清算が起きた価格」とするかは決めていない。**
- `aggTrades` の 1.2 GB を全期間読む費用。**測っていない。**
- 帯の幅を変えたときに結論が変わるか。**測っていない**(09-13 の教訓は「分解能で結論が変わる」だった)。

## 4. 3 件目(足りないこと・足りなくなりそうなこと)

**今日の実測から出たもの**(すべてこの日の作業で当たった):

1. **測定器は粗い価格分解能で壊れる。**40bp 刻みでタイが出て、`keep`/`refine`/`drop` で
   結論が変わる。400bp では効果が **0.000** で返り、**効果が無いときと区別がつかない。**
   → **実データの価格分解能を測らないと、陰性が信用できない。**
2. **継続(トレンド化)側は効果を 13.7% 小さく報告する。**粗い区間では
   **陰性を作る向きに偏る。**
3. **合否条件が実群の平均だけで、実群 − 対照群の差を一度も条件にしていない**(射程 13)。
   実データでの問いは「清算のあった窓と無かった窓で違うか」なので、**指標に群差が要る。**
4. **対照窓(清算が無い窓)の選び方が決まっていない**(射程 5)。
5. **カスケードの束ね方**(`gap_ms=60_000`)が実データで試されていない(射程 6)。
6. **`metrics`(建玉など)に 97 日の連続欠測がある**(`2024-03-04` 〜 `2024-06-08`)。
   **期間の約 2 割。**建玉を使う仮説は、その 2 割で測れない。**これは今日実測した。**
7. **清算のファイルが無い日が 3 日ある**(`2023-09-09` / `2023-09-23` / `2024-06-01`)。
   **清算が 0 件だったのか、取れていないのかは未確認。**取り違えると
   「その日は清算が無かった」という誤った陰性になる。
8. **リードの自己申告が当てにならない。**今日、関門の全文を 4 版出して 4 版とも欠陥、
   数の表を 2 度出して 2 度とも再現せず、**台帳に「直した」と書いたことが実物に入っていない**
   ことが 1 件あった。**測ったものは正しく、書いたものが間違っていた**という分布である。
   → **足りないのは、リードが書いたことを実物と突き合わせる手数である。**
