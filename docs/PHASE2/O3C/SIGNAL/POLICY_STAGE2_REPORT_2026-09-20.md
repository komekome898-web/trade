## (5) 設計に無い判断(全部)

1. **【解決済み】段2委任文【作るもの】2「6方策」は誤記**: 委任文【作るもの】1は明示的に
   「方策は7本(R2.7 C1 の『logistic 2 値(基準率)』を含む)」と書いているのに、直後の
   【作るもの】2だけ「6方策」と書かれている(数え違い)。**7方策(段1・R2.7と同じ ALL_POLICIES)
   で実行した**(委任文内の矛盾は【作るもの】1の明示的な「7本」を優先)。
2. **`main()`/`write_output` を段1・段2共通にした**: 委任文は「段1と同じ道具で」と指示している。
   別ファイルに複製するのではなく、`scripts/o3c_signal_policy.py` に `--stage {1,2}` を足し、
   `write_output(..., stage_no=)` で見出し・`summary.json` のキー・`synthetic_traces.csv` の
   有無だけを分岐させた(状態機械・帯・logistic 適用・価格の引き方は完全に共通の関数を通る)。
   段1の出力が変わっていないことを、この変更の前後で `--stage 1` を再実行し MD5 が完全一致する
   ことで確認した((2)節)。
3. **`load_calibration_bundle_ids`(D4 の突合)の実装**: 較正5,000件の print_id を
   `rows_continue.csv.gz` から `kind == "print"` かつ `print_id` が5,000件に含まれる行に絞り、
   その `bundle_id` 列を集合にした。委任文は「print_id → bundle_id」としか書いていないので、
   具体的な実装(pandas の `isin` によるフィルタ)は設計に無い判断。件数の突合(5,000件全てが
   見つかること)を `SystemExit` で強制した(見つからない場合は止める)。
4. **除外の判定は「後半に限定した bundle_id の集合」で行った**: `bundle_id` という文字列値は
   前半と後半で重複しうる(段2作業中に発見。テスト `test_calibration_bundle_ids_come_from_back_
   half_only` の当初案が誤った前提〈前半・後半で重複しない〉を含んでいたため修正した)。
   `select_stage2_cascades` は最初から `half == "後半"` に絞った連鎖の辞書だけを母集団にしており、
   較正5,000件の bundle_id も同じ後半データから引いているので、この重複があっても除外の正しさに
   影響しない(前半の bundle_id と誤って突き合わせる経路が無い)。
5. **`action_counts.csv` の「決済」に強制決済を合流させたままにした**: 段1のR2.7直しの選択を
   そのまま踏襲(段1報告 (5)-11 と同じ)。
6. **位置別内訳・判断の件数・出口行(per-print)は遅れ1秒だけ**: 段1と同じ「主の遅れ」の選択
   (MAIN_DELAY=1)を踏襲(段1報告 (5)-3 と同じ、R2.4 は3通りを対等に扱う)。
7. **logistic の生の確率値を出力に書かない**: 段1と同じ(判断ラベル・行動・約定価格・損益だけ)。

  分析できる)。
- logistic の較正・順位分離などモデル自体の性能数値はこの報告では扱っていない(§7.7の記録を
