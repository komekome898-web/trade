### 2.0 用語と符号(事実)

| 呼び名 | 列 | 中身 |
|---|---|---|
| **約定 VWAP** | `dist_vwap_bp` | 直前 W の**約定量**のプロファイルの重心(数量加重平均価格)− 清算価格 |
| **約定ノード** | `dist_node_bp` | 同プロファイルの**上位 10% のビン**のうち最も近いもの − 清算価格 |
| **建玉 平均建値** | `oi_dist_vwap_bp` | 直前 W の **ΔOI** のプロファイルの重心 − 清算価格 |
| **建玉ノード** | `oi_dist_node_bp` | 同プロファイルの**上位 10% のビン**のうち最も近いもの − 清算価格 |
| **側別 平均建値 / 側別ノード** | `oi_side_dist_*_bp` | taker の向きで按分したプロファイル(SELL 清算 → ロング側、BUY 清算 → ショート側)の同じ 2 つ |

**符号**: 上の 6 列は**すべて既存と同じ約束** `(位置 − p_liq) / p_liq × 1e4` である。
これに「清算の向きに正」へ揃えた列 `*_liqdir` を**別に足した**(表の値はこちら):

- SELL 清算(ロングの強制決済): `*_liqdir` = `dist_*_bp` × (+1)。**既存の列と同じ値。**
- BUY 清算(ショートの強制決済): `*_liqdir` = `dist_*_bp` × (−1)。**既存の列の符号を反転した値。**
- 対照行(側が無い): `*_liqdir` は NaN。

**正 = 価格がその位置を清算の向きに通り過ぎた後で清算が起きた**、負 = まだ通り過ぎていない。
この取り方は `docs/AUDITOR/ACTION_LOG.md` 055 でリードが「SELL は dist、BUY は −dist = 清算の
向きに正」と書いた取り方と同じである(事実。§3 で数値が一致する)。

## 4. 実装で置いた判断(該当語なしのものは全部ここに書く)

1. **約定側は 1 行も書き直していない(該当語なし)。**`scripts/o3c_oi_distance.py` は
   `o3c_price_level_table.process_day` をそのまま呼び、その戻り値の行に建玉側の列を足すだけである。
   **`o3c_price_level_table.py` は 1 文字も変えていない。**§3.1 の完全一致はこの作りの結果である。
2. **ΔOI ≤ 0 の 5 分は「積まない」であって「引かない」(該当語なし)。**
   リードの指示は「ΔOI > 0 の 5 分だけ」。建玉が減った 5 分に**どの価格の建玉が消えたか**は
   metrics からは分からないので、プロファイルから引くことはできない。
   したがって本書のプロファイルは**「その窓の中で新しく積み上がった建玉」**であり、
   **「今その時点で残っている建玉」ではない**(§5)。ΔOI ≤ 0 の件数は §2.6 に出した。
3. **5 分の境界(該当語なし)。**metrics の行 `create_time = T` を **T 時点の建玉のスナップショット**と読み、
   ΔOI(T) = OI(T) − OI(T−5 分) を **[T−5 分, T) の約定**が作ったものとして、その区間の VWAP の
   ビンに置いた。**直前の行がちょうど 5 分前にある組だけ**を使う(metrics に飛びがある所では ΔOI を作らない)。
   窓の入れ方は **T ≤ t かつ T > t − W**(t = 清算時刻 / 対照時刻)。**T ≤ t なので先読みは無い**(事実)。
4. **ΔOI > 0 でもその 5 分に約定が 1 件も無い桶は置けないので落とし、件数を数えた(該当語なし)。**
   162 件(§2.6)。黙って減らさないため `summary.json` に鍵を置いた。
5. **平均建値・ノードは「ビンの代表価格」で計算している(該当語なし)。**
   既存 `profile_stats` をそのまま呼ぶので、重心は **ビンの代表価格 exp((k+0.5)·log(1+b)) の
   重み加重平均**であり、各 5 分の生の VWAP の加重平均ではない。差はビンの幅(10bp)の半分以内。
   ノードの定義・同量のときの決め方(ビン番号の小さい方)・上位 10% の本数
   (`ceil(ビン数/10)`、最低 1 本)も既存と同じ。
6. **按分後のロング / ショートも「同じ 5 分の VWAP」に置いた(該当語なし)。**
   リードの指示は「**ΔOI をその比で按分する**」で、置く価格については何も言っていない。
   買い taker だけの VWAP と売り taker だけの VWAP に分けて置く作りも考えたが、
   **指示が変えているのは重みだけ**なので、価格は変えなかった。
   **この選び方の結果、ロング側とショート側は「同じ価格・違う重み」のプロファイルになる**
   (§2.6 のとおり重みはおよそ半々に割れるので、側別は全体とよく似た値になる。§6)。
7. **側別プロファイルの価格の範囲を全体と同じにした(該当語なし)。**
   ノードは「範囲の中のビン数の上位 10%」なので、範囲が違うとノードの本数が変わって比べられなくなる。
   範囲は「ΔOI > 0 の桶が 1 つでも入ったビンの最小〜最大」で、**間の重み 0 のビンも範囲に入れる**
   (既存の約定側と同じ)。重みの合計が 0 のプロファイル(片側に 1 も付かなかった場合)は
   ノードも平均建値も作らず NaN にする。**該当は 0 件だった**(§2.5)。
8. **欠測の判定は行ごと(該当語なし。リードの指示は「日」)。**
   読めた metrics の行から**末尾に向かって 5 分刻みで連続している区間**の先頭 T0 を取り、
   **窓の先頭 (t − W) が T0 − 5 分 以上**の行だけ建玉側を埋める。それ以外は建玉側 4 列を NaN にし、
   `oi_covered = 0` を立てる。**日単位で全部 NaN にするより NaN が少なくなる方向の判断である**
   (例: W = 8h で前の日だけ欠けている日は、08:05 以降の行が埋まる)。
   NaN にした件数は §2.5、日の一覧は `summary.json: days_with_no_oi_rows` / `days_metrics_missing`。
9. **符号を揃えた列は「足した」だけで、既存の符号の列も残した(該当語なし)。**
   `dist_vwap_bp` などは既存とまったく同じ意味のまま、`*_liqdir` を 6 列足した。
   **既存の表と比べるときは `dist_*_bp` を、清算の向きで読むときは `*_liqdir` を見る。**
10. **対照行には側別の列と `*_liqdir` を出さない(該当語なし)。**
    対照行には清算の側が無いので、「清算の向き」も「ロング側 / ショート側のどちらを当てるか」も
    決められない。無理に片方を当てず NaN にした。対照は §2.1 / §2.2 のとおり**絶対値**で並べている。
11. **レバレッジ換算の式と印(該当語なし = 式の導出は委任先)。**
    `implied_leverage = 1 / (d/1e4 + mmr)`、d = `oi_dist_vwap_bp_liqdir`(建玉の平均建値からの、
    清算の向きに正の距離 bp)。**導出**: 逆数建て(COIN-M)の建玉で、建値 P_e から価格が清算の向きに
    r = d/1e4 だけ動いたとき、証拠金に対する損失の割合はおよそ r である。清算は「証拠金の残りが
    維持証拠金率 mmr を下回るとき」なので、初期の証拠金率 1/L に対して **r ≈ 1/L − mmr**、
    よって **L ≈ 1/(r + mmr)**。**印は 仮定**:(i) 逆数建ての損益は r について線形ではない
    (P_e/P の形で効く)ので、これは r が小さいときの近似である。(ii) 建玉の平均建値を
    その清算された建玉の建値とみなしている。(iii) 資金調達率の受け払い・追加証拠金・
    段階的な維持証拠金率を無視している。
    `d/1e4 + mmr ≤ 0` は NaN。`--mmr` を渡さなければ 2 列とも全部 NaN(**数を作らない**)。
12. **量の 3 分位のしきい値は全期間の清算行の `qty` で置いた(該当語なし)。**
    日ごと・側ごとには切っていない。q50 = 17 / q90 = 296(枚)。
    境界は `qty ≤ q50` / `q50 < qty ≤ q90` / `qty > q90`。
13. **`metrics` の `create_time` を UTC として読んでいる(該当語なし)。推定。**
    日次ファイルの名前の日付と、その中の行が 00:00〜23:55 で閉じていること(288 行)、
    aggTrades の日次ファイルが UTC で切られていることから UTC と読んだ。
    **一次資料で確かめてはいない(未確認)。**ずれていれば建玉側の列だけが系統的にずれる。
14. **`--no-dedup-liq` を足した(該当語なし)。**既定は一意化**入**(リードの指示)。
    §3.1 の突き合わせは既存の表(一意化前)と同じ条件にする必要があるので、切る側の引数を足した。
15. **`--metrics-root` を `--data-root` と分けた(該当語なし)。**
    `<merged_root>` には `metrics/` が無く、建玉はリポジトリの
    `backtest_data/binance_cm_o3c_20260913/` にしかないため。
16. **対照の引き方は一切変えていない(該当語なし)。**同じ日の中で、どの清算からも ±5 分以上
    離れた時刻を一様に、清算と同数。種は `f"{seed}|{day}"`(既存 `sample_control_times` のまま)。
    **一意化で清算の件数が半分になるので、対照の点数も半分になり、引かれる時刻も変わる**(§3.2)。
17. **`is_buyer_maker == False` を「買い taker」とした(該当語なし)。**
    Binance の aggTrades の `is_buyer_maker` は「買い手が maker か」なので、False = 買い手が taker。
    ロングの積み上がりに当てるのはこちらである。**これは仮定ではなく列の定義である**(事実)が、
    **「買い taker の出来高の割合で新規建玉のロング / ショートが割れる」という当て方そのものは 仮定**
    (リードの指示にも「(仮定)」と書かれている)。
18. **建玉の重みは `sum_open_interest`(枚)をそのまま使った(該当語なし)。**
