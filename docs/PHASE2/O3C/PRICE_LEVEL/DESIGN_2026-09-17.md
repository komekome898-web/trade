# O-3c 1 件目: 価格帯ごとの約定量の積み上げと清算価格の位置関係 — 観測表の設計(2026-09-17)

原文(`docs/PHASE2/O3C/OWNER_INTENT_2026-09-12.md` §1): 「**価格毎の約定履歴の積み上げからどの価格帯で清算が起きるかの予測できるか、できるならエントリーや利確に活かせるか(これにより分析の軸や評価方法が変わる)**」。
オーナー決定 L-190「**空の行は2件ともYES**」= データは Binance COIN-M(aggTrades + liquidationSnapshot)、最初の成果物は**観測表(判定なし)**。

## 1. 単位と量

- **観測の単位**: 清算 1 件(`liquidationSnapshot` の 1 行 = 強制決済注文 1 つ)。**束ねない**(束ね方 `gap_ms` は 3 件目の一覧 §4 で「判断の置き所」として未決のまま。ここでは束ねずに 1 件ずつ置き、後で束ねられるように `time` を残す)。窓 472 日で 106,822 件(実測、`ACTION_LOG` 051)。
- **積み上げ(プロファイル)**: 清算時刻 t の直前 **W = 24 時間**の aggTrades を、価格ビン幅 **b = 0.1%**(t 時点の直近約定価格に対する相対幅。実装は `floor(log(price) / log(1 + 0.001))` で固定の対数ビン)に数量(`quantity`、COIN-M は枚数 = 100 USD 名目)を積む。W と b の根拠: W は資金調達 3 回分(8 時間 × 3)で、レバレッジ建玉の入れ替わりの目安として置いた**仮定**。b は BTC の 1 日の値幅(数 %)を数十本に分ける幅として置いた**仮定**。**W・b を変えた表も同じスクリプトで出せるようにする**(引数)。
- **清算価格 p_liq = `average_price`(約定した価格)。`price` ではない**(【訂正 2026-09-17】初稿は `price` と書いていた。標本走行で `price` は直前約定価格から ±35〜40bp の帯に固まり(中央値 −34.7bp、q5 −40.5 / q95 +39.8)、`average_price` は 0.0bp(q5 −0.3 / q95 +0.2)だった。Binance の強制決済注文は指値で、`price` はその指値、実際に約定した価格が `average_price`。設計の誤りはリードのもの。`price` 版の表も残す)。
- **ビンの統計**(各清算行について): 清算価格 p_liq のビンの数量の順位(全ビン中の百分位、100 = 最も厚い)/ p_liq から最も厚いビン(上位 10% のビン = ノード)までの距離(bp、符号付き)/ p_liq から最も薄いビン(下位 10% = 空白)までの距離(bp)/ 直前価格 p_0(t 直前の約定価格)から p_liq までの間にある数量の合計(全体に対する比)/ プロファイルの重心(数量加重平均価格)から p_liq までの距離(bp)。
- **対照**: 清算の無い時刻(各清算行に対し、同じ日の中で清算から ±5 分以上離れた時刻を一様に 1 点引く)で同じ統計を「直前価格 p_0 を p_liq の代わりに」計算した行。**清算行と対照行が同じ列を持つ**ことで、清算価格がプロファイルのどこに偏るかを比べられる。ここでは比べるだけで判定しない。

## 2. 表の列(1 行 = 清算 1 件 または 対照 1 点)

| 列 | 意味 |
|---|---|
| `kind` | `liq` / `control` |
| `time_ms` | 清算時刻(対照は引いた時刻) |
| `side` | 清算注文の向き(`SELL` = ロングの強制決済、`BUY` = ショートの強制決済。Binance の force order の定義) |
| `qty` | 清算数量(`original_quantity`) |
| `p_liq` | 清算の `price`(対照は p_0) |
| `p_avg` | 清算の `average_price`(対照は空) |
| `p0` | t 直前の約定価格 |
| `bin_pct` | p_liq のビンの数量の百分位(0〜100) |
| `dist_node_bp` | 最も近いノード(上位 10% のビン)までの距離、符号付き bp |
| `dist_gap_bp` | 最も近い空白(下位 10% のビン)までの距離、符号付き bp |
| `vol_between_ratio` | p0〜p_liq の間の数量 / W 内の全数量 |
| `dist_vwap_bp` | プロファイルの重心から p_liq までの距離、bp |
| `n_bins` / `total_qty` | プロファイルの厚み(ビン数、総数量) |

## 3. 手順

1. **標本走行(まず見せる)**: 3 件目の一覧 §4 と同じ 6 日(2023-06-25/26、2024-02-19/20、2024-10-13/14)+ 各日の前日(W = 24h のため)を読み、表を作る。行数と各列の分布(分位)を出す。**この段階で列の設計をオーナーに見せる。**
2. **全件走行**: 472 日全件(aggTrades 1.2 GB zip、1 日約 100 万行。標本走行の所要時間から見積もる)。バックグラウンドで走らせ、結果は `backtest_data/o3c_price_level_<date>/`(表 + MD5SUMS)に置く。
3. **読み**: 清算行と対照行の各列の分布を並べる(表と分位)。**判定バーは置かない**。「なぜそうなるか」を書き、次(束ね方・W・b を変える / エントリー・利確への含意)は枠組みとしてオーナーに見せる。

## 4. 測らないもの(射程)

- bitFlyer 側(約定単位は標本日 17 日だけ。L-190 で bitFlyer の清算は「集めない」)。
- 予測の当否・エントリーや利確の当否(判定しない)。
- 建玉(燃料の軸。99 日欠測、3 件目の一覧 §1)。
