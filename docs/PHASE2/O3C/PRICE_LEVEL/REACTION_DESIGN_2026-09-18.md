## 2. 引き金と起点

### 2.1 引き金

- **引き金 = 60 秒間隔で束ねた清算の終わり**(`build_cascades(gap_ms=60_000)`、一意化後)。
  **事実**(ROWS4 §2.2): 一意化後の清算 53,398 件 → 束 **22,036** 個。束あたり件数の中央値 1、
  q90 5、最大 122。束の長さは **幅 0 が 12,436(56.43%)**、10 分以上 0。向き long 12,458 /
  short 9,397 / mixed 181。
- **一意化は必須**(**事実**、ROWS4 §2.1): `liquidationSnapshot` は 1 件が全列同じ行で 2 回現れる
  (106,822 → 53,398。多重度 2 が 53,385 群 / 4 が 13 群、後者は 2023-09-21 の 1 ファイルに集中)。
- **束の向き** = 束に入った清算の side(`long` = SELL 清算、`short` = BUY 清算、混在は `mixed`)。
  **mixed 181 個は分けて出す**(**委任先の判断**。向きを決められないので主表から外し、件数だけ出す)。
- **gap は 30 / 60 / 180 秒の 3 通りで出す**(**委任先の判断**)。60 秒だけだと §10 の B(幅 0 の断片)の
  効き方が分からないため。主表は 60 秒、残り 2 本は感度として併記する。
  **本数を決めた基準(本監査 12 への対応、正直に書く)**: gap 3 通り・粒度 2 通り(60 秒バー・約定そのまま)は、
  ROWS4 §3 が測った組(60 秒バー・約定そのまま)と REPORT §0.0 の B 行(幅 0 の断片)を挟む形で置いた
  **仮定**であり、「なぜ 3 でも 5 でもなく 3 なのか」という本数そのものを決めた基準は、それ以上には無い。

### 2.2 起点

- **起点 = `after_shift`**: 起点の点 = `prices.at_or_after(end_ms)`(束の終わり以後の最初の点)、
  反応窓の終点 = `at_or_before(anchor_ts + h)`(窓の幅を h に保つ)。実装は
  `liq_response.compute_reactions(anchor="after_shift")`(**事実**、`src/bot/research/liq_response.py:472`)。

## 3. 測るもの(観測量)

**時間軸 h = 1 / 5 / 15 / 30 / 60 / 240 分**(6 本)。原文「みる時間軸 可能な限り多く」に対する
**委任先の判断**: 下限 1 分は bitFlyer 側の 1 分足と揃う最小(§6)。
**h の 6 本(とりわけ上限 240 分)は着手前に置いた仮定で、MDE や結果から逆算していない**
(**仮定**。`CLAUDE.md` §0.2 の A-12「根拠のない設定値を置く」に当たらないか本監査 11 で問われ、
根拠だった「束の長さ最大の約 24 倍・資金調達 8 時間の半分」という文を削除した。**上限 240 分は
仮定であるとだけ書く**)。
**6 本は独立でない**(同じ系列の読み替え。REPORT §0.0 の担保 1a と同じ注意)。

すべて**清算の向きに正**で揃える(SELL 清算 = ロングの強制決済 → 下向きが正、BUY 清算 → 上向きが正)。
符号の約束は OI_DIST §2.0 の `*_liqdir` と同じ(**事実**)。

- **(a) 価格変化**: 起点から h 後までの bp。**正 = 継続、負 = 反転。**
  `compute_reactions` の `bp_{h}m` に清算の向きの符号を掛けたもの。
- **(b) 到達**(2 つの到達を別々に数える。**委任先の判断**):
  - **戻り到達** = 「出てきた位置」へ h 以内に戻ったか。「出てきた位置」は 2 通り置く:
    束の直前 W の**重心**(`dist_vwap_bp` の位置)と、**一番近いノード**(`dist_node_bp` の位置)。
  - **前進到達** = 清算の向きに**進む先の次のノード**に h 以内に着いたか。
    「次のノード」= 清算価格から清算の向きに最も近い上位 10% のビン(無ければ NaN と件数)。
  - どちらも **到達までの時間**(秒)を出す。到達しなければ NaN。
  - 到達の判定は、起点から h までの**約定価格の列**を歩いて、位置をまたいだ最初の時刻を取る
    (**委任先の判断**: 終値だけで見ると窓の中で触れた到達を落とすため)。
- **(c) 最大の順行 / 逆行**: 起点から h までの間の、清算の向きの最大値と最小値(bp)。

## 11. なぜこの設計か(「なぜ」のループの回し方)

`CLAUDE.md` §5.2 / `research-protocol` §0: **判定は出口ではない。**
「案 → 検証 → なぜそうなるのかの理解 → 改良 → 再検証」。段 A はこのループの **1 周目の「検証」**である。

**候補の分け方をこう置いた理由(委任先の判断)**:
- 原文 §1.1 の末尾は「**転換が起きるか、またはそれがトレンドになるのか**」という**分岐**である。
  分岐を数にするには「どちらに行ったか」を**同じ物差しで**書ける必要がある。
  価格変化の符号だけだと、大きさの違う 2 つの結末が同じ「正」に潰れる。
  そこで **位置への到達**(戻り = 出てきた位置 / 前進 = 次のノード)を置いた。
  位置は既に全行に列がある(FULL / OI_DIST)ので、**新しい仮定を足さずに分岐を書ける**(**推定**)。

**1 周目に立てる機構仮説(3 つ。どれも未検証の候補で、判定ではない)**:

| 仮説 | 観測量でどう出るか | 反証の形 |
|---|---|---|
| **F1 燃料切れ** — 清算で建玉が消え、押す力が尽きて戻る | `doi_pre_1h` が負(または `doi_in` が大きく負)の群で、戻り到達が対照との差で大きい | その群で戻り到達の差が出ない |
| **F2 燃料補給** — 清算の裏で新しい建玉が積まれ、そのまま進む | `doi_pre_1h` が正の群で、前進到達の差が大きい | **前進到達率が ΔOI の符号で分かれない**(本監査 14 への対応。前版は「向きが F1 と同じになる(戻り到達の話に見える)」と書いていて、F2 が立てた前進到達の仮説に対する反証になっていなかった) |
| **F3 位置** — 薄い所(`bin_pct` 低・空白に近い)を抜けたときだけ次のノードまで走る | A1 の薄い群で前進到達の差が大きく、厚い群で差が小さい | `bin_pct` で分かれない |

**1 周 1 機構**(`research-protocol` §0.3)。**1 周目に検証(判定)の対象にする機構仮説は F1 だけとする**
(本監査 15 への対応: 「観測は 3 つ同時・改良は 1 つずつ当てる」という前版の書き方は、§0.3 が検証と
改良を分ける趣旨——後付けで都合の良い仮説を選ばせない——を保っていなかった。規則の対象〈検証か
改良か〉をずらして 3 仮説同時観測を通す形になっていた)。
**F2・F3 は同じ走行で観測量を出すが、1 周目では判定しない(探索の記録として残すだけである)。**
**周回数は多重性に算入する。3 周続けて新しい機構仮説が要るなら止めて、理解できていないと報告する**(§0.3)。

**「なぜ」に答えられない形で終わらせない**(§0.2): 段 A の報告には、
(1) どの群で差が出たか / 出なかったか、(2) その分解から言える機構、(3) その機構が設計のどこに触れば動くか、
の 3 つを必ず書く。**触れる場所が無いなら、無いと書く。**
