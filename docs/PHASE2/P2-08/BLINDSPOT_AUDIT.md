# P2-08 盲点監査(第 2 稿 PREREG 対象、2026-09-06)

## 1(高)USD/JPY 交絡が調達票から完全に欠落
BTCUSDT は USD 建て、bitFlyer FX_BTC_JPY は JPY 建て。m(t) の「先行性」の一部が USDJPY 自体のミニモメンタムで説明される可能性を検討していない。
リポジトリには既に `data/fx/USDJPY_1m.csv`・`backtest_data/fx_usdjpy_1m_*.csv.gz`(Dukascopy、2023-01〜、`schema/fx_usdjpy_reference.json`)がある。
チェック法: 合成 BTCJPY_synth = BTCUSDT close × USDJPY close を作り、現行信号 m(t) との相関・符号一致率を測定。USDJPY 変動でシャッフルする対照(対照5)を追加。ただし当該 USDJPY 系列は 2023-01 以降のみ→開発セット(2017〜2023-12-18)の大半はカバー外である点も明記要。

## 2(高)88-90% 一致という粗い指標で k=15..60 の頑健性が検証されていない
一致率は分単位の四本値比較であり、境界の丸め(数十秒〜1分)がある場合、短い k(=15分)ほどモメンタムの符号自体が反転しうる。現状 PREREG は「差を併記」のみで信号への影響を測っていない。
チェック法: lightchart と WS 再構成 tape(公式由来、2026-07〜09 の重複窓)の双方から m(t) を計算し、k=15/30/60 ごとに符号一致率と値の相関を出す。±1分・±2分ラグでシフトさせた頑健性テストを事前登録に追加する。

## 3(中)CFD ベーシス(現物との乖離)を測る経路が未着手
lightchart は `symbol=BTC_JPY`(現物)でも到達可能と本監査で確認した(301 リダイレクト、認証不要 — FX と同じ非公式 API)。CFD 特有のベーシス変動が m(t) の交絡因子・追加説明変数になりうるが PREREG に一切登場しない。
チェック法: 現物 BTC_JPY 分足を同期間取得し、FX-現物ベーシスの時系列を作って m(t) との関係を診断(条件分析)に加える。

## 4(中)SFD(乖離手数料)の料率・発動履歴データソースが無い
PREREG は「制度区分として分けて併記するだけで判定に使わない」とするが、SFD 発動中は taker の実質コストが跳ね上がるはずで、2017-2018 期に限らず現行制度でも発動時間帯を無視してよい根拠がない。SFD 料率・閾値の履歴データソース自体が調達票に未記載。
チェック法: bitFlyer 公式のSFD発動条件・過去発動記録(あれば)を洗い出し、発動時間帯を除外する感度分析を反復に追加するか、少なくとも「無視できる」根拠を反証可能な形で書く。

## 5(中)メンテナンス窓・ステータスカレンダーが未考慮
G2棚卸しは REST candles で 19:00 UTC 前後のフラット行(メンテ窓)を確認済みだが、PREREG の lightchart 既知欠陥 5 項目にメンテ窓由来の擬似シグナル(出来高薄・スプレッド異常)の言及がない。status.bitflyer.com は本監査で到達確認済み(HTTP 200)。
チェック法: 過去メンテ告知/実績を洗い出し、メンテ窓をまたぐ建玉・信号発火を除外する規則を既知欠陥に追加するか、影響が無視できることを実測で示す。

## 6(中)否定的事実の賞味期限切れリスク
N-002(2026-08 確認・期限90日→2026-11失効)は現時点で有効だが、本ユニットは反復8回まで走る可能性があり(停止規則)、最終評価(封印1回のみ)の直前に失効している恐れ。N-003/N-004(2026-09-06確認・期限180日)は現状問題なし。
チェック法: 最終評価直前に N-002 を再確認してから実行する運用ルールを PREREG かITERに明記する。

## 7(中)PC/環境分割リスクが未記載
`paper_logs/tape/*`(WS抽出、直近09-05まで継続)はフォワード評価の生データだが、収集プロセスがオーナーPCのみで動いているのか本環境と二重化されているのか記載が無い。G2棚卸しでは同種のREST収集が実際に13日間停止した前科がある。収集が止まればフォワード評価(封印後の生命線)が欠測する。
チェック法: `docs/OPERATIONS.md` §5 の実行主体を確認し、`paper_logs/tape` → `backtest_data` への定期凍結・監視の有無を明記する。

## 8(低)リード・ラグの向きと最適ラグが事後的
候補 k=15/30/60 は先に固定されており、Binance→bitFlyer の相互相関で最適ラグを実測した形跡がない(対照4は「先行なし」のみで「逆向き先行」は見ていない)。
チェック法: 開発セットの train 部分で cross-correlation(ラグ -60..+60分)を診断として一度だけ図示し、k候補の妥当性を確認する(選択には使わない)。

## 9(低)Binance Vision の分境界保証が一次資料未確認
「検査値全件一致」は自分のパイプライン内検算に留まり、Binance側の分バケット境界(00秒起点か)の一次文書を参照していない。lightchart側の境界ズレ(#2)と合わさると誤差が倍加しうる。
チェック法: Binance API/Vision の kline 定義ドキュメントを一次資料として引用する。
