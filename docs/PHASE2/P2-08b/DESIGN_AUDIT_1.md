## 依頼された 7 点の実測確認

### 1. 封印境界 = REST/WS の分かれ目
暦規則と一致(実測 #1)。利点: 開発セットが単一刻印(REST ms)で、封印+フォワードが単一刻印(WS μs)= 最終評価の系列がフォワードと同質。欠点: 開発 → 封印で**計測系が変わる**ため、封印での劣化が「エッジの消失」か「WS 欠け 0.6〜1.9%・μs 精度・束の順序」かを分離できない。対処: 診断 (c) の REST/WS 突合を**開発側の重なり 08-20〜08-22** で行い、同じ事象列で建玉価格の差(bps)を出しておく(封印を開けずにできる)。加えて REST ファイルの 08-23 00:00〜12:25 は封印側なので `load_unsealed` が切ることを確認する。

### 2. 探索面 9 構成の事象数と経済の桁
実測 #2・#6。**100 円/日を最初から満たせない構成**: 「CI 上限 < 100」の停止条件は、点推定 0 でも CI 上限が (10,1) 298 / (10,2) 295 / (10,5) 382 / (20,1) 128 / (20,2) 240 / (20,5) 320 / (30,1) 79 / (30,2) 192 / (30,5) 261 円/日【推定、sd と n は実測 #2・#4】なので、(30,1) 以外は**点推定が明確に負(−0.4〜−4.5 bps)にならない限り発動しない**。一方で最終バー「CI 下限 > 100 円/日」を n=100 で通すには net が (10,1) 4.8 / (10,2) 3.1 / (10,5) 2.6 / (20,1) 9.4 / (20,2) 10.4 / (20,5) 5.6 / (30,1) 10.6 / (30,2) 10.6 / (30,5) 9.1 bps 必要【推定】。往復費用 2.6〜5 bps と実測 #4 の粗応答(5 秒 +3〜+10)から、**s ≥ 20 の 6 構成は n=100 では最終バーに構造的に届かない**。修正案: 停止条件を「最良構成の日次円の**点推定** < 100 円/日 なら棄却」に強化し(CI 上限条件は残してもよいが単独では無力)、最終評価の n は構成ごとに (2.8·sd / 必要 net)² で事前に出す(問 2 の表から (20,1) ≈ 200、(30,1) ≈ 55、s=10 は費用余裕 2 bps で 300〜900【推定】)。

### 3. R(τ) = 応答(60) − 応答(τ)
正しく測らない。理由: (a) 60 秒基準は「完全に織り込まれた水準」ではなく、実測 #4 で応答は 10〜30 秒で最大・60 秒で減衰(オーバーシュートの戻り)。R(5) の符号が構成で反転するのはこれ。(b) 事象条件付き 60 秒 sd 37〜79 bps で、n=60 なら SE ≈ 5〜10 bps = 測りたい量(数 bps)より大きい。(c) 第 2 層の出口は τ=5 s なのに第 1 層は 60 s を基準にしており、τ* が取引と対応しない。代替: **R(τ) := E[応答(τ+h) − 応答(τ)]、h = 5 s(第 2 層の保有と同一)** を主量にし、τ* = R(τ) > 往復費用 となる τ の上限。併記として A(τ) 全曲線と CI、および「Binance の動き r_B のうち τ までに bitFlyer が動いた割合 A(τ)/|r_B|」(基準を 60 秒応答ではなく信号そのものに置く。ベーシスの変動は既知欠陥として印付け)。60 秒は記述統計に残す。

### 4. λ = 100 ms と「λ 後の最初の約定」
根拠は妥当(WS 受信 p50 61 ms + 判断 + REST 46 ms ≈ 110 ms、`KNOWLEDGE.md` (ah)・Tardis 東京 p50 42〜52 ms と同桁)。落とし穴: (a) **取引所間の時計差**が未測定で λ と同桁になり得る(問 8a)。(b) 1s klines なら t0 自体が 0〜1 秒遅れ、先行の大半(k=0 の 0.41〜0.58)を捨てる → aggTrades に固定(盲点 #8 未反映)。(c) 事象直後の最初の約定は **57〜78% が信号と同じ側**(無条件 50%)= 裁定者の taker 約定で、その価格は既に新しい ask/bid。同じ側なら「価格 + 片道費用」は二重計上(保守)、反対側なら bid で買ったことになり半スプレッド分楽観 → **同じ側の最初の約定を約定価格とし、反対側なら実測スプレッド分を加える**(側つきの規則)。(d) 同一刻印の束(58.8%)は束内の最悪価格(自分の側)を採る。(e) 出口 t0+5 s 後の約定は s ≥ 20 で 11〜25% が 5 秒超遅れる → 「X 秒以内に無ければ最終価格で仮決済し印付け」の規則が要る(実効保有が 5 秒でなくなる)。(f) 自分の注文: バックテストと PAPER では自分の約定はテープに無いので問題は生じない。LIVE 段階でのみ「自分の child_order_acceptance_id の約定を除外」が要る — 本単位の範囲外だが一文を残す。(g) 封印側 WS 欠け 0.6〜1.9% がバーストに集中するなら「最初の約定」を取りこぼして後の(不利な)価格を採る = 保守側だが、出口側でも同じ方向とは限らない。時間分布の報告(既に診断 (c))で足りる。

### 5. 「n ≥ 100 到達時に 1 回」
封印の意味は壊れないが手続きが無い。(a) 到達判定は **Binance 側の事象数だけ**で数えられ、bitFlyer 側の結果を見ずに済む → 「count-only スクリプトが封印+フォワードの Binance ファイルから最良構成の事象数のみを出力し、ITER に日付と n を記録。結果列は読まない」と明記(`load_sealed` の 3 重ガードとは別に、count-only は forward データにも触るので専用の読み手を一つ用意)。(b) 100 は MDE から導かれていない(§2)。(c) 最良構成の確定を反復 1 の終了時に ITER へ固定してから数える。(d) 到達日数の見込み(嵐日込みの率): s=10 で 1.5〜7 日、(20,5) 8 日、(30,5) 25 日、(20,2) 33 日、(30,2) 43 日、(20,1) 50 日、(30,1) 75 日【推定】。嵐日を除く率なら s ≥ 20 で 2〜3 倍。180 日規則に触れるのは (30,1) のみ【推定】。(e) s=10 が最良なら数日で到達するが、日ブロック・ブートストラップの日数が数日しかない → 「n ≥ X かつ暦 ≥ 14 日」の両方を到達条件にする。

### 6. Tardis・bitbank「診断専用・封印外」の宣言
宣言だけで構造が無い。(a) bitbank は 09-06 まで、Tardis は 2026-09-01(公開後)を含む = **封印期間の円市場の応答**を診断名目で読める。円市場は bitFlyer 主導(`KNOWLEDGE.md` (ac))なので封印の漏れに等しい。全診断系列に単位境界 08-23 を適用する(SEALED.json に登録して `load_unsealed` を通すか、`assert_not_sealed` を必ず呼ぶ)。(b) 主指標の計算モジュールは SEALED.json 記載ファイルしか開けない読み手(`load_unsealed(path, "P2-08b")` 以外の read_csv を禁止)にし、診断は別スクリプトで主モジュールを import しない。(c) 診断 (iii) は Tardis 購入の引き金に使うので「判定に使わない」は正確でない — 「選択と主検定に使わない、引き金判定にのみ使う」と書き分ける。

### 7. (i)(ii)(iii) の検定可能性
いずれも「出せなければ閉じる」の数値条件が無い。(i) 分内分解: 提案 = 「P2-08 の分足信号発火分について、60 秒応答のうち 0〜5 s / 5〜15 s / 15〜60 s に帰属する割合を CI つきで出す。0〜5 s の割合の CI 幅 > 50 pp なら判定不能」。(ii) 条件の向き: 雛形 §6 の書式(状態 × 指標表、状態間差と CI と MDE、同時置換の帰無 95 点)で「低ボラ三分位 − 高ボラ三分位の 5 秒応答差」を出し、差の CI が MDE 未満なら「判定不能」と書く(反復 1 の選択とは別に主検定を変えない)。(iii) 長期変化: 雛形 §5 の一式(単位 U = 年、窓 W、ブロック長、傾き bps/年と MDE、判定文)が**全く書かれていない**。Tardis 84 日(月 1 日のみ)で年別 n は 12 日分 → MDE を先に出し、「縮小していない」の定義(傾きの CI がゼロを含む、かつ直近 2 年の CI が正)を引き金条件に使う。
