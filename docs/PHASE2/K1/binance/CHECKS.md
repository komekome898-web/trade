## 1. 足の時刻・単位・時間帯

### C-01 足の時刻の意味(開始 / 終了)
- (a) Binance の kline には `open_time` と `close_time` があり、スナップショットは `open_time` だけを残している。実装者が別の列や `+59s` を足の時刻にすると、BitMEX(区間の開始秒)と 1 分ずれる
- (b) 1 分ずれると foot>1 の窓の切り方が変わる(窓の最初の 1 分が前の窓に入る)。foot=1 では影響なし。向きは決まらない
- (c) L-02: `load_bars('binance', 2017-08-17, 2017-08-17)` の先頭が `(1502942400, 4261.48, 4261.48, 4261.48, 4261.48)`(= CSV 先頭行を列名で読んだもの)。L-04: 2026-08-31 の最後が 23:59 の epoch
- (d) 一致する
- (e) 重大(壊れていれば foot>1 の全セルが別の足になる)。**結果: 合格**

### C-02 時刻の単位と時間帯
- (a) CSV は ISO 文字列 `YYYY-MM-DD HH:MM:SS+00:00`。tz を剥がして naive で `.timestamp()` すると **実行機の時間帯**で epoch になる(この箱は UTC なので通り、Windows の JST 箱で 9 時間ずれる)。2025 年以降の生 zip はマイクロ秒 epoch だが、スナップショットは ISO に直してある(README)
- (b) 9 時間ずれると日ブロック(`ts//86400`)と年の境界と foot≥15 の窓が全部ずれる。向きは決まらない
- (c) L-03: 別プロセスを `TZ=Asia/Tokyo` で走らせ、2017-08-17 と 2018-02-09 の本数・先頭・末尾が UTC と同一か。D-03a: 全行の tz 接尾辞が `+00:00`。D-06: 年別行数が index.json と一致(マイクロ秒誤読なら年が 55700 になる)
- (d) 同一 / 0 行 / 一致
- (e) 重大。**結果: 合格**(実装は aware datetime の `.timestamp()`、S-05 の 97 行目)

### C-03 秒が 0 でない `open_time`(**設計書に無い事実**)
- (a) **事実**: 21,602 行の `open_time` が分の境界に無い。2 つの連続区間: 2017-12-04 06:00:20 〜 2017-12-18 10:00:20(20,401 行、+20 秒)と 2018-02-09 09:59:14 〜 2018-02-10 05:59:14(1,201 行、+14 秒)。落とした後は 21,521 行。`fold()` は分に切り下げるので 1 分足の本数は変わらないが、区間の始まり(06:00:00 の行と 06:00:20 の行が同じ分)で衝突が 1 件ある。衝突の相手は `n_trades==0` なので落とした後は消える
- (b) 切り下げ後の足は「06:00:20〜06:01:19 の値動きを 06:00 と呼ぶ」もの。BitMEX の秒バーには無いずれ。2017-12 の 2 週間(高ボラ期)だけ、foot>1 の窓の境界が 20 秒ずれる。向きは決まらない
- (c) D-03b で区間を列挙、L-06 で loader が生 ts を返すか切り下げるかを記録、D-09 で衝突の件数
- (d) 期待は「0 行」だった → **期待と違った(事実として記録)**。loader は生 ts を返す(L-06: 1439 本すべて秒=20)、衝突 0(落とした後)
- (e) 軽微(2 区間・約 2 週間)。実装者の `last_load.open_time_off_minute` に件数が残るのは良い

## 2. 欠測の扱い

### C-04 `n_trades == 0` の行を落とす
- (a) 落とさなければ「約定の無い足は行を作らない」という BitMEX の条件と違う。落とすと h 本先・保有本数・`fixed_h3` の意味が「時計」から「約定のあった足の数」に寄る(BitMEX と同じ寄り方)
- (b) **事実**: 24,003 行(0.51%)、うち **2017 年が 23,696 行(2017 の 12.1%)**。2017 は h 本先の公称時間からのずれが他年より大きい(`gap_share` で見える)。全行 `o=h=l=c` かつ `o = 直前の終値`(事実)なので、foot=1 では同値足 = シグナル無し、無効化判定も色条件で走らない。foot>1 では窓の始値が変わりうる
- (c) L-02b/L-08: loader の本数 = 生 − 24,003。O-05: `baseline_unconditional` の n と `gap_share` が検査者の独立計算と一致。O-14: 実装者の `data_quality.json` と突合
- (d) 一致(1|1 の gap_share 期待 0.0024)
- (e) 重大(落とし忘れは全セルに効く)。**loader・出力とも合格**(§7.2 O-05 / O-14 / O-15)

### C-05 1 分を超える欠落(データの事実)
- **事実**: 落とす前の隣接間隔 > 60 秒は 35 件(README と一致)、最大 120,674 秒(2018-02-08 00:28 → 02-09 09:59:14)。上位 10 件は D-07 の出力(2018-06-26、2019-05-15、2019-08-15、2018-07-04、2017-09-06、2018-11-14、2019-03-12、2020-02-19、2021-04-25)。落とした後の 1 分バケット間隔≠60 秒は 11,483 箇所(ほぼ 2017)
- 設計書 §1 の「1 分を超える欠落」が落とす前か後かは書いていない。実装者は「落とした後」で数えている(`k1_binance_data_quality.py`)。**両方を併記すべき**(軽微)

## 3. 列・呼値・通貨

### C-06 `o/h/l/c` の取り違え
- (a) 位置 `[1..4]` で読む(実装者は列名 assert 付き)。列順が違えば h/l の入れ替えや o/c の入れ替えが起きる
- (b) o/c 入れ替え = 陽線/陰線が反転 = **強い/弱いのラベルが入れ替わり、向きも反転**。h/l 入れ替え = ヒゲが負になり `int()` が 0 に潰す
- (c) D-05: `h<l / h<max(o,c) / l>min(o,c)` が 0 行。L-02: 先頭行の o/h/l/c を列名で読んだ値と一致。O-11f/g: 実装者の出力(1 分足・年別の向きと門の数)を検査者の再実装(列名で読む)と厳密一致。O-12: 検査者の再実装と既存 `venue.binance` が厳密一致(検査者側の自己検証)
- (d) 全部一致
- (e) 重大。**O-12・O-11f/g とも合格**(検査者の再実装 = 既存の数 = 実装者の年別出力)

### C-07 呼値と `int()`
- (a) 原典は `int(top) > int(under)` で向きを決める(1 USD 単位に切り捨て)。BitMEX 0.5 刻み、Binance 0.01 刻みで同点の出方が違う。さらに **事実**: BitMEX の呼値は 2017-01 が 0.01、2017-06 が 0.1、2017-12 以降が 0.5(D-13、標本日)。設計書の「呼値 0.5」は 2017 前半には当てはまらない
- (b) 切り捨ては「1 USD 未満のヒゲ差を同点にする」。BTC 価格 4,000(2017)では 1 USD = 2.5 bp、78,000(2026)では 0.13 bp。**同じコードが年によって違う規則になる**(同点率が年で変わる)。向きは決まらない
- (c) O-11i/j: 年別の同点率を並べて表示(解釈はしない)。O-07: `--no-trunc` の n がセルごとに `≥` 原典(同点が解けて増える方向にしか動かない)。D-11: 小数桁 ≤2(**事実**: 3 桁が 2 行だけ、2018)
- (d) O-07 違反 0
- (e) 軽微〜重大(設計書が既に `--no-trunc` を並べる方針。ただし「BitMEX 2017 前半の呼値が 0.5 でない」は設計書の前提表に無い)

### C-08 USDT の意味
- (a) USDT は USD ではない(2017-2018 に数 % の乖離)。`int()` の 1 USDT と 1 USD の閾値、bp 建てのリターン、いずれも「USDT 建て」になる
- (b) 閾値のずれは最大でも数 % → 呼値差(50 倍)より 1 桁以上小さい(推定)。bp は比なので通貨に依らない
- (c) **検査で拾えない**(USDT/USD の系列を持っていない)。結果に「USDT 建て」と併記されているかを目視
- (e) 軽微(数値上)。ただし先物/現物の分離不能と同じく「言えない」に入れる

### C-09 先物(インバース)と現物
- (a) XBTUSD は XBT 建てのインバース契約。線形の `price/entry − 1` は現物の損益。BitMEX 側の測定も同じ線形式を使っているので「同方法」ではあるが、経済的な意味は違う
- (c) **検査で拾えない**。設計書 §7 に既に分離不能と書いてある
- (e) 誤検出の候補(方法は同じ。意味の違いは第 8 部の「言えない」)

## 4. 期間・年

### C-10 部分年(2017 = 8/17 から、2026 = 8/31 まで)
- (a) `per_year["2017"]` の n が BitMEX(1 月から)と母集団が違う。2026 は末尾 h 本のシグナルに先の値が無く、建玉は `ran_out`

- (c) O-04: 全ファイルの `per_year` の年集合 = 2017..2026、n の合計 = セルの n。O-05b: 1|1 の年別 n = 年別 1 分足本数(最終年 −1)。O-03: `explore == ['2017-08-17','2026-08-31']`
- (d) 一致
- (e) 軽微(隠さず n を出せばよい)。**effect.json は合格**

### C-11 年の境界
- (a) 年は入口の足の年。2019-12-31 に建てた玉が 2020 に決済されると `per_year["2019"]` に入る。BitMEX 2017-2019 では 2019 末の玉はデータ終端で強制決済(`ran_out`)、Binance では 2020 に持ち越す → **年別 2019 の母集団が BitMEX とわずかに違う**。同様に BitMEX の 2017-08-17 時点では建玉状態が引き継がれ、Binance は無から始まる
- (b) 影響はセルあたり両端で高々 1 取引(推定)。向きは決まらない
- (c) 機械検査は無し(出力に決済年が無い)。fold の窓は 86400 % (60·foot) == 0 なので年をまたぐ窓は無い(定義から)
- (e) 誤検出の候補(小さいと推定するが測っていない)

### C-12 BitMEX 2017 と Binance 2017 の切り揃え
- (a) 第 8 部の横並び(設計書 §6-1)は 2017-08-17 以降に切り揃える必要がある。BitMEX の `per_year["2017"]` はそのままでは 1 月からの数

- (e) 重大(揃えないと 2017 の横並びは別窓の比較)

## 5. `fold()` と再現ゲート

### C-13 `fold()` の窓境界
- (a) 1 分足を `fold(…, 1)` すると分に切り下げるだけ(恒等)。foot>1 は 60·foot 秒の epoch 倍数で切る。落とした行が窓の先頭だと始値は次の分の始値になる(BitMEX の「最初の約定秒の始値」と同じ意味)
- (c) D-09 / L-08: 落とした後の本数 = 1 分バケット数(衝突 0)。L-08b: foot 別本数が検査者の独立計算と一致(3 分 1,579,259 / 5 分 948,293 / 15 分 316,354 / 30 分 158,203 / 60 分 79,113)
- (d) 一致
- (e) 重大。**結果: 合格**(実装は `k1_source.load_bars` 内で assert もしている)

### C-14 再現ゲートが実際に何を比べているか
- **事実(コードから)**:
  - `body_wick.py` の組み込みゲート: 門 `s19/b24` × 強い/弱い × h∈{1,2,3,5,10} の (n, 平均±1e-3) だけ。`both`・`all` 門・区間は比べない。参照ファイルが無いと **`ref={}` で黙って空**になる(`reproduction_gate: []`)
  - `exit_ablation.py` の組み込みゲート: `full` の全セルの (n, 平均±2e-3) だけ。年別・決済理由・保有中央値・区間は比べない。参照が無いと黙って空
  - 設計書 §4.2 の BitMEX ゲート(再実行 vs コミット済み)は実装者のスクリプトで比べる、とだけ書いてある
- (a) 「ゲート 60/60 一致」が空リスト(0/0)でも同じ形で印字される
- (c) O-10: 件数が 60 で全 ok、かつ検査者が (n, 平均) を自分で突合。O-09: 件数 = `full` セル数 = effect のセル数、かつ検査者が n・平均・年別・決済理由・保有中央値まで突合。R 系: 再実行 vs HEAD を **全フィールド**で意味比較(signal_horizon / notrunc / body_wick / exit_ablation は差分 0、effect / direction_bias は ci95 以外差分 0 で、ci95 が動いたら報告)
- (d) 全部一致。effect の ci95 も **同じコード経路なら動かない**(乱数の消費順が同じ)。動いたら「経路が変わった印」
- (e) 重大。**結果: R 系 5 本とも差分 0、O-09 / O-10 合格**(§7.2)。実装者の `compare_gate.py` は再実行側だけの top-level メタを除いて全葉を厳密比較しており、検査者の再比較と結論が一致する

### C-15 BitMEX 経路の不変(差分から)
- **事実(差分)**: 5 本とも `base.load_seconds(EXPLORE_START, EXPLORE_END)` → `k1_source.load_bars(args.source, start, end)`。`bitmex` は `base.load_seconds` を呼ぶだけ(L-05 で 1 日分が同一)。`SOURCES['bitmex']` = 2017-01-01〜2019-12-31、出力 `docs/PHASE2/K1`(L-09)。`measure_katsuo_dispersion.py`(`load_seconds`/`fold`)は無変更(S-03)。年のハードコードは `sorted(set(years))` に置換(S-02)。`direction_bias` の venue 比較は `bitmex` 時だけ、Binance 側は従来の `load_binance_minutes(range(2017, 2020))`(落とさない版のまま → 既存 JSON と一致するはず)
- 差分で見つけた **軽微**: JSON の `note` が BitMEX 時代の文面のまま(「探索区間 2017-2019 のみ」)で Binance 出力にも書かれる(O-03b)。`render_k1_year_tables.py` の相場ラベルは `--dir` が K1 以外なら消す実装(S-06)
- (e) 重大(経路が変わっていれば全部が別の測定)。差分の目視は済み、機械検査は R 系待ち

## 9. 検査で拾えない(可能性のある)領域

1. **データそのものの真正性**: Binance Vision の kline が取引所の約定を正しく集計しているか(2018-02-09 09:59:14 の kline のように保守明けの足が異形)。BitMEX 1 秒バーが約定アーカイブの全約定(清算を含むか)から作られたか。どちらも一次資料が手元に無い
2. **USDT/USD**(§C-08)と **先物/現物**(§C-09)。数値では拾えない
3. **検査者の再実装が実装者と同じ誤読をしている可能性**(§0-A6)。`RESULT.md` §1.3 の擬似コードが原典と違っていれば、両者とも同じ方向に間違う
4. **ブートストラップの実装の正しさ**(日ブロック・種の固定)。方法が「同じ」であることは R 系で見るが、方法自体の妥当性は見ていない
5. **`--source bitmex` 再実行の実行環境**(メモリ 9 GB)が足りず途中で落ちた場合の部分出力。R 系は「差分あり」として拾うが、実装者が途中出力を報告に使えば拾えない
6. **描画(`TABLES.md`)の中身の正しさ**: 存在と年の列だけ見る。表の数値が JSON と一致するかは見ていない
7. **年の境界での建玉の持ち越し**(§C-11): 出力に決済年が無いので測れない
8. **設計書の外の選択**(例: `fixed_h3` の 3 本が「約定のあった足 3 本」であること)は BitMEX と同じ規則なので「同方法」ではあるが、2017 の欠落率の違いで意味が変わる。これは検査ではなく第 8 部の但し書きの問題
9. **同時に走っている実装者のプロセスが出力を書き換える途中**で検査が読むと、読めない JSON になる(O-00 で「読めない」と出るだけ)
10. **OOM で落ちた実行の出力が混ざっていないこと**は mtime・ログ・`load` メタ・セル数から推定したもので、落ちたプロセスが書きかけたファイルを後の実行が上書きした場合は区別できない(上書き後の中身は完走した実行のものなので、結果には影響しない)
11. **BitMEX 側の notrunc**(`signal_horizon_notrunc.json`)は再実行されていないので、その経路の不変は差分の目視(`--no-trunc` の扱いに変更なし)だけで、出力では確かめていない
12. **描画の中身**は「検査者が同じスクリプトを同じ JSON に対して走らせた出力が TABLES.md に含まれる」ことまで。描画スクリプト自体の誤り(表の計算)は、BitMEX 側と同じコードである以上「同方法」だが、正しさは見ていない
