読み込み順序(実際にたどった順、事前登録どおり): PROTOCOL.md → PREREG.md(最終評価節)→ ITER.md → `src/bot/research/sealed.py` → `src/bot/research/overnight.py` →(自分の数値を `FINAL_AUDIT_lower_own_numbers.json` に確定・保存)→ その後に初めて `RESULTS.md` / `RUN.json` / `exclusion_summary.csv` / `UNSEAL_LOG.jsonl` / MD5 を開封。禁止ファイル(KNOWLEDGE*, 他の AUDIT レポート, P2-01/P2-03 等)は未読。`load_sealed` は `PHASE2_FINAL_EVAL=P2-02` + `UNSEAL_TOKEN` の三重ゲート経由のみで呼び出した。

## 手法(独立実装の要点)
- 端点規則: t, t+1 とも [2021-04-13, 2026-09-03]。欠陥規則は事前登録の式入力ルール(close(t)/open(t+1) が0/空/誤プリント値なら該当ペアのみ除外)と幽霊行(出来高0・OHLC同値・close=前行close、全期間で機械除外)を実装。誤プリント判定(連続k≤3行、開始前行closeから開始c0として open/close 両方30%超乖離、直後行が±5%以内に復帰)も実装。
- 権利落ち日導出: `overnight.ex_dates_from_record_dates`(全期間の取引日暦、封印前+封印後を結合)。データ検証(中央値規則)を封印標本でも再計算。
- コスト: 保守 = 2/close(t)×10^4(往復1ティック)、楽観 = 0。CI はブロック・ブートストラップ(block=20, n_boot=2000, seed=20260906)。

## 前提の誤り(監査中に発見・自己修正)
1321 の呼値は現在の株価水準(66,000〜76,000円帯)では JPX 呼値テーブル上 5〜10円で、1343 の1円とは異なる。同一の「2/close(t)×10^4」を1321にそのまま使うと保守コスト後平均を過大評価する(監査時に自分も一度誤った: +5.55bps)。`config/constants.yaml` の `etf_tick_size_yen_by_price_band` で価格帯別に補正すると RESULTS.md の値とビット一致した。RESULTS.md 自体はこの補正を正しく適用済みで、このミスは監査側の実装バグであり報告書の誤りではない。他の figure には影響しない。

## 全体判定: 再現
CI境界の微小なブートストラップ実装順序差(いずれも10%未満、判定を左右しない)を除き、全headline figureが完全一致または10%以内で一致。結論を左右する数値はすべて一致。
