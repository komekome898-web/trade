## 2. 名指しされた再確認(3)対照 3 の整列可能性

- **夜間日次の日付慣行は manifest に書かれていない**。manifest が慣行を明示するのは `bars_1min`(取引日慣行、17:00 台は前夜)と
  `trading_day_daily`(前夜 + 日中)だけで、`night_session_daily` は「night session daily」としか書かれていない。
- 実測は**取引日慣行**で決着する: 夜間行 d の open は close_day(**前営業日**) と中央値 20 円差、同日 close とは 110 円差(§0)。
  行範囲も整合(夜間ファイルは 2007-09-19 始・2026-08-28 終、日中は 2026-08-27 終 = 夕方 1 本ぶん先行)。
- したがってペア (t, t+1) に対応する夜間行は **日付 t+1 の行**。この整列で 3 レグは一意に定まる:
  (a) close_day(t) → open_night(t+1)、(b) open_night(t+1) → close_night(t+1)、(c) close_night(t+1) → open_day(t+1)。
  実測: 被覆 3,235 / 3,240 ペア、平均 a = 0.13 / b = 1.63 / c = 1.16 bps(合計 2.92 = r_night 平均 2.91)。
- **事前登録に一文追加すること**: 「`night_session_daily` は取引日慣行(行 d = 前営業日の夕方のセッション)であり、ペア (t,t+1) には
  日付 t+1 の行を対応させる。根拠は close_day(t) と open_night(t+1) の一致(median 20 円)」。これが無いと (a)(c) の符号が入れ替わりうる。
- **整合性テストは無効(新規指摘)**: (a)(b)(c) の積は `open_day(t+1)/close_day(t)` に**恒等的に**telescoping するため、どの夜間行を
  当てても成立する。整合性テストは整列の検証にならない。整列の検証は上記の水準比較(前営業日 close との距離)で事前登録すること。
- 封印境界との整合は良好: 開発セット最終ペア 12-17→12-18 に必要な夜間行 12-18 は封印外、ペア (12-18, 12-21) の夜は夜間行 12-21 =
  封印行だが端点規則で除外済み。対照 3 にも同じ端点規則が適用される旨を明記すれば漏洩は無い。

## 3. 名指しされた再確認(4)`overnight_returns(kind="simple")`

`src/bot/research/overnight.py` に `kind: Literal["log","simple"]` が実在(simple は `open(t+1)/close(t) − 1`、既定は log)。
PREREG の依存は満たされている。**軽微**: `drop_glitches` は列 `r` に対し `|r| > threshold` を素で比較するため、simple 経路では
閾値が「単純収益 0.10」として効く(登録文は「|対数収益| > 0.10」)。開発セットでは除外は 3 件で一致するが、封印期間で
食い違いうるので「閾値は `r`(本単位では単純収益)に適用する」と一文で確定させること。

## 4. 新たに生じた問題(まとめ)

- **N1(要修正)** 夜間日次の日付慣行が未登録 — §2。対照 3 と、夜間不在 5 日の印付けの両方に効く。
- **N2(要修正)** 夜間不在 5 日の印付けが不精確。取引日慣行では「夜間が無い」のは行が欠けた日付 d の**前営業日の夕方**なので、
  該当ペアは (prev(d), d) の 5 本 — 実測で 2007-12-28→2008-01-04 / 2008-01-04→01-07 / 2008-12-30→2009-01-05 /
  2009-01-05→01-06 / 2016-07-15→07-19。「5 日を含むペア」と書くと (d, next(d)) 側(夜間は存在する)も巻き込む。ペアで指定すること。
- **N3(軽微)** 整合性テストの恒等性(§2)。**N4(軽微)** glitch 閾値の適用対象(§3)。
- MDE を独立標本 SE で計算しつつ CI はブロック・ブートストラップという前提の食い違いは、PREREG が自覚し実効 MDE を台帳に
  記す形で処理済み(可)。
