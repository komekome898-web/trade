# 執行堅牢化レイヤ(2026-08-21 第17報)

オーナー指示「ロジックでは勝てても注文で勝てない、という2019年の失敗を繰り返さないネットワーク堅牢システム」の実装記録。敵対的批評6巡+最終修正で収束。

## 実装(3層構造)

1. **失敗の分類学**(`src/bot/exchange/resilience.py`): 全transport/API失敗を SAFE_RETRY(送信前と証明可能: ConnectTimeout+新規接続マーカーのみ)/ AMBIGUOUS(注文エンドポイントの送信後失敗・**200だが本文不正も含む** → OrderStateUnknown、再送なし)/ REJECTED に分類。安全級のみ指数バックオフ+ジッタで再試行。下層(urllib3)の透過リトライも無効化を強制。**25例外型×2位相(transport/応答解析)の全てで「注文は1回しか試行されない」を機械証明**
2. **高速自動照合**(`order_management/reconciler.py`): 曖昧失敗後、照会のみ(送信メソッドが存在しない`QueryOnlyExchange`)で15秒予算・肯定的証拠のみ(自分の新しい注文IDの出現)で状態確定。**証拠の不在は絶対に自動クローズしない**(STATE_UNKNOWN維持+kill+アラート)。確定した約定は一元化された冪等記帳(`booked_size`ウォーターマーク)へ
3. **状態監視と適応**: gethealth+レイテンシEWMA+エラー率 → NORMAL/DEGRADED/CRITICAL(悪化は即時・回復はヒステリシス、90秒TTL)。劣化時はreadタイムアウト×2/×3・鮮度監視閾値も連動。**決済は全レベルで常に通す**。診断呼出(照合・ヘルス)は短い固定タイムアウト専用で取引経路を汚染しない。テレメトリ `data/api_health.csv` +ダッシュボードAPI状態タイル — **ペーパー稼働中の自宅PCから今すぐ劣化プロファイルの実測が始まる**

## LIVE起動時の取引所照合(新規)

LIVE起動はgetpositionsで建玉を取引所から採用(「LIVEの建玉は取引所が正」を実装)。照合失敗・不正応答・不明サイド・価格欠落は全て**起動拒否**(kill+アラート)。前プロセスのPENDING_SUBMIT残骸は肯定的証拠で採用または ABANDONED 終端化して通知。

## 正直な残余(全て記録・文書化済み)

- ダスト建玉(<最小0.001)はAPIでは誰にも閉じられない → 1エピソード1回の緊急通知+リスクブレーキ監視継続(kill発動はしない — 注文で減らせない露出に凍結を足しても無意味)
- Kill Switch発動中は決済も凍結(原則維持)。代わりに劣化での誤発動経路を遮断し、建玉付き発動時は手動手順をアラートに明記
- 保護損切りが完了足単位(最大60秒遅延)なのは既存挙動 — ティック毎化は挙動変更としてオーナー承認+カウント再スタート事項に**登録**(承認あれば実装)
- 劣化時エントリー抑制(`resilience.entry_gating`)は**既定OFF**(未登録の標本変更を防ぐ)。有効化は事前登録+承認経由
