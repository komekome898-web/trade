# Jev の手引き(この体制での使い方。2026-09-19、L-218「徹底的に調べてjevのスペシャリストになれ」)

一次資料の逐語集は `docs/DISCUSSIONS/2026-09-19_jev_review_inventories/D_study_notes.md`(説明書の全頁・料理本 18 本・評価集 4 件・ブログ・SDK・第三者のリポジトリ 4 件・X の投稿 19 件)。この手引きはそれをこの体制の言葉に直したもの。**規則は §4、着手前の点検表は §7。**

## 1. Jev とは何か(3 行)

文章と「状態」を渡すと、**あらかじめ決めた答えの集合の中から、確率つきで答えを返す**モデル。文章を書かない、理由を説明しない、考えを積み重ねない。ベンダーの言葉で「数秒で判断できる直感的な判定(System One)」を、コードから関数のように呼ぶための部品。確率は「0.8 と答えた集団の 8 割が当たる」ように訓練されている(校正)。**1 件の答えが正しい保証ではない。**

問いは 3 種類だけ。**はい/いいえ(noul: はいの確率)**、**選択(choice: 各選択肢の確率と確信度)**、**段階(score: 段階の確率と加重平均)**。1 要求に問いを何個でも並べられ、同時に評価され、互いの答えは見えない。

## 2. できないこと(ベンダー自身の一覧を、この体制の言葉で)

| ベンダーの記載 | この体制で意味すること |
|---|---|
| 文字どおりに読む。否定・二重否定・多段の間接は落ちる | 問いは 1 判断 1 問、肯定形、「反する」を聞かない(「守っている」を聞いて 1 − 確率 は code で) |
| 数えられない・数値の近さが分からない・段階の値を数値の補間に使うな | 件数・平均×件数・bp の差・行数は **code**。Jev には「どの文が主張か」だけ聞く |
| 日付を順序として読めない | 期限・窓・順序は code |
| 判断に関係ない内容が増えると精度が落ちる | 文書丸ごとを送らない。code が切り出した断片の対を送る(昼の失敗の主因) |
| 状態を敵対的として扱わない | **判定される側(リード)が state を書かない。**code が生の成果物・返答・記録から組む |
| はい/いいえ と 選択 の確率は互いに換算できない。否定形の問いの和は 1 にならない | しきい値は問いごとに測る。別の問いのしきい値を持ち回らない |
| 英語が主。日本語は「扱えるが同等ではない、自分の内容で試せ」 | 実測: 断片に切った状態なら日本語でも英語とほぼ同じ。文書丸ごとの日本語は未測定 |
| 文字列を生成できない | 自由な値が要る場面(検索語・要約)は別のモデル。Jev は「候補から選ぶ」まで |

## 3. 第三者が実測して書き残した落とし穴(公式に無いもの)

- **「問いが間違っていた。しきい値ではない」**(Foadsf/jev-for-engineers): 「改訂履歴から来た値か」と聞いたら、同じ値が 2 箇所にあって正解を捨てた。しきい値を動かす前に問いを疑う。
- **「判断モデルに算術をさせたら、確信度 0.04〜0.28 で『止める』と出て、成功に見えた」**(同): 無知の答えが安全側に倒れて成功に見える。数値の検査は code に移した。
- **「しきい値は勘だった。0.70 は実測した確信度の塊の真ん中にあり、明白な例を 0.01 差で落とした」**(同): しきい値は自分のデータで測ってから置く(0.60 / 0.85 に直した)。
- **はい/いいえ には確信度が無い。**確信度で門を作ると**一度も鳴らない門**になる(同)。0.5 が最大の無知、両端が確信。
- **別名 `jev-latest` は黙って中身が変わり、しきい値が全部ずれる**(bender #37)。版付き ID を固定する(この体制は `jev-1.13.0`)。
- **答えを位置で読むと、順序が変わったときに黙って食い違う**(bender #27)。答えは必ず問いの名前(鍵)で読む(この体制の `client.py` は鍵で読む)。
- **創業者の言葉**: 「コードベース丸ごと『安全か』と聞ける。だがうまくいかない。Jev は小さく分解した問いを組み合わせる方が向く」。
- **段階の使い方**(entity_alignment): 段階の 3 水準をそのまま 3 つの行動にすると「合わせるしきい値が無い」設計になる。
- **落ちた文の見つけ方**(autoformat): 「同じ段落か」と聞くと全部 yes になり、「前の行の文の途中から始まるか」と聞くと分かれた。**問いは、目に見える具体的な状況を書く。**

## 4. この体制の規則(全部、ベンダーの規定と実測から)

1. **Jev は判定しない。**印と確率を出すだけ。判断は LLM(リード・監査役)とオーナー(L-218)。「止める / 通す」の語を出力に置かない。
2. **state は code が組む。**判定される側が書かない。文書丸ごとではなく、code が切り出した **2 つの断片の対**(主張と根拠 / 定義と使用箇所 / 射程と判定バー / 意図マップの ○ と測定対象 / 原文と行動 / 使える経路と確かめた経路)。項目名を付けた object にする。
3. **問いは 1 判断 1 問、肯定形、criteria は具体例つき、英語**(断片は日本語のまま)。「存在するか」と「条件を満たすか」は別の問いに分け、同じ要求に並べる(投機的な fan-out)。code が組み合わせる。
4. **数える・比べる・日付は code。**Jev には「どれが主張か」「意味が同じか」「矛盾するか」だけ。
5. **しきい値は自分のデータで測ってから定数として 1 箇所に置き、結果を見てから動かさない。**まず「要確認 0.35」1 つ。行動の重さでしきい値を変えてよいが、それは code の分岐であって Jev の判断ではない。
6. **版は `jev-1.13.0` に固定。**応答の `model` を毎回記録し、変わったら止まって報告。SDK は使わず薄い `scripts/jev/client.py`(公式 SDK は 1 週間に破壊的変更が 2 回)。
7. **送るものは `redact` + `assert_clean` を通したものだけ。**鍵・生の会話記録・`paper_logs/`・口座と注文のログは送らない。送った本文はリポジトリに残さない、数値の結果(検出率など)もリポジトリに残さない(契約 MCA §2.3(f))。
8. **取引の経路には置かない。**LIVE・Kill Switch・リスク上限・注文状態・資本・口座・git の保護。
9. **沈黙を「異常なし」と読ませない。**届かなければ「未到達」を表示する(Stop フック `jev_notice.sh`、表示だけ、何も止めない)。

## 6. 次に足すもの(優先順)

1. 「これで全部」型の対(全て・全件・網羅 の文 と 添えた数え上げ)— KA-18 の見逃しを塞ぐ。
2. 意図マップの対を本番の事前登録(同じディレクトリに `INTENT_MAP.md`)で動かす — KA-06 型。
3. 調査班の報告に「主張 と 一次資料の引用」の対(引用検証の型、料理本 E.1 と同じ)。
4. リードの返答に「取れない・無い」の文 と リポジトリに固定した経路一覧 の対(監査に盛り込んだ後、L-217)。
5. 行動記録に、ベンダーの評価集「Agent Trace Observability」の問い(取り消せない操作の許可・最後の返答の主張に証拠があるか・どの手で最初に狂ったか)を当てる — 評価集合が 3 件しか無いので観測のみ。

## 7. 問いを 1 つ足す前の点検表

- [ ] その判断は code で完全に決まらないか(決まるなら Jev に聞かない)
- [ ] state は code が組み、判断に要る事実が全部入っているか(Jev は外を知らない)
- [ ] 問いは 1 判断か、肯定形か、criteria に具体例があるか、「存在」と「条件」を分けたか
- [ ] 答えの集合に「どれでもない」があるか
- [ ] 確率の読み方を決めたか(noul は はい の確率、0.5 は無知。choice は確信度も)
- [ ] しきい値は測ってから置いたか、定数は 1 箇所か
- [ ] 版は固定か、応答の `model` を記録するか
- [ ] 伏せ字を通すか、数値の結果をリポジトリに書かないか
- [ ] 印が付いたあと誰が判断するか書いたか(Jev ではない)
