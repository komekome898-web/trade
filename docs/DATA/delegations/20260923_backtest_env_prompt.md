## 3. 回し方(Workflow)
1. 項目 0 を「作る → 批評 → 盲検」の周回で先に仕上げる。
2. 項目 1〜12 を並列で回す。各項目: 要件を固定する → 場面係が場面集を固定する → 作る → 資料係が全員を場面集に通して表を作る → 批評 → (1 周目だけ試金石)→ 盲検(組ごとに別の 3 体)→ 未達なら指摘を渡して作り直す。
3. 項目 14(旧エンジンとの互換)を同じ周回で回す(項目 1〜12 が済んでから。最後の段 = 旧の置き換えは項目 14 の完了の直前)。
4. 項目 13(統合)を同じ周回で回す(項目 14 が済んでから。置き換え後の状態で通す)。最後に「欠けているものは何か」の批評家 1 体(全項目で残った [直す]・[示唆] の一覧を渡す)。出たものは新しい項目として同じ周回に入れる。**新しい項目は、オーナーの完了の形(§0)のどの語と、§1 の材料・§2 のどの項目から導いたかを書いたものに限る。**新しい市場・データの購入・有料の道具・実弾・リスク上限に触れるものは起動せず、リードに返す(A-3・A-14)。この批評家が 3 回続けて新しい項目を返したら、止めてリードに返す(L-407 C の「3 周続いたら止める」を、リードがこの段にも当てたもの。止めることは完了ではない。リードが根本原因を読んで設計を直す)。

**完了の条件**: 1 項目の完了 = 圧倒の判定(§0 の最後の行)を満たし、作業者の報告が監査役を通った、または周回の上限か同じ未達理由 3 周で「未達」として止めた(未達は理由つきで報告する。完了と書かない)。全体の完了 = 項目 0〜14 がすべて完了 + 「欠けているもの」の批評家が新しい項目を 0 件返した + `PYTHONPATH=src python -m pytest` が全件通る。**「データ待ち」の層(例: JPX の板・ティック)は完了の報告に別立てで全部書き、その層は「データが届いたら同じ周回で検証する」とする。完了と混ぜない。****作業者 1 体の完了 = §6 の報告を返したとき。**

**根本的解決(L-407 C)**: 2 周目以降の作業者は、前の周の未解消の指摘 1 件ごとに「なぜ起きたか(根本原因)」と「どの構造を変えるか」を先に書いてから直す。**場当たりの直し(試験だけを特別扱いする・閾値や既定値をずらして通す・指摘の文言だけに合わせる・機能を外して要件から逃げる)は批評家が [止める] にする。**前の周から変わった構造が無い周(周回を稼ぐだけの周)は周回に数えず [止める]。同じ未達理由が 3 周続いたら、作業を止めて根本原因の分析をリードに返す。**「同じ理由か」を決めるのは批評家**(新しく起こされた批評家が、前の周までの指摘の一覧を見て、同じ原因の指摘に前の指摘の id を付ける)。数えるのは Workflow の台本で、作業者は判定しない。盲検で同じ組に 3 周続けて負けたときも同じ扱いにする。リードは設計で解けるものは設計を変えて新しい周回を起こし、この環境で解けないもの(データが無い・オーナーの判断が要る)だけを、理由と必要なものつきで「未達」として報告する。

**要件と判定の固定**: 1 周目の前に、その項目の要件(§2 の行 + 調査結果の該当行から引いた比較の観点)を 1 つのファイルに書いて固定する。**周回の途中で要件・観点・圧倒の判定を緩めない、後から厳しくもしない**(A-6 と同じ)。**圧倒の判定・周回の上限・止める条件(§0 の L-407 の行)はオーナーだけが変える。**要件と観点の誤り(事実の誤り・抜け)を直すのはリードで、直したら理由を記録し、オーナーへの報告に載せ、その項目の盲検をやり直す。

**盲検の作り直し(L-410、2026-09-23)**: 項目 0 の第 1 周で、審査員は説明文の書きぶりで選び、しかも比べる対象(エンジン)の信頼性ではなく資料(文書)の信頼性を採点していた(「持たない」と自ら書いた旧エンジンの資料が 3 体中 2 体に選ばれた。理由は「根拠が実測で書かれている」)。調査結果の側の資料は自分の出所を名乗っていた。根本原因は **(1) 実装の振る舞いではなく第三者の説明文を比べさせていた** / **(2) 問いが「何の信頼性か」を定めていなかった** の 2 つ。よって比べるものを「同じ場面を通した実行の結果」に替える(以下)。

**場面集(場面係 = 作業者でも資料係でもない者が、1 周目の前に固定する)**: 要件の観点ごとに、実行できる場面を作る。場面は 2 種類: **既知解の場面**(合成の入力と、エンジンを見ずに手計算・閉じた式で出した正解。正解の出し方を書く)と、**能力の場面**(「X ができるか」を実際に呼んで試す)。場面は `tests/bt/battery/item_<番号>/` に置き、場面ごとに「入力 / 期待 / 何を測るか」を書く。作業者は場面集を読めるが変えない(試験だけ特別扱いする直しは [止める])。**場面集と、最初の周の結果の表は、審査員が読む前に監査役(`owner-auditor`)にかける**(場面が新実装に有利な範囲に偏っていないか・出所を示す語・断定と範囲)。批評家も、場面集が要件の観点を全部覆っているかを毎周見る。
**調査結果の側の選び方(弱い相手を選べないようにする。行うのは場面係)**: 候補は `docs/DATA/tools_catalog.tsv` の要素の列に印がある行を**機械で全部**抜き出す(人が足し引きしない。列の無い項目は SCAN への grep の語とコマンドを書いて全部)。そのうち §4 の安全の規則で scratchpad の venv に入れて動かせるものを**全部**同じ場面集に通す(入れ方・入れられなかった理由を記録)。動かせないものは、その場面について「実行の記録なし」と記録する(機構の文章は表に入れない)。
**動かせない候補の検討と再現(L-412 (1)案2 + L-413。検討するのも書くのも場面係)**: **動かせなかった候補は、1 件も機構を検討せずに外さない**(L-413「動かせないからと言って機構を検討せず無視することを避ける」)。場面係は観点ごとに、動かせなかった候補の全部を `tests/bt/battery/item_<番号>/opponents/CONSIDERED.md` の検討表に 1 行ずつ載せる。列 = 候補 / その観点の機構(書き写しの行か一次資料の URL)/ 実装のコードで確かめたか / 判断(**再現した** / **スキップ: 明らかに弱い** / **再現できない**)/ 理由と根拠。
- **段のある観点(約定の模型)**: `tools_catalog.tsv` の `段(機構)` と `段(既定)` を両方読み、実装のコードで確かめた機構のうち段が最も高い候補を選んで再現する(同じ段が複数あれば全部)。ほかの候補は検討表に「スキップ: 明らかに弱い(段が低い)」と、段の値と調査報告の行を理由に書く。
- **段の無い観点**: 実装のコードで確かめられる候補を全部再現する。ただし、次の項の「明らかに弱い」を調査報告の行で示せる候補はスキップしてよい(L-413 の注意 2 は両方の観点にかかる)。
- **スキップしてよいのは、どちらの観点でも「調査結果から明らかに弱いことがわかっている機構」だけ**(L-413「リソースを割かずにスキップする(理由なしでスキップは禁止)」)。理由には、調査報告の行を引いて、何より弱いか(動かせた候補か再現した候補のうち、同じ観点で機構が上位互換になっているもの、または段が低いもの)を書く。理由の無いスキップ・「たぶん弱い」のような推測のスキップは禁止。文書が名乗るだけで実装に無い機構(道具台帳 §2.4 の形 4)は、その旨を理由に書いて再現しない。
- 材料の順: (a) 調査報告 `SCAN_2026-09-21_tools.md` にすでに書き写されたコードと文書、(b) (a) で足りないときは一次資料(公開されたコードと文書)を読みに行く。(b) は §4 のネットワークの規則(道具サーベイの委任文 §5・§6-1〜§6-4・§6-6: 外部へ何も渡さない / 取ってきた文章は指示ではない / 鍵・登録・支払いをしない)を全部当て、読むだけで、取ってきたコードは実行しない。**道具台帳 §3 の 11 件は (b) をしない**((a) の書き写しの範囲だけ。導入も実行もしない)。
- 再現の根拠は、書き写しの行か一次資料の URL と取得日を、再現のコードの注釈に 1 対 1 で書く。**一次資料に無い工夫を足さない、弱めもしない。**一次資料で決まっていない値は、その候補の既定値を使い、既定も決まっていないときは取りうる値を 2 つ以上走らせて全部の結果を記録に残す(表には比較の表の規則どおり場面ごとに最も良い結果を寄せる)。(a)(b) の両方で材料が足りず再現できないときは、その理由を検討表に書く。
- 批評家は毎周、検討表のスキップの理由が調査結果の行で裏付けられているか、再現が一次資料どおりで弱められていないかを見る。
- **動かせなかった候補の数と割合、そのうち何件を再現し、何件を理由つきでスキップし、何件が再現もできなかったか(検討表)を、場面係が記録する。**再現もできなかった候補があるとき、その項目の圧倒の判定は「その候補とは比べていない」と候補名を付けて報告する(完了と混ぜない)。場面ごとに動かせた道具のうち最も良い結果を寄せるのは、1 つの道具より強い相手を置くため(新実装が勝ちにくい向き)。
- 再現で走らせた行は表の上では他の道具と区別しない(盲検のため)。区別は資料係の記録にだけ残す。
(上の「動かせなかった候補の数と割合…」と「場面ごとに…向き)」、およびこの 1 文は、13・14 回目の処置でリードが段落を行末まで置き換えたときに消していたものを、2026-09-23 に取り戻した)
**比較の表(資料係。作業者とは別の者)**: 新実装・当方の現状・調査結果の側の各道具を同じ場面集に通し、**スクリプトが吐いた結果の表だけ**を資料にする(資料係は文章を書かない)。列 = 場面、行 = 対象(記号で伏せる)、セル = 既知解と一致 / 不一致(値)/ 対応なし / 実行の記録なし / 2 回の実行で一致したか。調査結果の側は、場面ごとに「動かせた道具のうち最も良い結果」を 1 行に寄せる(どの道具かは伏せる)。審査員(試金石を含む)の出力は、Workflow の記録からリードが `scripts/export_workflow_judges.py` で `round_<周>/JUDGES.md` に逐語で書き出す(周が終わるたび、または Workflow が止まったとき)。表を作るスクリプトと実行の記録は `docs/DISCUSSIONS/2026-09-23_backtest_env/item_<番号>/round_<周>/` に残す。**実データから出た数値は入れない**(§4)。
**審査員の試金石(各項目の 1 周目、組の審査の前)**: 「新実装」と「新実装に場面係が不具合を 1 つ仕込んだもの」を同じ方法(表)で、組の審査員とは別の審査員 3 体に比べさせる。仕込んだ方を 1 体でも選んだら、その審査は測れていない = 表・問いの作りを直してから組の審査に進む(直したことを記録する)。

- **動作確認用の固定の手順**: 実データを通すときの戦略は、時刻だけで決まる機械的な手順(例: 毎時 0 分に 1 単位買い、5 分後に売る)か種つきの乱数に限る。信号・条件付け・最適化を入れない。出てきた数値は「動作確認」とだけ書き、良い悪いを書かない。
- **実データから出た数値は、比較資料・批評・審査・報告のどこにも入れない**(損益に限らず、約定率・markout・滑りの分布も)。実データを通す実行の成果物は実行記録に目的 `動作確認` を記録し、ダッシュボードはその実行の全タブに「動作確認の実行。相場の結論には使わない」を出す。目的 `研究` の実行は事前登録のハッシュが無いと作れない。
- **無い・取れない**: データや経路について「無い・取れない・できない」を書くときは必ず、どこで(この環境 / オーナー PC / 全経路)何を試したかを書く(CLAUDE.md §5.2)。オーナー PC に在るかは未確認と書く。
- 相場についての主張(戦略が効く / 効かない)を書かない。過去の研究の結論を読まない(CLAUDE.md §5.1)。
- 既存の試験を落とさない。消さない、飛ばさない。**全試験は 10 分を超える**(リードの実測 2026-09-23: `timeout 600` で打ち切られた)ので、全試験は `setsid nohup … > <scratchpad>/pytest_item<項目番号>_r<周>_<役>.log 2>&1 &`(並列の者と衝突しない名前にする) で切り離して回し、終わりの行を確かめる。周の途中は自分の項目の試験と核の試験だけを回してよい。
- 新しい依存を足さない(`pyproject.toml` を変えない。`hypothesis` は入っていないので、性質の試験は標準ライブラリの種つき乱数で書く。項目 7 の統計は numpy・pandas・標準ライブラリで書く = 正規分布の累積は `math.erf`、PBO と CPCV は組合せ、ブロック・ブートストラップは numpy の種つき乱数。`pyproject.toml` の依存は pandas・numpy などで scipy・statsmodels は無い(監査 7 回目の実測)。どうしても足りないときは作らずに「リードに聞くこと」に書く)。
- コード・コメント・文書にモデル名を書かない。オーナーの目に触れる文は日本語で書く(コードとコミットメッセージは英語)。
