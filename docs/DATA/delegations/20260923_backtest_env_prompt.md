## 3. 回し方(Workflow)
1. 項目 0 を「作る → 批評 → 盲検」の周回で先に仕上げる。
2. 項目 1〜12 を並列で回す。各項目: 資料係が要件を固定する → 場面係が場面集を作る → 監査役が場面集を検査し、[止める] があれば場面係が直して再検査する(§3「場面集」)→ 作る → 資料係が全員を場面集に通して表を作る → 批評 → (1 周目だけ試金石)→ 盲検(組ごとに別の 3 体)→ 未達なら指摘を渡して作り直す。
3. 項目 14(旧エンジンとの互換)を同じ周回で回す(項目 1〜12 が済んでから。最後の段 = 旧の置き換えは項目 14 が通過する直前)。
4. 項目 13(統合)を同じ周回で回す(項目 14 が済んでから。置き換え後の状態で通す)。最後に「欠けているものは何か」の批評家 1 体(全項目で残った [直す]・[示唆] の一覧を渡す)。出たものは新しい項目として同じ周回に入れる。**新しい項目は、オーナーの完了の形(§0)のどの語と、§1 の材料・§2 のどの項目から導いたかを書いたものに限る。**新しい市場・データの購入・有料の道具・実弾・リスク上限に触れるものは起動せず、リードに返す(A-3・A-14)。この批評家が 3 回続けて新しい項目を返したら、止めてリードに返す(L-407 C の「3 周続いたら止める」を、リードがこの段にも当てたもの。止めることは完了ではない。リードが根本原因を読んで設計を直す)。

**完了の条件**: 1 項目の終わり方は 2 つで、**通過** = 圧倒の判定(§0 の最後の行)を満たし、作業者の報告が監査役を通った / **止めた(未達)** = 周回の上限か同じ未達理由 3 周で止めた(理由つきで報告する)。止めた(未達)は通過に数えない。全体の完了 = 項目 0〜14 がすべて**通過** + 「欠けているもの」の批評家が新しい項目を 0 件返した + `PYTHONPATH=src python -m pytest` が全件通る。**「データ待ち」の層(例: JPX の板・ティック)は完了の報告に別立てで全部書き、その層は「データが届いたら同じ周回で検証する」とする。完了と混ぜない。****作業者 1 体の終わり = §6 の報告を返したとき。**

**根本的解決(L-407 C)**: 2 周目以降の作業者は、前の周の未解消の指摘 1 件ごとに「なぜ起きたか(根本原因)」と「どの構造を変えるか」を先に書いてから直す。**場当たりの直し(試験だけを特別扱いする・閾値や既定値をずらして通す・指摘の文言だけに合わせる・機能を外して要件から逃げる)は批評家が [止める] にする。**前の周から変わった構造が無い周(周回を稼ぐだけの周)は周回に数えず [止める]。同じ未達理由が 3 周続いたら、作業を止めて根本原因の分析をリードに返す。**「同じ理由か」を決めるのは批評家**(新しく起こされた批評家が、前の周までの指摘の一覧を見て、同じ原因の指摘に前の指摘の id を付ける)。数えるのは Workflow の台本で、作業者は判定しない。盲検で同じ組に 3 周続けて負けたときも同じ扱いにする。リードは設計で解けるものは設計を変えて新しい周回を起こし、この環境で解けないもの(データが無い・オーナーの判断が要る)だけを、理由と必要なものつきで「未達」として報告する。

**要件と判定の固定**: 1 周目の前に、その項目の要件(§2 の行 + 調査結果の該当行から引いた比較の観点)を 1 つのファイルに書いて固定する。**周回の途中で要件・観点・圧倒の判定を緩めない、後から厳しくもしない**(A-6 と同じ)。**圧倒の判定・周回の上限・未達で止める条件(§0 の L-407 と L-418 の行)はオーナーだけが変える。**要件と観点の誤り(事実の誤り・抜け)を直すのはリードで、直したら理由を記録し、オーナーへの報告に載せ、その項目の盲検をやり直す。

**盲検の作り直し(L-410、2026-09-23)**: 項目 0 の第 1 周で、審査員は説明文の書きぶりで選び、しかも比べる対象(エンジン)の信頼性ではなく資料(文書)の信頼性を採点していた(「持たない」と自ら書いた旧エンジンの資料が 3 体中 2 体に選ばれた。理由は「根拠が実測で書かれている」)。調査結果の側の資料は自分の出所を名乗っていた。根本原因は **(1) 実装の振る舞いではなく第三者の説明文を比べさせていた** / **(2) 問いが「何の信頼性か」を定めていなかった** の 2 つ。よって比べるものを「同じ場面を通した実行の結果」に替える(以下)。

**場面集(場面係 = 作業者でも資料係でもない者が、1 周目の前に固定する)**: 要件の観点ごとに、実行できる場面を作る。場面は 2 種類で、**どちらも呼んだ結果を正解と突き合わせる**(場面集の規則 1): **値の場面**(その値が正しいか。合成の入力と、エンジンを見ずに手計算・閉じた式で出した正解。正解の出し方を書く)と、**能力の場面**(X ができるか。X を使ったときに出るはずの観測できる結果を正解として決めておき、実際に X を使ってその結果が出るかを見る)。場面は `tests/bt/battery/item_<番号>/` に置き、場面ごとに「入力 / 期待 / 何を測るか」を書く。作業者は場面集を読めるが変えない(試験だけ特別扱いする直しは [止める])。**場面集と、最初の周の結果の表は、審査員が読む前に監査役(`owner-auditor`)にかける**(場面が新実装に有利な範囲に偏っていないか・出所を示す語・断定と範囲)。**場面集は作業者の 1 周目の前にかける。**[止める] があれば、場面係がその指摘を受けて直し(直す前に指摘ごとの根本原因を書く = §3「根本的解決」)、もう一度かける。場面集の監査と直しにも L-407 の条件をそのまま当てる(§0 の C の案 1 の文面「1 項目あたり最大 10 周。同じ未達の理由が 3 周続いたら「未達」として止め、報告する。」の「周」を場面集の監査 1 回と読む。同じ理由かは、監査役が前の回の指摘を名指しして示す)。**場面集の監査の回数は、作業者の周と同じ「1 項目あたり最大 10 周」に数える**(L-418「**案1 共有**」。例: 場面集の監査に 3 回かかれば、作業者の周は残り 7 周まで。場面集の監査で 10 回を使い切れば、作業者は 1 周も走らずに止めた(未達)になる)。共有するのは回数の上限だけで、「同じ未達の理由が 3 周続いた」の数えは、場面集の監査の指摘どうし・作業者の周の指摘どうしで別に行う(指摘の相手が場面集と実装で違い、またいで同じ理由にならない。リードの読み)。最初の周の結果の表は、その周の盲検の前にかける(3 回目の起動では、場面集の監査が作業者の 1 周目のあとにしか無く、場面集の欠陥が作業者を 1 周走らせてから見つかった)。批評家も、場面集が要件の観点を全部覆っているかを毎周見る。
**場面集の規則(2 回目の起動で、監査役が項目 0 の場面集と最初の表に [止める] を出したのを受けて足した。2026-09-23)**:
1. **能力の場面も、呼んだ結果を正解と突き合わせる。**「持っている」という申告、型や名前があることは数えない。能力があるかは、その能力を使ったときに出るはずの結果(正解)が出たかで決める(第 1 周の表では、能力の場面のセルが「2 回の一致」だけで決まり、能力を偽って申告する試金石と見分けがつかなかった)。
2. **場面は振る舞いを試し、作りの形を試さない。**例: 注文の通知は、データ源から入るか内部で作るかを問わず、戦略に届いたか・中身が正しいかで見る。
3. **表は観点ごとにまとめる。**場面の数で観点の重みが決まらないように、観点ごとの一致の数を出し、審査員には観点ごとに比べさせる。各観点に値の場面を 1 つ以上置く。
4. **動かせた道具は全部の場面に通す。**「この周では未実行」は禁止。試して動かなかった場面は、何を試したかと出たエラーを表の注記に書く。準備(カレンダー・データの束など)が §4 の「1 件の実行は数分まで」を超えるときは §4 が優先で、「動かなかった(数分の上限を超えた。試したこと: …)」と記録する(未実行とは書かない)。**時間の超過には実測を付ける**: 準備を始めた時刻と打ち切った時刻(または `time` の出力)とログの行を注記に書く。実測の無い「時間がかかる」は認めず、批評家が毎周確かめる。候補ごとの欠け(動かせない候補)と、場面ごとの欠け(動いた候補がこの場面だけ動かない)を分けて報告する。
5. **「最も良い結果」の順**(値の場面でも能力の場面でも同じ): 正解と一致 > 対応なし(明示的に拒否する・例外を出す)> 不一致(黙って違う値を返す)> 結果なし(正しさの欄の順。正しさが同じなら、再現の欄で「2 回の実行で同じ」を上に置く)。黙って誤った値を返すのが信頼性では最も悪い、とリードが決めた順(委任文の既存の規則「場面ごとに動かせた道具のうち最も良い結果を寄せる」の「良い」を定めたもの)。**オーナーへの報告に載せる。**
6. **検討表の判断は 4 つ**: 再現した / 持たないと確認した / スキップ: 明らかに弱い / 再現できない。「持たないと確認した」を「再現した」に数えない。「持たないと確認した」と書けるのは、その能力に当たる口(公開された関数・設定・文書の節)を探した方法と結果を書いたとき = 動かせた候補なら実際に呼んで失敗した(コマンドと出力)、動かせない候補ならコードの書き写しか一次資料で、その能力の口が無いことを行を引いて示したとき。`段(機構)` が空欄の候補は「段が低い」を理由にできない(実装で確かめる。第 1 周で、空欄の候補を動かすと要件を満たした例があった)。
