## 2. 設計(監査完了後に実装。実装前に本書で凍結)

1. **受領台帳(intake ledger)**: オーナーが送るログ・外部取得・スナップショットは全て `data/INTAKE.jsonl` に
   1 行(時刻、経路、ファイル、行数、期間、MD5、送付者)。`share_logs.bat` と `fetch_*` が自動追記。
2. **単一の真実**: 研究側は必ず `paper_logs/`(共有)を読む。`shared_or_local` を全読み手に強制し、
   ローカルが新しい場合のみローカル。読み手はどのコピーを読んだかを出力に明記(監査の「Files read」と同じ)。
3. **鮮度と網羅の表示**: ダッシュボードの「データ蓄積」に、各系列の**期間・行数・最終更新・ギャップ**を
   受領台帳から表示。リードの報告に出す件数は台帳の値のみ(手計算禁止)。
4. **スナップショット義務**: 判定・報告に使ったデータは `backtest_data/<name>_<date>/` に MD5 付きで
   保存してからでなければ結論を書けない(消失は「未検証」への格下げ規則を恒久化)。
5. **品質ゲート**: 取り込み時に自動チェック(重複、欠測、交差板、メンテ窓、極端リターン、列の型と意味の
   宣言ファイル `schema.json`)。`t`/`ts` のような列意味は schema に必ず書く。
6. **出所ファイル**: 定数(手数料、スプレッド、ティック、乗数)は `config/` に値と**一次資料 URL・確認日**を
   並記。値だけの定数を禁止。
7. **保持期限の先回り**: bitFlyer 31 日、OKX 30 日など期限付きソースは、期限の半分で自動スナップショット。
8. **外部ツールの再評価**: 位置分布チェッカー、Freqtrade のデータ層、暗号資産 MCP 群を「データ取得・保持」の
   観点で再評価する(以前の棄却理由が戦略性能だった項目は、データ基盤としての価値を別途判定)。
