# c3_yen_premium_revert の指値の変種(W4 カード 3)

オーナーの案(逐語):「毎分計算し直すなら、次の分にどの価格になれば持つべき大きさが変わるかわかるんじゃないの？それなら先にその予想価格に毎分指値おけば費用が掛からないんじゃないの？」
この案を、実際に取引された値段(bitFlyer FX の 1 分足の高値・安値と、置いた指値の値段)だけで確かめた記録。売り値と買い値の真ん中のような値段は作っていない。
言葉の判定(効く・効かない)は書かない。損益は持ち高 1 単位あたり、経費の前。指値の手数料は **未確認**(委任文「bitFlyer FX では 0 のはず【未確認】」)。

## 本値の読み(リードの判断 2026-10-02)

委任文の「値段が上がって e(P) < x_t になる値段には売りの指値を置く」を、**置いた時点の値段より向こう側(売りは直前の bitFlyer の終値より上、買いは下)にだけ段を置く**と読む(読み (b)、台本の `--passive`)。リードの判断の理由(要旨): オーナーの案は「値段がそこまで動いたら約定する」指値で、向こう側にだけ置くもの。字のとおりの読み (a) は、置いた時点で相手の側にある段を段の値段で約定させており、実際の取引所ならその注文は置いた瞬間に今の値段で約定して差を払う側になる。段の値段で約定させる扱いは実在しない約定(L-559)。読み (a) は結果として使わず、下の「採らなかった読み」に残す。

読み (b) の段: 読み (a) の段のうち、売りは値段 > 置いたときの値洗いの値段 C_place、買いは値段 < C_place の段だけを置く。飛ばした段の量は残った最初の段にまとめる(その段を超えたら持つべき大きさは読み (a) と同じ e になる)。C_place と e が食い違っていても、約定しない限り持ち高は動かない(その診断が表の「x_t とカードの e_t の差」)。

## 模型(リードの委任文の仕様 1〜5。台本 `scratchpad/w4/limit/limit_core.py` の冒頭に同じ説明。段の置き方の範囲だけが上の読み (b))

時計の分の終わり t ごとに、次の順で処理する(未来を読まない仕組みはこの順そのもの)。
1. **約定(分 (t−60 秒, t])**: bitFlyer FX の足が空でなければ(出来高 > 0)、分 t−60 の終わりに置いた段を、その足の高値 H・安値 Lo で約定させる。売りの段は H > 段の値段、買いの段は Lo < 段の値段 のときだけ(ちょうど届いただけでは約定にしない)。約定の値段は段の値段。持ち高は −1〜+1。足が空なら約定も値洗いもしない。
2. **カードの窓**: 足が空でなく、Binance の t で終わる分の行(行の時刻 t−60 秒)と USDJPY(as-of)があれば p_t = ln C_t − ln B_t − ln U_t を作り、カードと同じ手順でカードの持ち高を出してから窓に入れる(照合用)。
3. **段を置く(分 t の終わり)**: B_t・U_t があり窓が満ちていれば、次の分の終わり t+60 でカードが比べる窓 (t+60−W, t](p_t を含む)の上乗せの並び s、B_t·U_t、今の持ち高 x_t から段を置く。段の値段 L(v) = exp(v)·B_t·U_t。
   - 値段が窓の値 s[k] を超えると(H > L(s[k]))持つべき大きさは 1 − 2(k+1)/n、割ると(Lo < L(s[k]))1 − 2k/n(n = 窓の値の数。カードの q の同じ値を半分に数える規則の、境目の両側の値)。
   - 売りの段 = e(P) < x_t になる値段の境目 s[k](k = k_s, k_s+1, …、k_s = floor(n(1−x_t)/2))。量は最初の段が x_t − (1 − 2(k_s+1)/n)、ほかは 2/n。
   - 買いの段 = e(P) > x_t になる値段の境目 s[k](k = k_b, k_b−1, …, 0、k_b = ceil(n(1−x_t)/2) − 1)。量は最初の段が (1 − 2k_b/n) − x_t、ほかは 2/n。
   - 約定しなかった段は分の終わりで取り消し、分 t+60 の終わりに新しい B・U・窓で置き直す。1 分の中の海外の値動きには追従しない。
4. **両方の段が約定しうる分**: 「高値が先」(売りの段を低い順に、次に買いの段を高い順に)と「安値が先」の両方を、±1 の上限を 1 段ずつ当てながら計算し、損益の悪い方を本値にした。
5. **損益**: 分の損益(bp) = [x_前 × (C_t − C_前) + Σ 約定の量 × (C_t − 段の値段)(買いは +、売りは −)] ÷ C_前 × 10,000。C は空でない足の終値。日本時間の日ごとに合計(分の終わりの時刻で日を決める)。

成行の列: 成行の測定が保存した 1 分ごとの記録(`scratchpad/w4/measure/runs/c3_yen_premium_revert/<窓>.npz`)から、W1 C2 の式 P_t = e_t × (open_{t+2}/open_{t+1} − 1) × 10,000 で、指値の列と**同じ関数**で計算した。成行と指値は値段の基準が違う(成行は次の足の始値から次の次の足の始値、指値は段の値段と終値)。

表の各項目の定義(両列共通):
- 1 日あたり = 日本時間の日の合計の平均。95% 区間 = 日ごとの系列の circular block bootstrap(1 日・5 日の塊、1,000 回、種 20261002。`scratchpad/w4/measure/daily_stats.py` の関数)。
- 約定の回数: 指値 = 約定した段の数(同じ値段の段は 1 回、売りと買いは別に数える)。成行 = 持ち高が変わった決定の数。
- 取引 = 持ち高の向き(符号)が続いた区間(空でない分の並びで数える。0 は取引でない)。1 取引あたり = 損益の合計 ÷ 取引の数。保有 = 区間の始まりから向きが変わる分までの時間(分)。
  注: リードの `goal_table.py`(`W4_first3_RESULTS.md`)は空の足で向きの並びを切っているので、成行の取引の数・1 取引あたり・保有はそちらと少し違う。
- 最大の落ち込み = 日ごとの合計の累積の山から谷。最悪の日・最悪の月 = 日本時間の日・月の合計の最小。
- 両方の段が約定しうる分の割合 = 段を置いた分のうち、売りの段と買いの段の両方に約定の条件を満たす段があった分。
- 悪い方と良い方の差 = Σ(良い方 − 悪い方の分の損益)÷ 日の数。

## 最小注文の大きさ

**未確認**。1 段の量は持ち高 1 単位の 2/n(n = 窓の値の数。1h は最大 60、1d は最大 1,440、1w は最大 10,080)。BTC の枚数にすると「建玉の円 × 2/n ÷ BTC の値段」で、たとえば建玉 60 万円・BTC 300 万円なら 0.2 BTC × 2/n = 1h 0.0067・1d 0.00028・1w 0.000040 BTC【計算。建玉と値段は例として置いた仮定】。

探した範囲と見つかったもの:
- bitFlyer の公式の手数料の頁(`https://bitflyer.com/ja-jp/commission`、`/ja-jp/s/commission`): この環境から WebFetch は HTTP 403、curl は HTTP/2 の接続が切れて(curl: (92))本文を読めなかった【事実】。
- 検索(WebSearch「bitFlyer Lightning FX_BTC_JPY 最小注文数量 0.01 BTC」): 検索結果の要約に「Lightning 現物・Crypto CFD(BTC/JPY)の最小発注数量 0.001 BTC」とあったが、一次資料の本文は読めていない【未確認】。
- リポジトリの記録: `docs/OPERATIONS.md` 34 行「最小発注数量は 2024-10-21 に 0.01 → 0.001 BTC-CFD へ引き下げ済み」、`docs/DISCUSSIONS/2026-10-02_round1_premortem/READINESS.md` 165 行(同じ内容)。どちらも Crypto CFD(2024-03-28〜)の話で、測った期間(2017-08〜2022-12、Lightning FX の時代)の最小注文の大きさの一次資料ではない【事実】。その時代も 0.01 BTC だったかは **未確認**。
- 仮に 0.01 BTC が下限なら、上の例では 3 窓とも 1 段の量が下限より小さい【推定(例の仮定の上で)】。この模型は量の下限を入れていない。

## 関門 ② の監査の後の追記(2026-10-03、数値は変えていない)

監査役(owner-auditor、`docs/AUDITOR/ACTION_LOG.md` の「監査対象: W4-overnight/結果」)の直す件の記録。
- 各窓の「照合: …カードの持ち高がビット一致 True」の「カードの持ち高」は、模型の中でカードの式で計算した `e_card` のこと。成行の npz の持ち高と一致した。模型が保有する x_t ではない。x_t と e_t はほとんど一致しない(x = e の分の割合 1h 0.0636・1d 0.0133・1w 0.0083、差の平均 1h 0.5164・1d 0.2251・1w 0.1298。監査役が `minutes_*_passive.npz` から数えた値)。
- 指値の列の日の数は 1963、成行の列は 1962。期間の終わり 2022-12-31T15:00Z ちょうどの足が日本時間 2023-01-01 に入り、指値の列にだけ 1 分の日ができた(`1h/daily.csv` の最終行 `2023-01-01,0.739…,1,…`)。表の 2023 年の行は 1 分の損益。この日を除いて 1962 で割ると 1 日あたり 1h -237.14・1d -12.58・1w 28.40。
- 「所要時間」の「1h は 16:22Z ごろ開始」は誤り。(b) の 1h は `passive/1h/stats.json` の書き込みが 16:24:59Z、全体 569.8 秒なので開始は 16:15:29Z ごろ。16:22Z は (a) の 1h の終わり(16:22:53Z、613.5 秒、開始 16:12:40Z ごろ)。
- 走らせ直した回: `scratchpad/w4/limit/jobs/old_bugged/`(15:59Z まで)は、Binance の行の時刻が分の始まりからずれた行を使っていた版の出力で、捨てた。直しは `edit_align.py`(16:00:08Z、ずれた行を使わない。1w のログで使った 2,795,197 行・使わなかった 21,602 行)。`minutes_1w_partial.npz` と `smoke/` も途中の出力で、結果には使っていない。
- 「採らなかった読み」の表の `x_vs_card_e`(0.4767・1.4576 など)は `rejected_literal/*/stats.json` に入っていない((a) は `edit_dev.py` で列を足す前の台本で走った)。値は scratchpad の `minutes_{1h,1d,1w}.npz` からの再計算で、監査役の再計算と一致した。
- 「悪い方と良い方の差」が約 1e-13 になる理由: 段の量は元の x からの差で決まるので、同じ分に売りと買いの両方が約定しても持ち高は x − 売り + 買いで順番に依らない。±1 の上限に当たらないので、「悪い方を本値」の規則はこの模型では実質働いていない。「置いた時点で相手の側にあった段の約定 0」も、(b) では段の作り方でそうなる(確かめになっているのは試験の側)。
