# c6_weekend_gap_revert の測定(W4 第 2 陣、軽い測り方)

リードの決定(`docs/RESEARCH/cards/W4_batch2_LEAD_REVIEW.md`)と委任文の測り方で測った記録。言葉の判定(効く・効かない)は書かない。損益は bp・持ち高 1 単位あたり・経費前。書いてあるのは実際にしたことだけ。

## 何をどう走らせたか

- カード: `src/bot/research/cards/library/c6_weekend_gap_revert.py` の `WeekendGapRevert(gap)(gap = usdjpy / btc)`。関数は変えていない。
- 期間: 2017-08-01T15:00:00Z 〜 2022-12-31T15:00:00Z(全変種で同じ)。
- 持つ足: bitFlyer FX_BTC_JPY の 1 分足を封印の門(`bot.bt.data.loader.load`、kind bar、ts = 1 分の始まり、gap は accept、no_trade は drop)から読んだ。
- 参照: `usdjpy_close`(USDJPY の BID の close)。封印の門(`bot.bt.data.reference.load_reference`)で全期間を 1 回だけ読み、行の時刻は置き場の `timestamp` のまま(1 分の始まり。ずらしていない)、lag_ns 60 秒(CARD.md の測定の設定)。カードは `view.ref` で t までに使えるようになった行を順に読む。
- 区切り: 暦年(UTC の 1 月 1 日 0 時)ごとに、その区切りの足だけを門から読み、**同じカードの物を区切りをまたいで使い続けて** `run_card` に通し、記録をつないだ(scratchpad の `run_b2.py`。つなぎ方は前の 3 枚の `run_v2.py` の `run_carry` と同じ)。
  - カード 6 は参照の行を読んだ位置(`_seen`)を持つので、区切りの頭で `_seen` を 0 に戻し、区切りの最後の決定 t_last までに使えるようになった行をその区切りに、残りを次の区切りの頭に渡した(行を重ねて渡すことはしていない: 順に読むカードなので、重ねると同じ行を 2 回読む)。
- **慣らし(区切りの前の足を新しいカードに通して状態を作る形)は使っていない。** 委任文は「慣らしは、各カードが過去を読む最大の長さ以上にする」だが、カード 7 は当たりの連鎖(起点 = 直前の当たりの足)なので、新しいカードを 1 週慣らしても、全期間を一度に走らせたときの連鎖と同じ起点になるとは限らない【推定: 連鎖の起点が合うのは 2 つの連鎖が同じ足で当たったときだけ】。カード 5・7・8 は `view.bars(1)` と自分の属性しか読まず、カード 6 はそれに参照の行の位置が加わるだけなので、物を使い続ければ区切りの頭の状態は全期間を一度に走らせたときと同じになる。同じになることは下の照合で確かめた(範囲は照合の欄)。4 枚とも同じ形にした。
- 測定: 重い `measure_card`(1 分ごとの 1,000 回の作り直し・200 通りの対照)は打っていない(L-556)。`bot.research.cards.pnl.pnl` の P_t から、日ごとの系列の測定(`daily_stats.json`。式はファイルの `formula`。前の 3 枚の `daily_stats.py` と同じ)と、取引・落ち込み・月・買い売り(`extra.json`。式はファイルの `formula`)と、軽い診断(`diagnostics.json`)を出した。
- 区間: 日本時間の日ごとの損益 S_d を、塊 1 日・5 日の circular block bootstrap(`bot.bt.validation.block_bootstrap_ci`)、1,000 回、種 20261002、95%(百分位)。
- npz(`<変種>/run.npz`): open・high・low・close・exposure・decided・end_ns と、P_t を作り直すのに要る start_ns・volume(全足、区切りをつないだもの)。

## 照合(区切って読む = 全期間を一度に読む)

範囲: 変種 btc の 1 つだけ、2018-01-01T00:00:00Z〜2019-01-01T00:00:00Z の 1 年だけ、月の境の区切り 11 か所だけで比べた。ほかの変種・ほかの年・本番の走らせの暦年の境の区切りそのものは、この照合では確かめていない。

- 足 521,307 本・決定 520,293。足の並びの一致 True、持ち高の食い違い 0 本(完全一致 True)。 参照の記録(各足の最新の行の時刻と値)の一致 False。 所要 342.0 秒、最大 RSS 1.75GB(`runs/check_c6_btc.json`)。

- 参照の記録の食い違い(usdjpy_close): 足 2856 本(うち決定 2856)。区切って読んだ側の値がどれも「まだ行が無い」(-1)か True、どれも区切りの頭からその区切りで最初の行が届くまでの間か True。例: 2018-09-01T00:01:00.000000000, 2018-09-01T00:02:00.000000000, 2018-09-01T00:03:00.000000000, 2018-09-01T00:04:00.000000000, 2018-09-01T00:05:00.000000000。カードは参照の行を前の呼び出しの後に届いた分から順に読むだけで、各足の「最新の行」の記録(CardRun.ref_time・ref_value)は読まない。この記録は場面の変数に使うもので、この回の軽い測定と診断は使っていない(診断の USDJPY は門から読んだ全期間の行から直接作った)。

- 照合は同じ範囲で 3 回打った。1 回目(`runs/check_c6_btc.first.json`)は持ち高の一致と参照の記録の一致(False)だけを出した。2 回目(`runs/check_c6_btc.second.json`)で食い違う足を数えたが、区切りの頭の足の番号を足の終わりで探していた(境ちょうどに終わる前の区切りの足を頭と数えた)ため「区切りの頭からその区切りで最初の行が届くまでの間か」が False と出た。頭を足の始まりで探すように直した 3 回目(`runs/check_c6_btc.json`)が上の行。3 回目は順番待ち(sched.sh)を通さず、手で使用量を読んでから 1 本だけ起動した(sched.log の chk3_c6_btc の行)。持ち高の食い違い 0 本は 3 回とも同じ、食い違う参照の記録の足の数 2,856 は 2 回目と 3 回目で同じ(1 回目は数えていない)。
