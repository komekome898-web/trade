# 嵐リプレイ検証・方向性予測研究(2026-08-20 第9報)

レーダー稼働確認後の継続研究。ペーパーで数週間待つ代わりに、直近30日に実際に起きた嵐に対して現行スキャルパー規則をそのまま再生(リプレイ)し、前倒しで検証した。**結果は2件とも明確な陰性**であり、うち1件は即時のパラメータ修正につながった。

## 1. 嵐イベントライブラリ(新規データ資産)

- `scripts/build_storm_library.py`: 直近30日(bitFlyer公開約定の取得可能上限)の嵐16件について、[発生30分前, 発生90分後]の2時間窓をBinance 1秒足+bitFlyer約定(1秒集計・taker売買別出来高)で統合。計11.5万行・16ファイル(`data/storm_events/`)
- bitFlyer履歴は31日で消えるため、`backtest_data/storm_events_20260820/` に恒久スナップショット保存(gzip 796KB)

## 2. 嵐の方向性予測研究 — 不合格(明確な陰性)

210日・351嵐で、発生「前」に方向(上/下)を当てられるかを事前登録基準(精度≥58%・n≥40・p<0.05)で検証。

- 嵐の上下は49.3%/50.7%で無偏
- 事前登録スペック(発生1分前読み)ではモメンタム94%・フロー87%等が「合格」に見えたが、これは**トートロジー**と判明: 嵐の定義(30分リターン)の窓の内側を読んでいるだけで、嵐を「予測」ではなく「計測」していた
- 定義窓を完全に外した31分前読みでは、モメンタム56.0%(p=0.18)・フロー53.2%(p=0.50)と**コイントスに崩壊**
- 唯一統計的に残る「24時間レンジ位置」(70.9%)は時間分解能のないレジームラベルで、日次等加重の経済性は**マイナス6.6bps/日**。クラスタ補正後の|t|は全構成で1未満
- **結論: 嵐の方向は事前に予測できない。指値の事前ポジショニングは不採用**

含意: レーダー(いつ)は使えるが方向(どちらへ)は張れない → 「発生後に方向が確定してから追随する」現行構造の妥当性を裏付け。

## 3. スキャルパーの嵐リプレイ — +5bps基準に不合格

`scripts/replay_scalp_storm.py`: 現行規則を完全再現(RestingLimitクラスを本番スクリプトからimportし、判定ロジックの乖離を構造的に排除)。ルックアヘッド0件・クールダウン厳守・約定レイテンシ中央値2秒を確認済み。

| 指標 | 値 |
|---|---|
| シグナル/約定/取り逃し | 194 / 116 / 76(約定率59.8%) |
| グロス期待値 | **+1.83bps/取引** |
| ネット期待値(burst時コスト3.96bps) | **−2.13bps/取引**(勝率37.9%) |
| ネット(calmコスト2.93bps感度) | −1.10bps/取引 |
| イベントクラスタbootstrap 95%CI | [−5.14, +1.25]、P(真の期待値≥+5bps)≈0 |
| 16イベント中ネット負け | 11件(勝ち3件が全体を支配) |

**構造的な発見(逆選択)**: maker指値が取り逃したシグナルをtakerで入った場合は+2.11bps、実際に約定したシグナルは−7.22bps相当 — **差9.3bps**。「指値まで戻ってくるのは逆行が続くときだけ」というmakerの病理が定量化された。maker建て自体はtaker建てより約5bps有利だが、その利得は約定の質の悪化で相殺されて余りある。taker建てに切り替えても−3.53bpsで救済不能。

**保有時間・閾値の頑健性**: hold120秒(+3.23)が最良だが16イベントのin-sample選択であり不採用。どの構成も+5bpsに届かず。

## 4. 武装閾値の即時修正(本報の実務的成果)

リプレイの最も確度の高い指摘: **レーダー武装時の閾値引き下げ10→8bpsは有害**。

| | シグナル | 約定 | ネット/取引 | sd |
|---|---|---|---|---|
| 武装(閾値8) | 97 | 68 | **−4.14bps** | 9.6 |
| 平常(閾値10) | 97 | 48 | +0.72bps | 38.8 |

レーダーの2.23倍リフトは「嵐がいつ始まるか」の主張であり、「その窓の中の8〜10bpsの弱いバーストが取引に値する」という主張ではなかった。閾値低下で追加購入した限界的トレードは系統的に質が悪い(−4.1±1.2bps)。

→ `run_scalp_paper.py` の `--thr-armed-bps` 既定値を **8→10に戻した**(武装中も閾値据え置き)。レーダーの点灯・エントリー時の武装状態はJSONLに記録され続けるため、「同一閾値での武装帯 vs 平常帯」比較というより綺麗な検証がペーパーで継続する。

## 5. オーナーへの期待値設定

- リプレイはn=16(事前登録の30件未満)・1秒足近似のため**方向性の証拠**であり、判定はペーパー実績30件で行う(事前登録どおり)
- ただし現時点の証拠は「ペーパーも−2bps/取引前後に収束し、判定は不採用となる」可能性が高いことを示す。その場合は却下レポートが正式な成果物になる
- 現在の生き残り候補: スプレッドMM/板不均衡フィルタ(板データ蓄積待ち)・OI系仮説(スナップショット30日蓄積待ち)。嵐追随スキャルプは「観察続行・期待値低」に格下げ
