## 2. 当セッションの経路との差 — **地域制限は経路の産物だった**

| 取引所 | 当セッション(データセンタ) | オーナー PC |
|---|---|---|
| binance_um REST | **451**(地域制限) | **200** |
| bybit REST | **403** | **200** |
| okx WS | **接続リセット** | **接続 + 清算 8 件** |
| bitmex | 200 / 接続 | 200 / 接続 |

**含意**: `LIQUIDATION_HISTORY_SURVEY.md` の「取れない」判定のうち、
**当セッションの経路で 451 / 403 だったものは再確認の対象**である
(Binance REST `allForceOrders` など)。中身が無いことを確かめたもの
(Binance Vision の KeyCount=0、Bybit / BitMEX アーカイブに清算フラグが無い、
Deribit の約定に `liquidation` フィールドが無い)は**経路と無関係**なので変わらない。

## 3. 訂正 — BitMEX の「清算 1 件」は誤カウントだった

オーナー PC の出力は bitmex に `liquidations: 1` と出したが、その中身は

```json
{"table": "liquidation", "action": "partial", "keys": ["orderID"], ..., "data": []}
```

= 購読直後に届く**「現在オープンの清算注文」のスナップショット**で、**空**である。
確認スクリプトの判定が `action ∈ {insert, partial, update}` だけを見ていて
`data` の中身を見ていなかった。**中身がある時だけ数える**ように直した
(`scripts/check_liquidation_feeds.py`)。

- **判定そのものは変わらない**。接続は本当に成立しており、記録に使える。
- **記録データは汚れない**。記録器は生のメッセージをそのまま保存し、解釈は読み手の仕事。
  空の `partial` が 1 行入るだけで、それは既知欠陥として `schema/liquidations.json` に載っている。
- 誤っていたのは**「何件来たか」という数え方**だけ。BitMEX の実際の清算は 60 秒間 **0 件**だった。

## 4. 未確認のまま残ること

- **60 秒は短い**。「清算未発生」は静かな 1 分を見ただけで、**その取引所の清算頻度を測っていない**。
  頻度は記録が回り始めてから 1 日ぶんで測る(手順 P8 §3)。
- 銘柄カバレッジが取引所で違う(binance_um = 全銘柄 / okx = 全 SWAP / bybit = BTCUSDT / bitmex = XBTUSD)。
  **取引所間で件数を比べるときは、この差を先に均さないと比較にならない。**
- 長時間の安定性(切断頻度・再接続の成否)は未測定。記録器のログで後から分かる。
