# 清算ストリームの到達確認 — オーナー PC 実測(手順 P8 §1、2026-09-08)

**測ったこと**: 4 取引所の清算(強制決済)ストリームが**オーナー PC から届くか**。
`scripts/check_liquidation_feeds.py`(GET + WebSocket、各 60 秒待ち、読み取り専用・認証なし)。
実行 2026-09-08T15:57:20Z(日本時間 09-09 00:57)。

**これが必要だった理由**: 到達性は**経路の性質**であって取引所の性質ではない。
記録器はオーナー PC で動くので、当セッション(データセンタ経路)の結果では決められない。

## 2. 当セッションの経路との差 — **地域制限は経路の産物だった**

| 取引所 | 当セッション(データセンタ) | オーナー PC |
|---|---|---|
| binance_um REST | **451**(地域制限) | **200** |
| bybit REST | **403** | **200** |
| okx WS | **接続リセット** | **接続 + 清算 8 件** |
| bitmex | 200 / 接続 | 200 / 接続 |

**含意**: `LIQUIDATION_HISTORY_SURVEY.md` の「取れない」判定のうち、
**当セッションの経路で 451 / 403 だったものは再確認の対象**である
(Binance REST `allForceOrders` など)。中身が無いことを確かめたもの
(Binance Vision の KeyCount=0、Bybit / BitMEX アーカイブに清算フラグが無い、
Deribit の約定に `liquidation` フィールドが無い)は**経路と無関係**なので変わらない。

## 3. 訂正 — BitMEX の「清算 1 件」は誤カウントだった

オーナー PC の出力は bitmex に `liquidations: 1` と出したが、その中身は

```json
{"table": "liquidation", "action": "partial", "keys": ["orderID"], ..., "data": []}
```

= 購読直後に届く**「現在オープンの清算注文」のスナップショット**で、**空**である。
確認スクリプトの判定が `action ∈ {insert, partial, update}` だけを見ていて
`data` の中身を見ていなかった。**中身がある時だけ数える**ように直した
(`scripts/check_liquidation_feeds.py`)。

- **判定そのものは変わらない**。接続は本当に成立しており、記録に使える。
- **記録データは汚れない**。記録器は生のメッセージをそのまま保存し、解釈は読み手の仕事。
  空の `partial` が 1 行入るだけで、それは既知欠陥として `schema/liquidations.json` に載っている。
- 誤っていたのは**「何件来たか」という数え方**だけ。BitMEX の実際の清算は 60 秒間 **0 件**だった。

## 4. 追記(2026-09-09)— binance_um は「接続できる」が「データが来ない」

記録を 12 時間走らせた結果、**binance_um だけファイルが 1 つも出来ていなかった**
(bitmex / bybit / okx は出来ている)。ログには「接続」の行があり、切断も出ていない。
**接続は成立しているのに 1 件も届いていない。**

切り分けのため、開発セッションの経路から Binance の複数ストリームを実測した:

| ストリーム | 結果 |
|---|---|
| `fstream` `!forceOrder@arr`(USD-M 全銘柄の清算) | 50 秒で **0 件** |
| `fstream` 組み合わせストリーム経由の同じもの | 45 秒で **0 件** |
| `fstream` に明示 SUBSCRIBE | `{"result":null,"id":1}` は返る = **購読は受理されている**。以後 0 件 |
| `fstream` **`btcusdt@aggTrade`(対照。最も賑やかな約定)** | 15 秒で **0 件** |
| `dstream` `!forceOrder@arr`(**COIN-M**) | 40 秒で **13 件**(例: `USELESSUSDT` BUY 359 枚) |

**読み取れること【事実】**: 購読名は正しい(SUBSCRIBE が受理され、同じ購読名が
COIN-M では機能している)。**`fstream` ホストだけが、この経路にデータを流していない。**
最も賑やかな約定ストリームすら 0 件なので、「清算が起きていないだけ」ではない。

**まだ言えないこと【未確認】**: オーナー PC でも同じ理由かどうか。オーナー PC からは
fapi の REST が 200 で通っている(L-032)ので、REST と WS で扱いが違う可能性がある。
**対照ストリームをオーナー PC で 1 回測れば決まる** → 到達確認スクリプトに
`control_ws` を組み込んだ(清算 0 件のときだけ自動で対照を測り、
対照も 0 件なら判定を「使える」ではなく「接続はできるがデータが来ない」にする)。

**採った手**: **binance_cm(COIN-M)を記録対象に追加**した。USD-M の代用ではない
(証拠金が現物建ての別商品)が、**Binance で唯一実際に届いている清算**であり、
履歴を持たない系統なので、判断がつくまで記録しないと空白になる。
binance_um は外さない — 届く経路なら最大手の全銘柄が取れるので、外す方が損が大きい。

## 5. 未確認のまま残ること

- **60 秒は短い**。「清算未発生」は静かな 1 分を見ただけで、**その取引所の清算頻度を測っていない**。
  頻度は記録が回り始めてから 1 日ぶんで測る(手順 P8 §3)。
- 銘柄カバレッジが取引所で違う(binance_um = 全銘柄 / okx = 全 SWAP / bybit = BTCUSDT / bitmex = XBTUSD)。
  **取引所間で件数を比べるときは、この差を先に均さないと比較にならない。**
- 長時間の安定性(切断頻度・再接続の成否)は未測定。記録器のログで後から分かる。
- **binance_um が沈黙している理由**(経路か、venue の地域制限か)。オーナー PC で
  対照ストリームを 1 回測れば決まる。
- **2026-09-08 21:00 UTC〜09-09 の記録に、二重書き込みの痕跡があるか**。
  同時刻に記録器プロセスが 2 つ観測されており(I-003)、gzip の追記が混ざった
  可能性がある。ファイルが共有され次第、読み出して確かめる。
