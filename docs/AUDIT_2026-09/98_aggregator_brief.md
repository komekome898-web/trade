# 審査官(aggregator)への指示 — 所見だけから順位と再判定一覧を作る

あなたは独立の審査官である。リード(本プロジェクトの研究責任者)の説明文・報告書・知識台帳は読まない。
読むのは `docs/AUDIT_2026-09/` 配下のみ: `00_packets.md`(主張の逐語文と評価元)、`PROTOCOL.md`、
`01_assumption_register.md`(前提の誤り台帳)、`02_provenance_costs.md`、各パケット報告(`A_*.md` … `Z_*.md`、
`AA_*`〜`AQ_AR_*`、第2監査 `B2_*`/`E2_*`/`T2_*`、裁定 `E3_*`)。リポジトリの他の docs/ は開かない。

## 出力 `docs/AUDIT_2026-09/99_master.md`(≤ 400 行)

1. **主張別判定表**: `00_packets.md` の 165 主張それぞれに、監査パケット、判定(再現 / 数値差異(維持) /
   結論変更 / 再計算不能→未検証 / 判定不能(検出力不足))、決定的な数値、二重監査の一致/不一致。
   複数パケットが同じ主張を扱い矛盾する場合は矛盾を明記し、どちらを採るかと理由を書く。
2. **maker 経済の統合裁定**: E/E2/E3、L、M、N/O/P、Q、AB、I/J、Z の所見を「クオート位置(内側/best)× キュー
   (無/背後)× cap 長 × 決済(maker 継続/taker 強制)」の一枚の表にまとめ、bitFlyer FX_BTC_JPY の小口 maker が
   期待できるネットの範囲と、どの条件で正/負になるかを結論する。
3. **前提の誤りの統合**: 台帳の 77 件を「型」(定数、分母、対照、イベント定義、データ品質、時刻、コスト前提、
   検出力、選択汚染、記述の過大)で分類し、各型について**再判定が必要な主張の一覧**と優先順位(再判定で
   結論が変わる可能性 × その主張に依存する下流の数)を作る。
4. **生存主張の順位表**: 監査後に生き残った主張(通過側の戦略候補、法則、係属)を、次の基準だけで順位付けする:
   (a) 独立監査による再現の強さ(二重監査一致 > 単独再現 > 数値差異)、(b) 検出力(MDE ≤ 主張効果)、
   (c) コスト補正後の余裕(実測コストでの純余裕)、(d) データの新鮮性(将来データで確認済みか)。
   **期待収益の大きさや「金が乗っている」ことは基準にしない**。各行に「次に必要な検証」を一文で書く。
5. **閉鎖が確定した主張の一覧**と、**格下げ(未検証/判定不能)の一覧**。
6. **リードの異論欄**(空欄で置く。リードが後から書く)。

## 規律
- 数値は必ず出典パケットを添える。監査報告に無い数値を作らない。
- 「再現」と「棄却の妥当性」は別: 棄却が再現しても、検出力不足(MDE > 主張効果)なら「判定不能」に格下げする。
- 監査者間の矛盾は隠さず、解消できないものは「未解決」と書く。
- 本文は日本語、モデル名は書かない、コミットしない。
