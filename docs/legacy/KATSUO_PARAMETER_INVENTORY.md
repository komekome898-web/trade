### 1.1 `candlelen` は閾値ではなく、**インライン化された変数**だった

同じ作者の `matilda_for_TaroCamp37.py` に答えがある(449 行・513 行):

```python
candlelen = abs(candle)                                    # 449
...
if topbeard > underbeard and topbeard > candlelen:         # 513
elif underbeard > topbeard and underbeard > candlelen:     # 518
```

**マチルダでは `candlelen` は「実体の長さ」を入れる変数**で、ヒゲと実体を比べる判定に使われている。
カツオはこれを `abs(candle)` と**直接書いた**ため、変数だけが宣言に残った。
コメント「ローソク足判定長さ」は**調整可能な定数の意味ではなく、比較相手の長さ**を指している。
`= 0` は初期値にすぎない。**したがって `candlelen` は掃引軸ではない。** 判定は生きている
(`> abs(candle)` として)。

## 2. ヒゲの測り方(166-186 行 / 226-246 行。2 箇所に同じ内容が重複)

**足の向きで測り方が変わる。** これが要点で、単純な「上ヒゲ = High - max(O,C)」ではない。

| 足 | `topbeard` | `underbeard` |
|---|---|---|
| 陽線 (`candleSign == 1`) | `High - Close` | `Open - Low` |
| 陰線 (`candleSign == -1`) | `High - Open` | `Close - Low` |
| 同値 (`candleSign == 0`) | `High - Open` | `Close - Low` |

結果はどちらも「実体の外側の長さ」で一致する(陽線は Close が上端、陰線は Open が上端)。
**同値足だけ扱いが違い**、`signal = 0` に固定される(実体長 0 なので判定に入れない)。

## 3. シグナルの条件(同上)

```
signal = -1 (売り) ⇔ topbeard   > abs(candle)  かつ  int(topbeard)   > int(underbeard)
signal = +1 (買い) ⇔ underbeard > abs(candle)  かつ  int(underbeard) > int(topbeard)
それ以外 → signal = 0
```

条件は **2 つの積**:

1. **ヒゲが実体より長い**(`> abs(candle)`)— オーナーの記憶どおり
2. **反対側のヒゲより長い**(`int()` で**切り捨ててから**比較)

> `int()` の丸めは**ほとんど効かない**【実測・訂正】。2019 年 15 分足で、丸めの有無で判定が
> 変わるのは **119 本 = 全足の 0.34% / シグナルの 0.9%**。
> 「事実上の最小差フィルタ」と最初に書いたが、**過大評価だった**。
> **なお「頻度を絞っているのは `beardline` の方だ」と続けて書いていたが、それも誤り**(L-053)。
> 意図された規則では `beardline` が絞り `bigbeardline` が増やすので、
> **正味の頻度は年によって増えも減りもする**(§1.2 / §3.1)。

`lcprice`(**ヒゲの先端 = 無効化ライン**)も同時に決まる:
`signal = -1` なら `lcprice = High`、`signal = +1` なら `lcprice = Low`。

### 3.1 **意図された条件**(オーナー確定 2026-09-09、L-052 / L-053)

上の §3 は **v03 のコードが実際にやっていること**である。**意図はそれと違う。**

> 「ヒゲの長さは前提です。『上ヒゲ陰線・下ヒゲ陽線が最も強い』に含まれるヒゲは
> **19 以上**のものを指します。加えて**そのヒゲが実足よりも長いか**も判定に加えていた記憶があります」(L-052)
>
> 「24 については **『実足の長さに関わらずそれ単体で長いヒゲ』**と定義するものでした。
> つまり**シグナル条件の 2 段目を飛ばす**ものです」(L-053)

```
勝った側のヒゲ w = 反対側のヒゲより長い方(int() で切り捨てて比較)   ← 条件 3。常に必要
シグナルあり ⇔ ( w ≥ beardline かつ w > |実体| )      ← 通常の枝(19)
            または ( w ≥ bigbeardline )                ← 実体を飛ばす枝(24)
```

**3 つの条件の役割**:

| 条件 | 役割 | 24 の枝で |
|---|---|---|
| ヒゲ ≥ 19 | ヒゲと呼べる最小の長さ | 24 の方が厳しいので実質不要 |
| ヒゲ > 実体 | 反発の勢いが実体を上回るか | **飛ばす** |
| **ヒゲ > 反対側のヒゲ** | **買いか売りかの向きを決める** | **飛ばさない**(オーナー確認済み、L-053)。飛ばすと向きが決まらない |

**v03 との差【実測、15 分足、bp 建て】**: §1.2 の表のとおり、
**24 の枝は v03 が一度も見ていなかったシグナルを年 1,954〜4,495 本拾い直す**
(意図どおりのシグナルの 16〜32%)。**長さの門は絞る装置ではない。**

## 4. 4 分岐の行動(485-533 行、メインループ)

**強さは「反対建玉をどうするか」で表現されている。** 判定値ではなく行動の差。

| 足 | ヒゲ | 行動 | 強さ |
|---|---|---|---|
| 陽線 | 上ヒゲ | 買い建玉があれば `order_exit()`、無ければ `order_sell()` | **弱い**(順張り建玉は決済で止める) |
| 陽線 | 下ヒゲ | **無条件** `order_buy()` | **強い**(ドテン・買い増し) |
| 陰線 | 下ヒゲ | 売り建玉があれば `order_exit()`、無ければ `order_buy()` | **弱い** |
| 陰線 | 上ヒゲ | **無条件** `order_sell()` | **強い** |

**オーナーの記憶「上ヒゲ陰線と下ヒゲ陽線が最も強い反発」= コードと一致。**

**ヒゲが出なかった足(`signal == 0`)にも仕事がある**:

| 足 | 建玉 | 行動 |
|---|---|---|
| 陽線 | 売り建玉 | `Close < lcprice` なら**保持**、`Close >= lcprice` なら `order_exit()` |
| 陰線 | 買い建玉 | `Close > lcprice` なら**保持**、`Close <= lcprice` なら `order_exit()` |

= **ヒゲの先端を終値で抜かれたら降りる**。損切りはこの 1 本だけで、
価格幅でも時間でもなく**「反発の根拠が消えたか」**で切っている。

## 5. バグ 2 件(**検証の前に、どう扱うか決める必要がある**)

### A. 建玉上限の条件が逆(303 行 / 339 行)

```python
if abs(mybtc) >= sizemax:      # 建玉が上限「以上」のとき
    ... 注文を送る ...
else:
    msg = 'ポジションオーバー！注文はスルーするぜ'
```

メッセージと挙動が**逆**である。意図は明らかに `abs(mybtc) < sizemax`。
このままだと **建玉 0 のとき `0 >= 6000` が False** なので、
**新規建玉が一度も入らない**。`order_exit` と `order_out` には同じ判定が無いので、
決済系だけが動く。

**含意**: v03 は**このままでは新規建玉を建てられない**。
実際に稼働していたのが v03 なのか、修正済みの手元版なのかは、コードからは分からない。
**検証は「意図された挙動(`<`)」で行うべき**と考えるが、オーナーの判断を仰ぎたい。

### B. 買いドテンの枚数が足りない(313 行 vs 349 行)

```python
# 買いドテン: mybtc < 0
orders = orderset(size + mybtc, price1, size, prize2, buy=True)
# 売りドテン: mybtc > 0
orders = orderset(size + mybtc, price1, size, prize2, buy=False)
```

売り側は `buy=False` で内部が `size1 = -size1` になるため、
`-(3000 + 3000) = -6000` で**正しく倍**(反対建玉の解消 + 新規)。
買い側は `3000 + (-3000) = 0` で **1 本目が 0 枚**になる。
**買いドテンだけ壊れている**(符号の扱いが非対称)。正しくは `size - mybtc`。

## 6. 注文の作り方(285-297 行、370-405 行)

### 新規・増し玉(`orderset`)— **常に 2 本**

| 本 | 価格 | 執行条件 |
|---|---|---|
| 1 | **板の最良気配ちょうど**(買いは `bids[0][0]`、売りは `asks[0][0]`) | `ParticipateDoNotInitiate` = **post only**(メイカー限定、取れなければ約定しない) |
| 2 | `prize2 = price1 ∓ |price1 - lcprice| / 2` = **ヒゲの半値戻り**の位置 | 指定なし(**テイカーになりうる**) |

`price1` は**発注時点の板**であって、足の終値ではない。
2 本目は「ヒゲの半分だけ戻ったら、もう一段乗せる」= **押し目の 2 段構え**。

### 決済(`orderset_exit`)— **常に 4 本**

`price` = 板の最良気配、`sign` = 買い戻しなら +1 / 売り決済なら -1。

| 本 | 種別 | 価格 |
|---|---|---|
| 1 | 指値 (ReduceOnly, post only) | `price` |
| 2 | StopLimit (ReduceOnly, post only, LastPrice) | 発動 `price + sign*1.5` / 指値 `price + sign*1` |
| 3 | StopLimit (同上) | 発動 `price + sign*3.5` / 指値 `price + sign*3` |
| 4 | Stop(成行、ReduceOnly) | 発動 `price + sign*5` |

**1.5 / 1 / 3.5 / 3 / 5 ドルの固定階段**。**ボラティリティに一切連動しない絶対ドル建て**で、
BTC が 4,000 ドルの時代と 60,000 ドルの時代で同じ幅になる。
**検証で最も再検討の価値がある定数群。**(当時の BTC は 1 万ドル前後なので 5 ドル ≈ 5 bp)

## 9. 使われていない変数(宣言だけ)

**AST で Load 0 件を確認したもの**(§1 の枠内の方法):
`price_open` / `price_high` / `price_Low` / `price_close` / `length` / `error` /
`totallen`(= High - Low)/ `candlelen`(→ §1.1)/ `beardline`・`bigbeardline`(→ §1.2)。

**5 本のリスト** `candleList` / `candleSignList` / `signalList` / `topbeardList` /
`underbeardList` は `.append` されるので Load は立つが、**添字も集計も 0 件** =
**中身が一度も読まれない**。

**このうち意図を追う価値があるもの**:
- **`totallen`(= High − Low、足の全長)**: 代入だけされている。`beardline` / `bigbeardline` と
  並べると、**「足の全長がこれ以下なら見送る」というフィルタの片割れ**に見える【推定】。
  ヒゲ長で切るのか全長で切るのかは別の設計であり、**掃引では両方を候補に置く。**
- **5 本のリスト**: 履歴を貯める形だけがある。マチルダでは同名のリストが
  `candlelenList[-vola_count:-1]` として**ボラティリティの推定**に使われている
  (`matilda_for_TaroCamp37.py` 488 行)。カツオでも**ボラ適応を入れる手前まで作って
  止めた**可能性がある【推定】。§10 の「絶対値かボラ比か」はこの延長線上にある。
- `price_open` 等 4 本と `length` / `error`: 対応する実装がどこにも無く、
  意図を推定する材料も無い。**不明**として残す。
