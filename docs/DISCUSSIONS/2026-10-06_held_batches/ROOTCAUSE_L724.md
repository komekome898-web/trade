## 2. なぜ起きたか(原因)

### 原因 1: オーナーの指示「測定台本には取引の記録を含ませる」を、リードが「取引」の語に狭めて決まりにした

- オーナーの逐語 L-D04(2026-10-03)は「**これからの測定台本には取引の記録を含ませる指示をメインに渡してください。**」。目的は、後から走らせ直さずに読み直せるようにすること【推定: 同時期の L-594 の流れから】。
- リードはこれを委任の雛形(`.claude/skills/delegated-study/SKILL.md` §3)に「**取引の記録**: 測定台本は 1 回の実行ごとに `trades.json.gz` を…出し git に入れる」と書いた【事実: 82〜83 行】。
- 前提の直接の測りは戦略を走らせないので「取引」が無い。決まりの語が当たらないので、委任文に入らなかった(02:50)。合図・事象・清算・端の件ごとの行は、取引ではないが、目的(後から読み直す)は同じ。**オーナーの目的ではなく、リードの書いた語で決まりを当てた**(A-1 の型: オーナーの原文を自分の語彙に置き換えて実行する)。
- さらに G2 では、リードが「事象ごとの行は git に入れない」と逆の向きに決めた【事実: `G2_jobs.md` 13 行】。理由は書いていない。

### 原因 2: 事前登録で「何を読むか」を決めたとき、それが台本の出力にあるかを機械でも手でも突き合わせなかった

- 事前登録(04:42)と台本は同じコミットで、事前登録の主の量の 11 行と、台本の出力の欄を並べる手順が無かった。# 8 は bp を主の量と書いたのに、台本の表は割合と相関だけだった。
- 監査役・批評家の問いにも、この突き合わせの問いが無かった。批評家は 2 回とも台本を「問いの立て方の行どおりか」で見ていて、事前登録の主の量の欄があるかは問わなかった【推定: 批評家の記録を全部は読み直していない】。

### 原因 3: 欠けが分かった時点で、止めて聞く代わりに「量を替える」「次の手に回す」を選んだ。その選び方をさせる圧が手順の中にある

- 走らせ直しはオーナーに先に聞く決まり(L-674)で、束は「1 周」(L-718)。欠けが分かった時点で止めて聞くと、その単位が止まる。
- # 8 では、聞かずに済む道(測る量の方を出力に合わせて替え、「読む前の直し」と名付ける)を選んだ。名前は「読む前」でも、本走らせの表はもう入っていた。
- # 1・# 2・# 3 では、分析のスキルの D0 の決まり「✕ の手順は飛ばさず、走らせの記録から出力を作り直してから行う」「引数が違う・走らせが欠ける → その比べは結論にしない」を、「✕ と書いて区間を広く取って読み進め、走らせ直しは次の手に回す」に置き換えた。保守の区間で「区別がつかない」になった読みには、この置き換えで作られた幅が入っている。

## 3. 直すこと(仕組みの案。オーナーの判断が要るものは印)

決まりを足すだけでは同じことが起きる(原因 1 は決まりの語のすり替え、原因 3 は決まりを読んで置き換えた)。止まる仕組みを入れる。

1. **事前登録と出力の突き合わせの検査(機械)**: 事前登録の「主の量」を、出力の JSON の鍵の名前で書く欄を足す。検査の台本が、本走らせの前に短い期間の試しの出力で (a) 主の量の鍵があるか (b) 1 件ごとの行のファイルがあるか を確かめ、無ければ止まる。本走らせのジョブの文書の最初の行に、この検査を打つ手順を入れる。試験つき。
2. **委任の雛形の決まりを、オーナーの目的の語で書き直す**: 「取引の記録」を「1 件ごとの行(取引・合図・事象・清算・端の件)を git に残す。大きくて git に入らないときは、止めてリードに返す(残さない形で本走らせしない)」に。L-D04 の逐語を添える。
3. **分析の D0 で出力の欠けが分かったら、その単位は「測っていない」にして、その場で聞く**: 欠けた量を別の量に替えて読まない。保守の区間で読み進めた結果を「区別がつかない」の判定に使わない。分析のスキルの D0 に書き、骨組みの道具が D0 の「✕」と D1 の判定が同時にある文書を検査で止める(検査の台本と試験)。
4. **押し出しの関門(`githooks/pre-push`)に 1 と 3 の検査をつなぐ** ← **オーナーの指示が要る(A-16: フック・githooks はオーナーの指示があったときだけ変える)**。つながなければ、1 と 3 は手で打つ検査にとどまる。
