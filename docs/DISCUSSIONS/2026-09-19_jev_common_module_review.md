# Jev を「研究・調査・監査・返答」の共通モジュールとして使えるか — 体制の全面見直しに基づく判断(2026-09-19、L-215)

**出所(オーナー逐語、L-215)**: 「**このプロジェクトの全体の体制をもう一度全て見直せ。研究にも調査にも監査にもあなたの返答にも効果的に使える共通モジュールとしてjevが使えるのか判断しろ**」
**前提の資料**: オーナー提供 `2026-09-18_jev_trade_integration_decision_for_fable_v2.md`(同じディレクトリ。§1.1 の 4 層、§7〜§11 の差し込み点、§22 の共通の包み、§27「Jev採用を前提に結論しない」)。
**材料(委任で作った棚卸し、`2026-09-19_jev_review_inventories/`)**: A = 体制の判断点 42 件 / B = 失敗 44 件(事故 12・既知解 16・禁止事項 30・監査の判定 32 の集計)/ C = ベンダー一次資料の逐語(能力・不得意・契約・ベンダー自身の Claude Code 向けスキル本文)。
**合成例の試し**: 返答・調査・研究・監査で各 3 例(数値は `data/jev/eval/probes_2026-09-19.txt`、リポジトリに入れない = 契約 MCA §2.3(f))。**試しであって測定ではない。**
**これは判断であり、測定でも実装でもない。**測るには新しい事前登録(§7)が要る。

## 1. 結論

**使える。ただし「1 つの型」としてだけ。**

共通モジュールの正体は、**「code が並べた 2 つの断片(主張と根拠、定義と使用箇所、射程と判定バー、意図マップと測定対象、原文と実行内容、使える経路と確かめた経路)に対して、狭い問い(裏付けあり / 矛盾 / 何も言っていない、または yes/no)を投げる」**という 1 つの操作である。4 用途で共通なのはこの操作と問いの文(5〜6 個)だけで、用途ごとに違うのは **code が何を並べるか**である。

これが成り立つ根拠は 3 つ。
1. **失敗 44 件のうち、狭い分類で捕まる 10 件はすべてこの型**(§2)。しかも 5 組すべてが「オーナーが疑問文で介入して初めて発覚」で、自己発見 0 件。
2. **判断点 42 件のうち、今「リードの頭の中」にしか無いもの(機械が無い)が 5 件あり、その全部がこの型**(§3)。
3. **ベンダー自身がこの型を「Verify and escalate」「Universal Verification」として最上位の用途に挙げ、失敗の型(数える・日付・数値・多段の間接・敵対的な state)を明記している**(§4)。この体制で Jev に任せてはいけない場所は、その明記と一致する。

**使えない場所(Jev に置かない)**:
- 数える・日付・数値の突き合わせ(件数一致、平均×件数=総量、git diff の行数、期日)→ **code**。失敗 44 件中 16 件はこれで、Jev の採否と無関係に code で塞ぐ(§6)。
- 定義文と実装コードの突き合わせ(I-005/KA-05 型)、独立実装での再計算(旧 I-008 の 10 欠陥)、リポジトリ横断の照合、新しい問いの生成 → **LLM(監査役)**。
- 打ち切り(監査の無限ループ I-011、週間予算 I-007)、順序(I-012)→ **code の計数器と順序の強制**。分類の問題ではない。
- 取引の経路(LIVE・Kill Switch・リスク上限・注文状態・資本・口座・git の保護)→ **絶対に置かない**(資料 §20)。
- **判定される側(リード)が state を書く形** → 置かない。ベンダー「state は敵対的として扱われない」。state は必ず code が生の成果物・返答・会話記録から組む。

**Jev なしで同じ目的に届く部分(資料 §27「代替も比較対象に」)**: 監査回数の膨張(I-011)は検出の問題ではなく打ち切りの問題で、L-200 の打ち切りで既に減っている。Jev が効くのは資料の目的 4 つのうち「監査精度↑」(前段で 3 型を潰す)と「トークン↓」(監査役に渡す文脈を絞る)であり、「監査回数↓」は Jev より打ち切り規則と決定論的検査の方が大きい。**これは L-209 の検討記録 §1 の見立てと同じで、変えない。**

**監査役の「止める」32 件の理由は 3 型に収束**(棚卸し B の集計): (1) 本文と出典(生ログ・git diff・コード)の不一致、(2) 射程・前提と判定基準の矛盾、(3) 数値の出所未記載。(1)(3) は「どの文が主張・数値か」の抽出だけ Jev(ベンダー「抽出は判断、算術は code」)、突き合わせは code。(2) は 2 つの節を並べて Jev。

## 4. 根拠 3 — ベンダーの規定との対応(棚卸し C)

| ベンダーの逐語 | この体制での意味 |
|---|---|
| 「Verify and escalate. 特定の主張や項目をその証拠と突き合わせ、不確かなものや落ちたものは人か推論モデルに回す」(スキル本文) | §1 の「1 つの型」そのもの |
| 「Universal Verification … 推論の記録・道具呼び出し・引用の誤り・幻覚を、本体の LLM 呼び出しの何分の一かの費用で検出」(用途マップ) | 監査の前段・行動記録の検査 |
| 「数えられない」「日付を順序として読めない」「数値の近さを判断できない」「Score を数値の補間に使うな」 | §1 の「code に置く 16 件」 |
| 「書かれた問いに文字どおり答える。否定・二重否定・多段の間接は落ちる」 | 問いは 1 判断 1 問、肯定形、criteria は具体例で書く |
| 「state を敵対的として扱わない」 | state は code が組む。判定される側が書かない |
| 「決定に関係ない内容が増えるほど精度が落ちる」 | 文書丸ごとではなく、code が切り出した断片の対を送る(JEV-EVAL-001 の失敗の主因) |

| 64k/32k トークン、$0.042/M 入力・出力無料、1,200 要求/分 | 費用は制約にならない。上限は成果物 1 本を断片に切れば届かない |

## 5. 4 用途の設計(資料 §7〜§11 の差し込み点に対応)

共通部: `scripts/jev/`(既存)に `verify` 問い集合を足す — `relation`(choice: supports / contradicts / unrelated)+ 用途別の noul 数個。呼び出しは資料 §22 の `jev_decide("<用途>/<問い集合>", state)`。**state を組むのは code。**しきい値は 2 段(ベンダーの守衛の例: 0.35 で人が見る、0.70 で止める)を事前登録で固定し、開封後に動かさない。

| 用途 | code が並べるもの(state) | 問い | 効かないもの | 走る場所 |
|---|---|---|---|---|
| **返答**(資料 §7) | 返答の文ごとに: 「取れない・無い・できない」の文 + **リポジトリに固定した経路一覧**(この環境 / オーナー PC / 委任 / 全経路)+ 返答に書かれた確認 / 数値 + その出所の行 / §0.1 表の左右 / オーナーへの依頼文 + 経路一覧 | 全経路を確かめたか・主張は確認と矛盾しないか・自分でできることを頼んでいないか・左の行動は右の逐語の範囲か | 要約の良し悪し・言い訳(O-8)は分類できない。日本語以外は code(文字種)で | 返答を出す前。まずリードが打つスクリプト。**フック(Stop)に掛けるにはオーナーの指示が要る(A-16)** |
| **監査**(資料 §10・§11・§18) | 成果物から: 否定的主張 + 添えられた範囲・方法 / 記号の定義文 + 各使用箇所 / 射程の節 + 判定バーの節 / 意図マップの ○ の行 + 測定対象の一覧 / 「なぜ」の節 / 数値 + 出所の行 | 3 型(不一致・矛盾・出所なし)+ 「なぜ」が機構を述べているか | 定義とコードの突き合わせ、独立再計算、横断照合 → 監査役のまま | 監査役を呼ぶ前(前段)。監査役には落ちた対と不確かな対だけを渡す(トークン↓)。**監査の省略(Phase 3)は含まない** |
| **研究**(資料 §9) | 事前登録から: 射程と判定バー / MDE の有無と欲しい効果 / 意図マップの △✕ / 委任先の報告から: 事前登録の禁止事項 + 報告の記述 | 逸脱があるか・陰性を名乗れるか(項目化済みなら code) | 判定そのもの・機構の理解・帰無の設計 | 事前登録の後・走行前と、報告の受領時 |
| **調査**(資料 §8) | 調査班の報告から: 主張 + 一次資料の引用 / 経路と方法の記載 / 資料の種別 | 裏付け・矛盾・無関係 / 経路が書かれているか / 一次・二次・共同体 | 検索幅の決定(狭めない。資料 §8 の禁止どおり) | 委任先の報告の受領時(検収の前段) |

## 6. Jev の採否と無関係に code で塞ぐもの(失敗 16 件の側)

数値と出所の突き合わせ(本文の数値 ↔ table.csv / summary.json / git diff --stat)、平均 × 件数の総量、列挙の件数、共有経路の最終到達時刻、予算の閾値の停止、監査回数の上限、台帳ファイルの操作順序の強制。**これらは Jev より先に効く。**着手はオーナーの指示待ち(体制の見直しの一部)。

## 7. 測る前に決めること(オーナー)

1. **差し込み方**: (a) リードが打つスクリプトだけ(フック変更なし)/ (b) Stop フックに掛ける(A-16 = オーナーの指示が要る)。推し: まず (a)、効くと測れたら (b)。
2. **新しい単位 JEV-EVAL-002**: §5 の「監査」の設計を、同じ 22 組で測る。**同じ集合に対する 2 つ目の設計なので多重性に算入し、判定の後に新しい成果物での追試を要る**(研究の規律のフレッシュデータ追試)。しきい値 2 段を事前登録で固定。
3. **返答の単位**: 過去の「取れない・無い」発言(記録に残る分)+ 経路一覧で測る。経路一覧の置き場所は `config/`。
4. **監査役を通すか**: この文書は監査役を通していない(L-204「監査をとめろ」、I-011)。通すなら 1 回だけ。
5. ベンダーの Claude Code 用プラグイン(`typesafe@typesafe-ai`)の導入(設定の変更。指示があるまで入れない)。

## 8. 射程(何を測っていないか)

合成例は各 3 件で測定ではない。JEV-EVAL-001 の 22 組の結果は「文書丸ごと + 広い問い」という設計の結果で、§5 の設計の性能は未測定。行動記録の検査(資料 §9・§14)は評価集合が 3 件しか無く、結論を出せない。日本語の文書丸ごとの精度は未測定(断片に切るので使わない)。「監査回数が減るか」は Phase 2 を回さないと測れない(資料 §15)。
