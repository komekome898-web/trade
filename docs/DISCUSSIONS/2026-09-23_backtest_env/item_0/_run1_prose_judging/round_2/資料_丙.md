# 項目 0(核)比較資料 丙

観点は固定した要件(REQUIREMENTS.md)の V1〜V6。各節 3 行以内(何ができるか / 既定で何が起きるか / 根拠)。

## V1(時刻表現の一貫性)

- 何ができるか: 全事象の受信時刻を単一の整数型(64bit・ナノ秒・UTC)で表現し、専用の検査関数を通さない限り事象を作れない。単位変換(秒・ミリ秒・マイクロ秒・ISO文字列)も同じ経路を通る。
- 既定で何が起きるか: 整数以外の値・範囲外の値・桁違いの単位取り違え(変換後の値が妥当な年代の範囲から外れる場合)は例外で弾かれ、事象は作られない。
- 根拠: 検査関数の実装と、それを呼び出す事象の基底クラスの初期化処理をコードで確認。

## V2(事象型の網羅性)

- 何ができるか: 約定・板の写真・板の差分・足・資金調達・清算・時計・注文の受付/拒否/約定通知の10種類を、共通の列挙型と1対1で対応する専用の型として持つ。
- 既定で何が起きるか: 列挙型に無い種類の事象は作れない。列挙型と型定義の対応が崩れていないかを確かめる専用の試験がある。
- 根拠: 列挙型の定義と10種類それぞれに対応する型定義をコードで確認。

## V3(ルックアヘッド不能性)

- 何ができるか: 戦略に渡す「見える範囲」は、戦略を呼び出す前に境界(現在の事象までの位置)を確定させたうえで構築され、その境界の外の事象を返す経路を持たない。
- 既定で何が起きるか: 戦略は現在の事象より後の事象を参照できない。呼び出しのたびに新しく作られた窓口しか渡されないため、以前受け取った窓口を保持して後から使っても時刻は進まない。
- 根拠: 境界の確定 → 窓口の構築 → 戦略呼び出し、という順序をコードと付随する説明で確認。

## V4(決定的な事象順序)

- 何ができるか: 同時刻の複数事象を、時刻 → 事象種別ごとの優先順位(決済系 → 市場状態系 → 自注文の通知系 → 心拍)→ 一意な到着順番号、の3段階の規則で並べる。
- 既定で何が起きるか: 一意な番号まで含めるため同順位の事象は存在せず、同じ入力を再実行すれば常に同じ並びになる。
- 根拠: 並び替えの規則の実装と、全事象種別が優先順位表に含まれることを検査する内蔵の表明をコードで確認。

## V5(戦略APIの疎結合性)

- 何ができるか: 戦略が受け取るのは、現在時刻・現在の事象・見える範囲の取得・発注・取消の5つのメソッドだけを持つ専用の窓口オブジェクトで、実行主体そのものは渡されない。
- 既定で何が起きるか: 戦略のコードから口座残高・建玉・発注簿といった内部状態へ到達する経路が無い。窓口の公開面がちょうど5つであることを確かめる専用の試験がある。
- 根拠: 窓口オブジェクトの実装と、公開面を数え上げる試験をコードで確認。

## V6(拡張点の分離)

- 何ができるか: 約定・遅延・費用・口座の4つを、それぞれ独立した型の約束事として外へ出し、核の内部にはその4つのどの具体的な処理も実装していない。
- 既定で何が起きるか: 4つの部品を何も渡さなければ、何もしない既定の部品が使われて動く。部品を差し替えても実行主体のコード自体は変更不要であることを、外部の試験が示している。
- 根拠: 4つの型の約束事の定義と、外部で作った試験用の部品で動かす専用の試験をコードで確認。
