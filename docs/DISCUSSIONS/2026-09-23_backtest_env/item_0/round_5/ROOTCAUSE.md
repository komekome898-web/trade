## B. i0-r4-02 送った注文を、戦略があとの呼び出しから書き換えられる

**なぜ起きたか**: 核の路(戦略 → 取引所の要求、取引所 → 戦略の通知)は、送った**物そのもの(参照)**を運んでいた。`OrderRequest` は凍結したデータクラスだが、凍結は 1 段目の欄だけで、`extra` の中身(`api.py:89`、「タプルであること」だけを検める `api.py:103-104`)に入れたリストや辞書は、戦略・戦略の見る注文(`OrderView.request`)・送りの路・取引所の側(`account.check_order`・`fill_model.on_order`、`engine.py:782-800`)・結果の記録(`EngineResult.order_requests`)の全員が同じ物を指していた。核には「路を渡る物は値である(送った時点の中身で決まり、あとから誰も変えられない)」という規則が無く、それを守らせる所(作る時の検査か、渡す時の写し)も無かった。凍結したデータクラスであることを、中身まで値であることと取り違えていた。

**同じ根の別の穴(この周に見つけた。指摘ではない)**: 逆向きの路にも同じ形がある。約定の模型が返す報告の文の欄(`Reject.reason`・`StateUnknown.detail`・`Ack.venue_order_id`)は型を検めておらず、そのまま通知の事象(`OrderRejectEvent.reason` など、`events.py:316-385`)に入って戦略に届く。約定の模型が拒否の理由に変えられるリストを入れ、あとで中身を足すと、戦略の見る注文の `reason` が、通知を 1 つも通らずに取引所の時刻に合わせて変わる。確かめた出力(`scratchpad/bt/item0_r5_worker_probe_reason2.py`、T0+5 秒の市場の事象で模型がリストに足す): `(4000000000, 'TradeEvent', ['venue says: rejected'])` → `(5000000000, 'TradeEvent', ['venue says: rejected', 'venue secret at T0+5s'])`。通知の遅れを置けば、取引所の側の状態が遅れを飛び越えて戦略に届く(ルックアヘッドの路)。

**どの構造を変えるか**: 「**路を渡る物は、作った時点で中身まで値である**」を型の構造にする。渡す時に写すのではなく、作る時に値にする(写しは、写し忘れた所から漏れる。値なら誰と共有しても安全)。
1. `OrderRequest` を作る時(`__post_init__`)に `extra` を検め、中身まで変えられない形に作り直す(新しい部品 `src/bot/bt/core/values.py`)。受けるのは「値のデータ」だけ: `None`・`bool`・`int`・`float`・`complex`・`str`・`bytes`・`Decimal`・`Fraction`・列挙の値と、それらを入れたタプル・リスト・辞書・集合。リストは変えられないリスト、辞書は変えられない辞書、集合は `frozenset` に作り直す(元の型は覚えておく)。それ以外(関数・任意のオブジェクト・生成器・循環する入れ物)は `OrderApiError` で断る。関数や任意のオブジェクトは、写しても中で戦略の今の状態を読める(送ったあとに中身が変わる)ので、値として受けない。
2. `extra_dict()` は、毎回新しい、元の型(リスト・辞書・集合)のままの写しを返す。取引所の側が読んだ物を変えても、何も変わらない。これで `OrderRequest` は中身まで値になり、ハッシュも取れる。
3. `extra` の形(2 つ組・鍵は空でない文字列・鍵の重複なし)も作る時に検める(i0-r4-07: 形の誤りが、注文の届いた時刻に取引所の側で初めて出ていた)。
4. 通知の事象の文の欄(`OrderAckEvent.venue_order_id`・`OrderRejectEvent.reason`・`OrderCanceledEvent.reason`・`OrderStateUnknownEvent.detail`)を「`str` であること」で検める。事象の欄はこれで全部が値(数・文字列・数のタプル)になる。
5. 試験(`tests/bt/item_0/`): (a) 戦略が送ったあとに、自分の入れ物・戦略の見る注文から読んだ `extra_dict()`・結果の記録から読んだ物を変えても、取引所の側が届いた時刻に受け取る中身は送った時点のものであること(注文の遅れ 10 秒、変えるのはあとの呼び出し)。(b) 取引所の側が受け取った物を変えても、戦略の見る注文と結果の記録は変わらないこと。(c) 値のデータを種つき乱数で入れ子に作り、`extra_dict()` が元と等しい・元を変えても変わらない・`hash` が取れることを確かめる。(d) 値でない物(関数・任意のオブジェクト・循環)と形の誤りは作る時に断ること。(e) 約定の模型が文の欄に `str` でない物を入れると、その報告の段で断られること(上の確かめた穴)。(f) 核が作る全部の事象型について、欄の全部がハッシュの取れる値であること(事象型が足されたとき、中身の変えられる欄を持てば落ちる)。

## C. i0-r4-06 秒・ミリ秒の整数を、ナノ秒として黙って受ける

**なぜ起きたか**: 核の時刻は「int64 のナノ秒」だが、実行時には単なる `int` で(`Nanos` は `NewType`、`time.py:38`)、単位を運ばない。単位の誤りを捕まえる検査は、単位の札が付いた値を変換する `to_nanos`(`time.py:103-149`、既定の窓 1970〜2100 と、呼び手が渡す窓)にしか無い。核の入口(事象の構築 `validate_nanos`、`time.py:74-90`)は札の無い `int` を受けるので、int64 に収まるかしか見られない。そして**実行そのものが「この実行の時刻はどの範囲か」を持っていない**ので、事象の時刻の大きさを突き合わせる相手が無かった。`end_time_ns` にだけ単位の誤りの検査があるのは、最初の事象と比べられる 1 点だからで(`engine.py:602-608`)、事象の時刻には比べる相手が無い。既定の窓(1970〜2100)を核に置いても、秒の値(1970-01-01 の 1.7 秒後)もミリ秒の値(同じく 28 分後)も窓に入るので捕まらない。一方で「全ての int64 は時刻で、0 と 1970 年より前も含む」(`test_bt0_no_time_sentinel.py`、i0-r2-01)は核の規則なので、核が勝手に下限を決めることもできない。時刻の範囲を知っているのは呼び手(データ層・実行の設定)だけである。

**どの構造を変えるか**: **実行の設定に「この実行の時刻の範囲」を持たせ、入力の事象の時刻をそこに突き合わせる。**
1. `CoreEngine(..., time_span_ns=(lo, hi))` を足す(両端を含む。両端とも `validate_nanos` を通し、`lo <= hi`)。与えたとき、入力から読んだ事象の `exchange_time_ns` と `received_time_ns` の両方が範囲の外なら、その事象を読んだ時点で `TimestampUnitError`(流れの名前・何件目・値・範囲・「秒やミリ秒をナノ秒として渡していないか」)で断る。秒の流れとナノ秒の流れを混ぜた実行は、秒の流れの最初の事象で止まる。
2. 与えないときは、核は範囲を突き合わせず、そのことを黙らない: 結果の `defaults_used` に `time_span` を載せる(差し込み口を与えなかったときと同じ記録の場所。「呼び手が与えず、核の既定(= 突き合わせない)で走った」の意味)。既定で下限を決めない理由は上の「全ての int64 は時刻」。項目 1(データ層)と項目 8(再現性)が、データの範囲から `time_span_ns` を渡し、実行記録に載せられる。
3. `CORE_CONTRACT["time"]` とは別に `CORE_CONTRACT["run_settings"]` に、範囲の検査の規則と「与えなければ `defaults_used` に載る」を機械で読める形で書く。
4. 試験(`tests/bt/item_0/`): 秒・ミリ秒・マイクロ秒の整数を渡した事象が、範囲を与えた実行で断られること(受けた事象の時刻の種類 2 つ = 取引所の時刻と受け取った時刻の両方)。範囲の端ちょうどは受けること。範囲を与えない実行は今までどおり全部の int64 を受け、`defaults_used` に `time_span` が載ること。範囲の設定そのものの誤り(小数・逆順・int64 の外)を断ること。
