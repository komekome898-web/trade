## A. i0-r2-01 1970 年より前の時刻で、注文と通知が時刻 0 に飛ぶ

**なぜ起きたか**: 路(チャンネル)の FIFO の揃えを「前に着いた時刻」という裸の整数 1 つで持ち、「まだ何も通っていない」をその整数の 0 で表していた(`engine.py:439-440`)。時刻の定義域は int64 の全体で負の値を含むので、0 は「無い」の印ではなく、実在する時刻(1970-01-01T00:00:00Z)である。「無い」を定義域の中の値で表したため、`max(送った時刻 + 遅れ, 0)` が負の時刻を 0 に持ち上げた。同じ形(時刻の欄の既定値が 0)が、ほかに 3 か所ある: 戦略側の注文の口の「今」(`api.py:190` `_now: int = 0`)、待ち行列の鍵の 3 つ目(`engine.py:448` `received: int = 0`。同じ段の中では定数なので今は害が無いが、同じ種類の印)、約定の知らせの時刻(`interfaces.py:99` `venue_time_ns: int = 0`。手で作ると 1970 年の約定になる)。

**どの構造を変えるか**: 「無い」を時刻の定義域の外(`None`)で表す。
1. FIFO の路を 1 つの型(`_FifoChannel`)にし、前の時刻を `Optional[int]` で持つ。空の路は送った時刻 + 遅れをそのまま使い、揃えは前の要素があるときだけ効く。注文の路と通知の路はこの型を使う(揃えの書き方が 1 か所になる)。
2. 注文の口の「今」を `Optional[int]` にし、最初の呼び出しの前に使われたら止める。
3. 待ち行列の鍵の 3 つ目は、入力の配信では記録された受け取りの時刻、それ以外はその項目の時刻そのもの(0 を使わない)。
4. `FillNotice.venue_time_ns` を既定値なしの必須の欄にし、int64 のナノ秒として検める。

## B. i0-r2-02 取消を 2 つ出していると、1 つ目の拒否で「取消の答え待ち」が消える

**なぜ起きたか**: 「取消を送り、答えがまだ無い」という事実は**要求 1 件ごとに 1 つずつある**のに、注文ごとの bool 1 つ(`cancel_pending`、`api.py:163`)で表していた。bool は「いくつ行き来しているか」を持てないので、どの取消への答えでも倒れる。さらに、戦略の側は届いた通知が「どの取消への答えか」を知る手段を持っていなかった: 取消の拒否と取消についての状態不明には `request_kind` があるが、取消の成立(`OrderCanceledEvent`)には無く、取引所が自分で消した(期限切れなど)のか、こちらの取消への答えなのかが区別できない。取引所の側も、1 つの取消に答えが 2 つ(取消の成立と取消の拒否など)返ることを止めていなかった(`engine.py:726-739` は答えが 1 つ**以上**あるかしか見ない)ので、数えても合わない余地があった。

**どの構造を変えるか**: 取消の答え待ちを**件数**の事実にし、答えと要求を 1 対 1 に結ぶ。
1. 取引所の側: 1 つの取消には答え(取消の成立 / 取消の拒否 / 取消についての状態不明)を**ちょうど 1 つ**返させる。0 件も 2 件以上も `VenueProtocolError`。
2. 通知: 取消の成立の通知に「こちらの取消への答えか」を載せる(`OrderCanceledEvent.request_kind`: `"cancel"` = こちらの取消への答え、`"new"` = 新規注文への答えの一部(IOC の残りなど)、`"venue"` = 取引所が自分で消した(期限切れなど))。エンジンが、どの呼び出しの中の報告かから決める。
3. 戦略の見る注文: `cancels_in_flight`(送って答えがまだ無い取消の件数)を事実として持つ。取消を送るたびに 1 足し、取消への答え(上の 3 種)が届くたびに 1 引く。`cancel_pending` はその件数が 1 以上かを表す読み出し専用の値にする。終わりの状態(約定・取消・拒否)になっても件数は残す(残った取消には取引所が答えを返すので、答えが届いたときに 0 になる)。表に出す `state` は今までどおり事実から導く。
4. 路は FIFO なので、ある注文への k 番目の答えは k 番目の取消への答えである。件数が負になるのは核の不変条件の破れで、黙って 0 に戻さず止める。

## C. i0-r2-03 `history_limit` を付けると、同じ履歴への 2 つの問いが違う答えを返す

**なぜ起きたか**: 同じ履歴を 2 つの別々の入れ物(全体の一覧と型ごとの一覧)に持ち、**それぞれに別の保持の規則**(それぞれ N〜2N 件で別々の周期に切る)を当てていた(`engine.py:604-606・630-636`)。「型ごとの一覧は全体の一覧の同じもの・同じ順」という約束(`api.py:326-328`)を、作りの上で保つものが何も無かった。加えて、切り捨てたことを答えの側で表す手段が無く、切った部分に掛かる問い(窓の始まりが切った部分に入る・件数が残した分より多い・範囲を付けずに全部を求める)にも、短い答えを黙って返していた(`api.py:406-417`)。先読み(未来の時刻)には `LookAheadError` を置いたのに、過去の切り捨てには同じ考え(完全に答えられない問いは断る)を当てていなかった。

**どの構造を変えるか**:
1. 保持の規則を 1 つにする: 保持は型ごとに決め(型ごとに最新の N〜2N 件)、全体の一覧は「型ごとに残した事象の和」を配信の順に並べたものとして、型ごとの切り捨てに合わせて作り直す。こうすると「全体の一覧を型で抜いたもの」と「型ごとの一覧」は作りの上で同じになる(片方だけを切る道が無い)。
2. 切り捨てを事実として持つ: 型ごとに「最後に捨てた事象の配信の通し番号(`seq`)と受け取りの時刻」を記録し、戦略の文脈に渡す。
3. 切った部分に掛かる問いは `HistoryTruncatedError` で断る: 問いの窓の始まり(`since_ns`、無ければ最初から)が、関わる型の捨てた部分に掛かり、かつ件数 `n` で窓を残した部分だけに閉じられない(答えの最も古い 1 件が、関わる型の捨てた事象より後でない)とき。答えが返るときは、切らない実行と同じ答えになる。

## D. i0-r2-10([直す])「未来の事象はどこからも届かない」という説明が言い過ぎ

**どの構造を変えるか**: 説明を、核が保証する範囲(文脈とそこから属性で辿れる物には、戦略がまだ受け取っていない事象が 1 つも無い)と、保証しない範囲(処理系の内部を覗く手段: 呼び出しの積み重ね・`gc`)に分けて書く(`engine.py` と `api.py` の冒頭、契約の `visibility`)。別の処理の単位で戦略を動かすことは、この周ではしない(要件の測り方は公開の手段で、公開の手段では止まる)。

## E. i0-r2-11([直す])`visible_events(n=負の数)` が黙って空を返す

**なぜ起きたか**: `n` の検査を「型が int か」だけにし、値の範囲(件数は 0 以上)を検めず、`n <= 0` を 1 つの枝で空にしていた。時刻の引数(未来は止める)と同じ「誤った問いは断る」を件数に当てていなかった。

**どの構造を変えるか**: 件数の引数を検める所を 1 か所(`_count_arg`)にし、負の数は `OrderApiError` で止める。`n=0` は「0 件」として空を返す(前の周の i0-r1-02 の約束どおり)。
