## A. 順序の指摘 4 件(i0-r1-05・06・10・12)は 1 つの根本原因から出ている

**なぜ起きたか**: 核の待ち行列の鍵は `(時刻, 優先度, 出所, 通し番号)` で、2 つ目の「優先度」は**事象の型**(と要求の種類: 新規 10 < 取消 11)で決まっていた(ordering.py:101-128)。核には「路(チャンネル)」という考えが無く、「同時刻の並びの規則」を**すべての事象に型の順で当てる**形で書いていた。FIFO は、路ごとに着く時刻を `max(…, 前の時刻)` で揃える(engine.py:538・545・677)ことで作ろうとしたが、時刻を揃えると同時刻が生まれ、同時刻では型の優先度が路の順を上書きする。つまり「時刻の単調さ」を「順の保存」と取り違えていた。

- i0-r1-05: 取消 X → 新規 Y を同じ時刻に揃えたあと、`VENUE_ORDER < VENUE_CANCEL` で新規が先になる。
- i0-r1-06: 通知の時刻を揃えたあと、ACK < FILL < STATE_UNKNOWN の型の順で並ぶ。
- i0-r1-10: 1 本の入力の中でも、同時刻なら型の順で並べ替える(型の順を入力の中にまで当てていた)。
- i0-r1-12: 配信の路には時刻の揃えすら無く、遅延の揺れで 1 本の入力が自分を追い越す。

**どの構造を変えるか**: 待ち行列の鍵を「型の優先度」から「**路の段 + 路の中の位置**」に替える。

1. 路を 5 つに分け、それぞれを FIFO として持つ。①入力が取引所に届く(取引所の時刻・併合の順)、②戦略 → 取引所の要求(新規と取消を**1 本の路**で、送った順)、③入力が戦略に届く(入力 1 本ごと、受け取った順 = 記録された受け取りの時刻、同じなら入力の中の位置)、④取引所 → 戦略の通知(1 本の路で、取引所が出した順)、⑤戦略の時計。
2. 鍵は `(時刻, 路の段, 路の中の位置)`。同時刻では路の段の順(①→②→③→④→⑤)、同じ路の中では路の位置の順。**型は鍵に入らない。**
3. 型の順が使われるのは、順の情報が無いところ = **別々の入力の先頭どうしが同じ取引所の時刻に並んだとき**の併合だけ(先頭の型の順、次に入力の名前)。1 本の入力の中の順は、型によらず入力の順を守る(i0-r1-10)。
4. 配信の遅延(③)は、同じ入力の中で「前に受け取った事象」を追い越させない。遅れた事象は待ち行列から出るときに、同じ入力でそれより前に受け取った事象がまだ届いていなければ、その事象の届く時刻まで待たせる(i0-r1-12)。記録された受け取りの時刻そのもの(`received_time_ns`)が入力の順と違う場合(場面 p4-received-time のように遅れて受け取った約定)は、受け取った順で届ける(記録そのものが受け取りの順を示すので)。

## B. i0-r1-07 取引所の台帳が STATE_UNKNOWN で履歴を失う

**なぜ起きたか**: 台帳は注文ごとに**状態の文字列 1 つ**だけを持ち(engine.py:146)、StateUnknown は要求の種類を問わず、その 1 つを UNKNOWN に上書きした(211-212)。「受付を受けたか」「どれだけ約定したか」という既に確定した事実が、1 つの欄の上書きで消える。そのあとの検査は UNKNOWN という文字列だけを見るので、受付済み・一部約定済みの注文にも 2 回目の受付と新規の拒否を通した。状態不明には「新規が通ったか分からない」と「取消が効いたか分からない」の 2 種類があるのに、1 つの値で表していた。

**どの構造を変えるか**: 台帳は注文ごとに**事実**を持つ(受付を受けたか・約定の合計・終わりの状態・新規についての不明・取消についての不明)。報告は事実に照らして検める(受付済みなら 2 回目の受付も新規の拒否も矛盾)。取消についての不明は受付や約定の事実を消さない。表に出す状態の名前(`venue_states`)は事実から導く。

## C. i0-r1-09 戦略の見る状態から STATE_UNKNOWN が消える

**なぜ起きたか**: B と同じ形の欠陥が戦略の側にあった。`OrderView.state` 1 つの欄に、注文の一生(受付待ち・受付済み・不明・終わり)と「こちらの取消が行き来している最中」を**同じ欄**で入れていた。取消を送ると STATE_UNKNOWN を PENDING_CANCEL で上書きし(api.py:203-206)、取消の拒否が来ると「受付を受けていたか」から前の状態を**推測で**戻した(250-252)。不明は取引所の答えでしか解けないのに、戦略の側の操作と推測で解けていた。

**どの構造を変えるか**: 戦略の見る注文も事実で持つ(受付を受けたか・取消を送って答え待ちか・何についての不明か・終わりの状態)。表に出す `state` は事実から導き、**不明は、それを解く取引所の答え(新規についての不明なら受付・拒否・約定・取消成立、取消についての不明なら取消成立か全量の約定)が届くまで STATE_UNKNOWN のまま**にする。取消の答え待ちは別の欄(`cancel_pending`)で見せる。

## D. i0-r1-08 未来の時刻からの読み出しが素通りする

**なぜ起きたか**: 先読みの検査を「引数ごと」に書いていた。`until_ns` には「今より後なら止める」を書いたが、`since_ns` には書かなかった(api.py:354-362)。規則が「時刻の引数はどれも今以下」という 1 つの形になっておらず、引数を足したときに漏れる作りだった。

**どの構造を変えるか**: 時刻の引数を検める所を 1 か所にし(`_time_arg`)、履歴を読む口の時刻の引数は**すべて**そこを通す。今より後の時刻は、どの引数でも `LookAheadError` で止める。

## E. i0-r1-11 長さ 0 で値幅のある足を受け付ける

**なぜ起きたか**: 足の検査は「始まり ≤ 終わり」という**時刻の並び**しか見ず(events.py:254-261)、「足は正の長さの区間を集めたもの」という**足の意味**を検めていなかった。始まりの時刻で打たれた足(データの誤り)は、始まり = 終わりの形で現れるので、並びの検査を通り抜けた。

**どの構造を変えるか**: 足の区間を `[始まり, 終わり)` と定め、`start_time_ns` を与えるなら `start_time_ns < exchange_time_ns` を必須にする(長さ 0 の足は作れない。1 件の約定は約定の事象で表す)。

## F. i0-r1-13 `end_time_ns` と `history_limit` が検められない

**なぜ起きたか**: 「時刻は必ず `validate_nanos` を通る」という関門を、事象の時刻と待ち行列の時刻にだけ置き、**走らせ方の設定**(`CoreEngine` の引数)には置いていなかった。設定の数も同じ検査を通すべき入口だという考えが抜けていた。

**どの構造を変えるか**: `CoreEngine` の時刻の引数は構築時に `validate_nanos` を通す(float・bool・int64 の外は止める)。単位を取り違えた値(秒など)は int64 の範囲に入ってしまうので、**最初に処理する時刻より前で終わる窓**(何も処理せずに終わる窓)を最初の一歩で止める。`history_limit` は整数(bool を除く)で 1 以上に限る。
