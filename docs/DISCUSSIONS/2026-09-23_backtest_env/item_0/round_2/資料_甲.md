# 項目 0(核)比較資料 甲

観点は固定した要件(REQUIREMENTS.md)の V1〜V6。各節 3 行以内(何ができるか / 既定で何が起きるか / 根拠)。

## V1(時刻表現の一貫性)

- 何ができるか: 事象の時刻は表形式データの時系列索引をそのまま使っており、単一の整数型への統一や単位の検出・拒否を行う専用の機構は無い。
- 既定で何が起きるか: 秒・ミリ秒・ナノ秒などの単位が混在していても、変換や検査をせずにそのまま扱われる。
- 根拠: 該当コード中に単位の変換・検査に相当する処理が無いことを、関連する語での検索で確認。

## V2(事象型の網羅性)

- 何ができるか: 扱える事象は「足(一定間隔の四本値)」の1種類のみで、約定・板の写真・板の差分・資金調達・清算・時計・注文の受付/拒否/約定通知に相当する型は存在しない。
- 既定で何が起きるか: 足以外の事象は表現できず、戦略に渡されるのも足の系列だけになる。
- 根拠: 戦略が受け取る引数の型を定義したコードで確認。

## V3(ルックアヘッド不能性)

- 何ができるか: 戦略へは、現在位置までの足の系列をその都度切り出して渡す作りになっており、「足」という1種類の事象については未来の値を渡さない構造になっている。
- 既定で何が起きるか: 事象が足の1種類しか無いため、複数種類の事象が混在したときにも同じ強制が効くかは、この実装からは判定できない。
- 根拠: 切り出して渡す処理のコードと、それを呼ぶ繰り返し処理のコードで確認。

## V4(決定的な事象順序)

- 何ができるか: 事象は1種類(足)しかないため、同時刻に複数種類の事象が起きたときにどちらを先に扱うかという規則そのものを持たない(規則を書く対象が無い)。
- 既定で何が起きるか: 単純な逐次の繰り返し処理が足を1本ずつ処理するだけで、事象種別間の優先順位という概念は存在しない。
- 根拠: 繰り返し処理本体のコードで確認。

## V5(戦略APIの疎結合性)

- 何ができるか: 戦略は「足の系列を受け取り、売買の指図を返す」という1つのメソッドだけを持つ設計方針が文書化されており、戦略の実装は口座・発注・取消を直接扱わない。
- 既定で何が起きるか: 返り値は1つの指図オブジェクトにまとまっており、事象ごとの呼び出し・発注・取消という複数の窓口には分かれていない。
- 根拠: 戦略の基底クラスの説明文とメソッド定義で確認。

## V6(拡張点の分離)

- 何ができるか: 費用の計算は実行主体と同じファイルに埋め込まれたデータ構造で表され、口座の状態(現金・建玉など)と約定判定(執行方式を表す文字列引数による分岐)は実行主体の関数の内部にローカル変数・条件分岐として直接書かれている。遅延の模型に相当する概念は無い。
- 既定で何が起きるか: 費用・口座・約定判定を差し替えるには、実行主体の関数そのものを書き換える必要がある。
- 根拠: 費用のデータ構造・執行方式の分岐・口座の変数を定義したコードで確認。
