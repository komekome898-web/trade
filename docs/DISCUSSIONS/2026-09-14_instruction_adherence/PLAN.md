## ① 行動チャネルを、リードが著者でない材料として監査に渡す

### 根拠

- Compliance Gap **Theorem 2**: テキストだけからは手順の乖離を検出できない。
  盲検の人間 9 名で κ = 0.130、15 件中 **0 件**を正しく同定。**LLM 監査役でも回収率 40%(最良 60%)。**
- Westbrook 2021: 「独立」二重確認の実地内訳は **真に独立 1.0% / priming 92.5%**、
  priming された方は誤りを減らさなかった。
- RealCritic: 自己批評は 6 モデル中 5 でマイナス、他者批評は全モデルでプラス。
- **この体制の現状**: 監査役はリードが呼び、リードが書いた成果物を、リードの文脈と一緒に見ている。
  **定義上 priming されている。**17 回回して行動が変わらなかったのはこの構造の帰結。

### 設計

**新規スクリプト `scripts/trace_metrics.py`**

- 入力: 会話の記録 JSONL(`transcript_path`)。フックが `.claude/state/transcript_path` に落とす。
  `--jsonl <path>` で明示指定も可。
- **「手(move)」への分割**: オーナーの user メッセージを境界にする。
  フック由来のシステム通知・task-notification は境界にしない(オーナーの発言ではない)。
- 各手について、**機械的に抽出できるものだけ**を出す:

| キー | 内容 |
|---|---|
| `tools` | 道具名ごとの呼び出し回数 |
| `read_goal` | この手の中で `PROJECT_GOAL.md` / `OWNER_INTENT_*.md` / `OWNER_MODEL_SOURCE.md` を Read したか(真偽) |
| `first_write_at` | 最初の Write/Edit が何回目の道具呼び出しか |
| `claims_without_output` | 断定語を含むアシスタント返答のうち、同一返答内に tool_result が無いものの数(O-3 の機械化) |
| `audit_calls` | 監査役呼び出しの位置と、その**直後**に `ACTION_LOG` へ Write したか(I-009 の機械化) |
| `protected_writes` | 保護対象パスへの書き込みの有無 |
| `n_tools` | この手の道具呼び出し総数(④ の分母) |

- 出力: `docs/AUDITOR/TRACE/YYYY-MM-DD_<session先頭8桁>.json`
- **スキーマを固定し、自由文フィールドを持たせない。**リードの要約・主張が入る余地を構造で無くす。

**新規フック `.claude/hooks/trace_snapshot.sh`**

- `SessionStart`: `transcript_path` を `.claude/state/transcript_path` に保存。
- `Stop`: `trace_metrics.py` を走らせて TRACE を更新。

**監査役の定義変更 `.claude/agents/owner-model-auditor.md`**

- 検査の入力を次の 2 つだけに限定する条項を足す:
  - (a) `docs/AUDITOR/OWNER_MODEL_SOURCE.md` の逐語(現行どおり)
  - (b) **当該手の TRACE JSON**
- **リードが書いた成果物本文・要約・主張は渡さない。**
- 監査役の返答の形は現行どおり(通す/止める + 逐語の根拠)。

**汚染の検査 `scripts/verify_gates.py` に 2 ケース追加**

- TRACE JSON に想定外の自由文フィールドが混入したら落ちる(スキーマ検査)。
- 監査役へ渡すプロンプトにリードの成果物本文が含まれていたら落ちる。
- **通る側と止まる側の両方**を測る(現行の他ケースと同じ形)。

### 承認が要るもの

- **A-15**: 監査役の定義変更。
- **A-16**: 新規フックと `settings.json` への配線。

### 効いたと言える条件

監査役が TRACE だけを見て出した指摘のうち、**リードの文書を見ていたときには出なかった型**が出ること。
出なければ、priming が原因ではなかったことになる。

## ② 遵守の主張ではなく、プロセス指標を項目ごとに数える

### 根拠

- Urbach 2014: 自己報告コンプライアンス **98%** で、死亡率 OR 0.91(P=0.13)、合併症 OR 0.97(P=0.29)。
  **効果ゼロ。**
- Haynes 2009 の効果の実体はプロセス指標にあった:
  予防的抗菌薬 56.1% → 82.6%、口頭確認 54.4% → 92.3%、**6 指標すべて実施 34.2% → 56.7%**。
- Leape: 「it is not the act of ticking off a checklist that reduces complications,
  but **performance of the actions it calls for**」。
- **この体制の現状**: `ACTION_LOG` の「判定: 通す」を数えている。**これはオンタリオの 98% と同じ性質の数字。**

### 設計

**新規 `docs/AUDITOR/PROCESS_METRICS.md`** — 定義だけを人が書く。値は書かない。

| # | 指標 | 定義(TRACE から機械的に計算) |
|---|---|---|
| P1 | ゴール参照率 | オーナーの発言以降、最初の Write/Edit までに `read_goal` が真だった手の割合 |
| P2 | 対応表の提示率 | §0.1 の対応表を出してから着手した作業単位の割合 |
| P3 | 主張と出力の同居率 | 断定語を含む返答のうち、同一返答にコマンド出力があった割合(O-3) |
| P4 | 逐語の即時貼付率 | 監査役の返答を、次の道具呼び出しより前に `ACTION_LOG` に貼った割合(I-009) |
| P5 | 1 作業単位あたりの道具呼び出し数 | `n_tools` の中央値と分布(④ の閾値の根拠になる) |
| P6 | 指摘の実物反映率 | 監査役の指摘のうち、**実物の差分として入ったもの**の割合(「直したと書いた」対「直っている」) |

  という §1-3 の教訓に従う。

### 承認が要るもの

なし(`docs/` のみ)。ただし `TREND.md` の項目変更は監査役の運用に関わるので、**① と同時にオーナーへ出す。**

## ③ 逸脱しなくても作業が完了する経路 / 逸脱を構造的に不可能にする

### 根拠

- Reason の分類: 逸脱を**自分で書いてから進んだ**ものは error ではなく **violation**。
  violation は情報不足で起きていないので、**規則の追記・強調・再掲では原理的に直らない。**
  効くのは (a) 逸脱しなくても仕事が終わる経路、(b) 構造的に不可能にすること、の 2 つだけ。
- ビンクリスチン: 誤ラベル防止・分離保管・専門病棟限定・**独立二重確認とタイムアウト**・警告ラベルが
  全滅した後、**ミニバッグ(脊椎針に物理的に刺さらない)だけが効いた**。
- NIOSH / ISMP: 「規則と方針」は最下層。forcing function だけが high-leverage。
- FAA 実測: 手順不遵守の **16〜34% が意図的な違反**、それが事故の **15.5〜47%** に寄与。

## ④ 作業単位を短く切る

### 根拠

- McMillan 2026(Claude Code CLI **1,650 セッション / 16,050 観測**):
  **生成関数 1 つごとに遵守オッズが 5.6% 低下(OR = 0.944, 95%CI [0.937, 0.951], z = −14.82,
  p = 1.08 × 10⁻⁴⁹)。**別コードベース・別モデルでも同方向に再現。
  一方、ファイルサイズ(p=0.16, BF10=0.096)・指示の位置(p=0.83)・分割構成(p=0.19)・
  矛盾の併存(+0.33pp, p=0.912)は**いずれも検出されず。**
- Laban et al.: 毎ターン全要件を再掲(RECAP)しても **76.6**、FULL の **93.0** には戻らない。
  **「思い出させる」対策の上限がこれ。**
- Swiss の手術チェックリスト観察: Team Time Out は 96-100% 実施、
  **Team Sign Out は 22%**。原因は「必要な人が既に居ない」= **実施の前提が消えていること。**
- **この体制の現状**: 今日は 1 つのセッションで **1,054 回**の道具呼び出しをした。

### 設計

**新規フック `.claude/hooks/move_budget.sh`(PreToolUse)**

- 現在の手の道具呼び出し数 N を数える(`.claude/state/move_counter`)。
- N = 閾値 T → **1 行だけ**表示: 「この手は N 回目。委任か区切りを検討」。
- N = 2T → 拒否し、委任か、いったん報告して区切ることを要求。
- **表示は 1 行だけ。**警報疲労(Joint Commission / Drew 2014)を避けるため、
  規則の再掲はしない。

**閾値 T を、いま決めない**

- McMillan の OR は「**生成した関数 1 個ごと**」であって「道具呼び出し 1 回ごと」ではない。
  **単位が違うので、文献から直接 T を決められない。**
- A-12(根拠のない設定値を置かない)に従い、
  **② の P5(1 作業単位あたりの道具呼び出し数の分布)を 2 週間測ってから、
  その中央値を初期値に置く。**
- **測るまで数字を書かない。**

**`delegated-study` スキルの位置づけを書き換える**

- 現行: トークン節約の手段(I-007)。
- 変更後: **遵守率の道具**でもある。委任先は毎回まっさらな文脈から始まるので、
  セッション内減衰の分母がリセットされる。
- 測定・実装・機械的な直し(参照の付け替え・逐語の移設・数え直し)は**既定で委任**。
  リードは判断だけ書く。これは I-007 に既にあるが、**動機が変わる。**

### 承認が要るもの

- **A-16**: `move_budget.sh` と配線。
- スキル文言の変更は承認不要。

### 効いたと言える条件

**委任した単位と、リードが自分で通した単位で、P1〜P6 を比較する。**
委任側が有意に良くなければ、④ は効かなかったことになる。**これが④の唯一の証拠。**

## ⑤ 日常の規則集と、危機時の短い read-do を分ける

### 根拠

- Arriaga 2013(無作為割付、17 チーム × 106 シナリオ):
  **危機時の read-do チェックリストで、救命手順の不遵守 6%(あり)対 23%(なし)、P<0.001。**
- 一方、日常型の do-confirm は実地で再現に失敗(Urbach 2014)。**混ぜてはいけない。**
- Degani & Wiener 1993: 「長いチェックリストは do-list に堕落し、設定の冗長性を失う。
  **it can easily 'migrate' to those items that are crucial to the safety of the flight**」。
- FAA AC 120-71B §5.4: 「**'set' や 'checked' という一般的応答は情報量が乏しい**」
  → **実際の指示値を答えさせる。**
- FAA AC 120-71B §5.2.2.5(5): 「**A checklist should not be depended upon to initiate a change
  in aircraft configuration**」→ **チェックリストは検証装置であって実行装置ではない。**
- Delta 1141: challenge と response の間隔が **1 秒未満**。コールアウトは全部正しく、
  フラップは出ていなかった。**引用の存在は遵守の証拠にならない。**

### 設計

**`CLAUDE.md` は現状維持**(252 行 / 太字 159)。
位置もサイズも効果が測定されていないので、**いじる根拠が無い。**

**新規 `docs/AUDITOR/READDO/` — 各 1 枚・10 項目以内・read-do 形式**

| ファイル | 開く条件(機械が決める) |
|---|---|
| `audit_stop.md` | 監査役が「止める」を返したとき |
| `push_blocked.md` | 押し出しの関門が止めたとき |
| `before_unseal.md` | 判定区間を開ける直前 |
| `owner_objection.md` | オーナーが否定的な語を出したとき(`owner_turn_digest.sh` が検出) |
| `repeat_defect.md` | 同一作業単位で 2 回同じ型の指摘を受けたとき |

**設計上の決めごと**

1. **開く条件をリードの自覚に任せない。**「今は危機だ」と判断させない。フックが検出する。
2. フックは**該当する read-do のパスを 1 行表示するだけ。**全文は出さない(警報疲労)。
3. **各項目の応答は「確認した」ではなく「何が見えたか」を書く。**(FAA §5.4)
4. **read-do は作業を起動しない。検証だけ。**(FAA §5.2.2.5(5))
5. **各枚の最後の項目は必ずこれにする**:
   > **直したと書く前に、実物を開いて差分を出し、その出力をここに貼る。**

   今日の最も重い誤り(「片方だけ塞いで、両方塞いだと台帳に書いた」)に直接対応する。
   監査役の逐語: 「**報告の内容の誤りより重い**」。

### 承認が要るもの

- `docs/` の新設は承認不要。
- **A-16**: 該当イベントでパスを表示するフックの追加。

### 効いたと言える条件

read-do を開いた回で、P6(指摘の実物反映率)が上がること。

## ⑥ 一回の導入ではなく継続して測る + 回避の測定

### 根拠

## この計画が抱えるリスク(先に全部書く)

1. **リードが書いた関門は、今日 4 版出して 4 版とも欠陥だった。**
   だから `verify_gates.py` に**通る側と止まる側の両方**の試験を足すまで、
   ①〜⑥ のどれについても「効いている」と書かない。
2. **解除ファイルはリードが作れる。**構造的な不可能性ではない。R1・R4 で測る。
3. **「プロンプトに書く」対「コードで強制する」の効果量は、査読付き文献に存在しなかった。**
   方向としては言えるが、**どれだけ良くなるかは予測できない。**
   オーナーの「微減するだけでは」という懸念を否定する材料は無い。
4. **自己点検が下がるという証拠は推論タスクのもの**で、規則遵守での直接測定ではない(Huang et al. が射程を明記)。
   ①の根拠のうち RealCritic / Huang はこの限界を負っている。
   限界を負っていないのは Westbrook(実地の二重確認)と Compliance Gap(手順遵守そのもの)。
5. **Compliance Gap は単著・独立ラボの 2026 年プレプリントで、追試を確認していない。**
   ただし「監査証跡 97% / ファイル読み 0%」という選択性は、
   このセッションのリード自身の測定(報告書 20 回書き直し / ゴール 0 回読み)と独立に一致している。
6. **McMillan のセッション内減衰は、著者自身が「事前登録された仮説ではなく探索的所見であり、
   独立再現を要する」と書いている。**④ の根拠はこの 1 本に強く依存している。
7. **機械が増えることそのものが L-102 に逆行する。**上に数を明示した。
