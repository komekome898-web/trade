## 1. 3 層: カード / 合成器 / 帰属

### 1-0 全体の形【設計】

```
本番: 気配・約定・Binance の値 ─(橋 §2)→ 研究の口の事象 ─→ 合成器(版ごとに 1 つ)
                                                              │ 足ごとにカードを呼ぶ → e_i
                                                              │ 重みで足し合わせ → 目標の持ち高
                                                              └ 注文(研究の口の OrderRequest)
                                                                     │
本番の注文の道(今の _try_order → 事前の検査 → OrderManager)←────┘ (橋が直す)
約定・拒否 ─(橋)→ 研究の口の通知 ─→ 合成器
合成器の「足ごとの記録」+ 実際の約定 ─→ 帰属(カードごとの損益)
```

研究(バックテスト)では、橋の代わりに `CoreEngine`(`src/bot/bt/core/engine.py`)が同じ合成器を動かす。**合成器とカードのコードは研究と本番で 1 つ**。違うのは、事象を届ける側と、注文を受ける側だけ。

### 1-1 カード

カード = 1 つの案を、足ごとに持ち高 e(−1〜+1)を出す関数にしたもの。**注文は出さない**。

```python
# 置き場所の案: src/bot/research/cards/base.py(新)
from dataclasses import dataclass
from typing import Protocol
from bot.bt.core import BarEvent, StrategyContext

@dataclass(frozen=True)
class CardOutput:
    e: float                                   # −1.0〜+1.0。+1 = 買いの上限、0 = 持たない
    kind: str = ""                             # その足の信号の種類。旧互換のカードだけが使う(§5-1)
    notes: tuple[tuple[str, float], ...] = ()  # 計算の途中の値(記録と帰属の表示用。判断には使わない)

class Card(Protocol):
    card_id: str                    # docs/RESEARCH/cards/<id>/CARD.md の id(第 4 版 §3-1)
    streams: tuple[str, ...]        # 読む流れの名前(例: ("price", "leader"))
    warmup_bars: int                # これより足が少ないうちは e = 0 を返す
    def position(self, bar: BarEvent, ctx: StrategyContext) -> CardOutput: ...
```

- 入力は「その足の終わりまでに受け取れた事象」だけ。カードは `ctx.visible_events(EventType.BAR, n=...)`・`ctx.last(...)` で過去を読む。未来を読もうとすると研究の口が `LookAheadError` で止める【事実: `src/bot/bt/core/api.py` 722〜760 行の `visible_events` の説明】。
- カードは注文の関数(`ctx.place_order`)を呼ばない。合成器が `position` に渡す前に、注文の関数を呼べない包みで渡す【設計】(呼んだら例外。試験で確かめる)。
- カードは自分の状態(前の足の e など)を持ってよい(第 4 版 §2「出口の規則・保有中の判断は e の時系列に入る」)。ただし状態は**自分の過去の e と、読んだ事象だけ**から作る。実際の約定・帳簿の持ち高は読まない(読むと、執行のずれがカードの中に混ざり、帰属が分けられない)。

### 1-2 合成器

合成器 = 研究の口 `bot.bt.core.Strategy` で書いた、ただ 1 つの戦略【事実: 研究の口の形は `src/bot/bt/core/strategy.py` 8〜15 行、`on_event(self, event, ctx) -> None`】。版ごとに 1 つ作る。

```python
# 置き場所の案: src/bot/research/composer.py(新)
from bot.bt.core import Event, Strategy, StrategyContext

@dataclass(frozen=True)
class VersionSpec:
    version_id: str                 # 版の番号(研究から本番まで同じ)
    registered_on: str              # 登録日(UTC の日付)。確認はこの日より後のデータで
    cards: tuple[tuple[str, dict], ...]   # (card_id, 水準)
    price_stream: str               # 合成器が動く足の流れ(bitFlyer の足)
    weight_rule: str                # 重みの出し方の名前(段 4 で決める。版 X0 は "single")
    size_rule: dict                 # 量の決め方(§1-2 の「量」)
    starting_equity_jpy: float

@dataclass(frozen=True)
class DecisionRow:                  # 合成器が足ごとに 1 行書く(帰属・ダッシュボード・突き合わせの材料)
    version_id: str
    bar_end_ns: int                 # 足の終わり
    decided_ns: int                 # 判断した時刻(= その足を受け取った時刻)
    cards: tuple[tuple[str, float, float, str], ...]   # (card_id, e_i, w_i, kind_i)
    target_q: float                 # Σ w_i·e_i を −1〜+1 で切ったもの
    unit_size: float                # q = 1 のときの量(BTC)
    target_size: float              # 刻みに丸めた目標(符号つき BTC)
    position_before: float          # 判断の時点で合成器が知っている自分の持ち高(約定の通知から)
    order_ids: tuple[str, ...]      # この足で出した注文

class Composer(Strategy):
    def __init__(self, version: VersionSpec, cards: Sequence[Card]) -> None: ...
    def on_event(self, event: Event, ctx: StrategyContext) -> None: ...
    decisions: list[DecisionRow]    # 足ごとに 1 行足す。橋と測定器が呼び出しのたびに読む
```

- **動くとき**: `price_stream` の足(`BarEvent`)を受け取ったときだけ判断する。同じ窓の他の流れの足は先に届いているものだけを使う(研究の口の並びの規則は「取引所の時刻 → 種類 → 流れの名前」【事実: `engine.py` 627〜718 行の `_SourceMerger`】。橋は同じ並びで渡す。§2-4)。
- **自分の持ち高**: 約定の通知(`OrderFillEvent`)と `ctx.order(...)` から数える。帳簿は読まない(研究でも本番でも同じ情報だけで動くため)。
- **量**: 目標 = target_q × unit_size を、商品の刻み(0.001 BTC)で切り捨てる。unit_size の決め方は版に登録する。版 X0(旧互換、§5)は今の bot と同じ「min(1 注文の上限 130,000 円, 資産 × 2 倍 × 0.9) を刻みで切り捨て」【事実: `src/bot/main.py` 1105〜1116 行】を使う。この関数は研究と本番で同じものを呼ぶ【設計】。
- **注文**: 目標と今の持ち高の差を、成行の `OrderRequest` で出す。持ち高を減らすだけの注文は `reduce_only=True` にする(橋がこれを「決済」として今の決済の道に通す。§2-4)。
- **記録の出し方**: 研究の口には注文以外の出口が無いので、合成器の属性 `decisions` に行を足す。今の研究の口の戦略も同じやり方で属性に記録を残している【事実: `src/bot/strategy/k1_xvenue.py` の `exit_reasons`(97 行付近で作り、`_order` で足す)】。

### 1-3 帰属(各カードの持ち高 × 実際の約定)

```python
# 置き場所の案: src/bot/research/attribution.py(新)
@dataclass(frozen=True)
class FillRow:
    version_id: str; t_ns: int; side: str; size: float; price: float
    mid_at_fill: float              # 約定の時点の仲値(気配から)
    fee_jpy: float
    origin: str                     # "version"(版の注文)/ "protective"(bot の損切り。§2-5)

@dataclass(frozen=True)
class CostRow:
    version_id: str; t_ns: int; kind: str      # "funding" / "leverage_fee"
    position: float; price: float; amount_jpy: float   # 払ったら正

def attribute(decisions: Sequence[DecisionRow], fills: Sequence[FillRow],
              costs: Sequence[CostRow], marks: Sequence[tuple[int, float]]) -> AttributionTable: ...
```

計算【設計】:
1. 足 t のカード i の仮の持ち高 x_i(t) = w_i(t) × e_i(t) × unit_size(t)(丸める前、BTC)。
2. カード i の値動きの損益 = Σ_t x_i(t) ×(次に持ち高が変わる時点の値段 − この時点の値段)。値段は、その足で版が実際に約定したならその約定値、約定していない(相殺で注文が出なかった)なら判断の時点の仲値。
3. 経費の割り振り: 約定の経費(約定値と仲値の差 × 量)は、その足の |Δx_i| の比で割る。資金調達とレバレッジ手数料は、課金の時点の x_i の比で割る(資金調達は向きで符号)。
4. **残り** = 版の実際の損益 − Σ カードの損益。内訳は「刻みに丸めた分」「相殺で払わずに済んだ経費」「bot の損切り」「遅れ」に分けて出す。**恒等式(Σ カード + 残り = 実際)が成り立つことを試験で確かめる**。
5. 同じ関数を、バックテスト・paper・実弾の記録に当てる(計画 段 4「バックテスト・paper・実弾で同じ計算」)。記録の形を 3 つで同じにするのは橋の役目(§2-6)。

### 2-2 研究の口の作り(橋の選び方を決める事実)【事実】

- `CoreEngine` は、渡された流れを「取引所の時刻」で混ぜる。作ったときと、1 件取り出すたびに、**全部の流れの次の 1 件を先に読む**(`engine.py` 627〜718 行の `_SourceMerger`、`_pull`・`pop`)。流れが終わる(`StopIteration`)と、その流れは二度と読まない(`engine.py` 645〜648 行)。
- 戦略に例外が出ると、その `CoreEngine` は以後使えない(FAILED)(`engine.py` 929〜961 行の `_usable`・`step`)。
- 研究の口の `FillModel` は取引所の**模型**で、本物の注文の道ではない(`src/bot/bt/core/interfaces.py` 153〜170 行)。
- 戦略に渡す `StrategyContext` は `bot.bt.core` から公開されているが、`CoreEngine` はそれを内部の部品(`_context_calls`・`_alive_switch`・`DeliveredHistory`・`_StrategySide`)で組み立てている(`engine.py` 1046〜1126 行)。

つまり、**`CoreEngine` を、時々しか事象が来ない本番の繰り返しから、そのまま 1 件ずつ回すことはできない**: 次の事象がまだ無いと、流れを読むところで止まるか、流れが終わってしまう【事実から導いた推定。試作で確かめる】。

### 2-3 3 つの作り方と、推奨

| 案 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|
| **(A) 推奨: 研究の口の核に「1 件ずつ届ける口」を足す** | `bot.bt.core` に小さい公開の部品 `LiveSession`(仮の名)を足す。`CoreEngine._deliver` と**同じ内部の部品**(履歴・注文の控え・文脈の取り消し)を使い、`deliver(event) -> list[OrderRequest]` で 1 件ずつ届け、合成器が出した注文を返す。取引所の側(約定・拒否)は持たず、橋が通知を `deliver` で戻す | 合成器が見るもの(未来を読めない・呼び出しが終わったら文脈が使えない・注文の控え)が、研究と同じ部品で保たれる。bot の繰り返しは 1 本のまま(スレッドを使わない)。注文は今の 1 本の道を通る | 研究の口の核を変える(核の約束の文書と試験を足す。批評家を通す) |
| (B) `CoreEngine` を別のスレッドで回す | 流れを「待つ」作りにし、事象のたびに続けて心拍(`ClockEvent`、時刻を 1 ns 後ろ)を入れて、先読みで止まらないようにする | 核を変えない | スレッドの同期が要る。例外 1 回で FAILED になり、作り直しに履歴の再生が要る。注文の受け手を `FillModel` の形で作ることになり、今の注文の道(事前の検査・キルスイッチ・状態不明の扱い)と 2 本になる |
| (C) 足ごとに `CoreEngine` を作り直して過去の窓を再生する | 足のたびに、過去の窓の事象で新しい `CoreEngine` を最後まで回し、最後の時刻の注文だけを使う | 核を変えない。合成器が過去だけで決まるなら同じ答え | 窓が長いカードで重い(第 4 版 §4-2 は 365 日の分位を使う: 1 分足で 525,600 本を毎分再生【計算】)。損切りなど、外から入った約定を再生に入れる仕組みが別に要る |

推奨は (A)。決め手は「注文は今の 1 本の道(`_try_order` → 事前の検査 → `OrderManager`、キルスイッチ、状態不明の扱い)から出す」こと(CLAUDE.md §1 の安全不変条件をそのまま保つため)【設計】。
**(A) が実際に作れるか(内部の部品を `CoreEngine` と共有できるか)は【未確認】**。実装の最初に試作の試験で確かめ、できなければ (B) と比べ直してオーナーに出す(§5-3 の手順 0)。

### 2-5 今の `step()` のどこを置き換えるか【設計】

### 3-2 注文の扱い【設計】

- paper の版の注文は、その版の `PaperExecutor` が、共通の気配で仮に約定させる(今と同じ「最良の売り / 買い + すべり」【事実: `paper.py` 46〜67 行】)。版どうしの約定は互いに影響しない(仮の約定なので、板を食う分も互いの影響も入らない。これは paper の限界として書く)。

### 3-4 隠れていた衝突: 版ごとの損失の停止【事実と、オーナーに聞くこと】

今の事前の検査は、日次の損失・最大の落ち込み・連敗に当たると、**キルスイッチを入れる**【事実: `src/bot/risk/pre_trade_checks.py` 63〜80 行】。版が 1 つなら問題ないが、複数の版を並べると、**paper の版の 1 つが日次の損失に当たっただけで、実弾の版を含む全部の版が止まる**。

### 3-5 再起動【設計】

- 各版の帳簿は自分のファイルから戻す(今の `_restore_paper_state` を版ごとに。`main.py` 564〜626 行)。

## 5. 入れ替えの手順

### 5-1 今の paper bot(xborder_momentum)をカードに移す【設計】

今の動き【事実: `src/bot/strategy/xborder_momentum.py` 25〜52 行、`main.py` 760〜808 行、`config/config.yaml` 30〜33 行】:
- Binance の k 本前からの値動き(対数)mom。k = 30、入る閾値 0.8%、決済の帯 0.05%。
- mom > 0.8% で「買い」、< −0.8% で「売り」、|mom| ≤ 0.05% で「決済」、その間は「様子見」。Binance の値が無ければ「様子見」。
- 「買い」のとき: 売りを持っていれば**決済だけ**(ドテンしない。次の足でまだ「買い」なら買う)。持っていなければ、SFD の守りが通れば買う。「売り」も向きを逆にして同じ。持っている向きと同じなら何もしない(増し玉しない)。
- 損切り: 足が完成したときだけ、含み損が 0.5% 以上なら決済(版の判断より先)。損切りのあと「様子見」なら持たないまま。

これを 2 つに分ける:
- **カード `xborder_mom`**: e = +1(買い)/ −1(売り)/ 0(決済)/ 前の足の e(様子見)。`kind` に「買い・売り・決済・様子見」を入れる。
- **版 X0 の合成器 `legacy_xborder`(旧互換)**: e ではなく `kind` と自分の持ち高から、上の「買い」「売り」「決済」の規則どおりに注文を出す。

`kind` を出す理由: 目標の持ち高を追う合成器(target = e × 量)だと、(1) 売りを持っているときの「買い」で 1 本の足でドテンする、(2) 損切りのあとの「様子見」で e = +1 のままなので建て直す。どちらも今の bot と違う動きになる。今の動きと同じにするには、「買い」と「様子見で前が買い」を見分ける必要があり、e だけでは見分けられない【事実から導いた設計】。
目標の持ち高を追う合成器(段 4 の版 0 の形)は、**別の版**として登録して測る。入れ替えではない。

### 問い 1: paper の版が損失の停止に当たったとき、どこまで止めるか

| 案 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|

- (b) 手順 1 と同時に入れ、突き合わせは経費を切った設定で行う。

§2-3 の (A)(研究の口の核に「1 件ずつ届ける口」を足す)で進めてよいか。核を変えるので、手順 0 の試作の結果を添えて改めて出す。
