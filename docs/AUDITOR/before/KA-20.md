## 該当箇所(全文引用、73-79 行付近)

```bat
echo [share_logs] adding retention snapshots (backtest_data\auto_*)
for /d %%D in (backtest_data\auto_*) do git add "%%D"

rem 清算ストリーム: 買えないデータなので、PC 1 コピーのままにしない (L-026)
echo [share_logs] adding liquidation stream (data\liquidations)
if exist "data\liquidations" git add -f "data\liquidations"
rem Commit only when there is something staged (quiet no-op otherwise).
git diff --cached --quiet || git commit -m "paper logs snapshot %date% %time%"
```

## 何が誤りだったか

`data\liquidations` は常駐の記録プロセスが継続的に追記する生ファイルであり、他の全ての
生データ(`backtest_data\auto_*` 等)が「コピーしてコピーを commit」する方式なのに対し、
清算ストリームだけが `git add -f` で**生ファイルそのものを追跡**していた。記録が動いている
限り作業ツリーは決してクリーンにならず、`git pull --rebase` が構造的に一度も通らない状態を
作っていた(2026-09-09、`restart_all.bat` が `[1/5]` で実際に停止)。

その結果、**修正コードが PC に届かない状態が固定化し、オーナーが手元でバッチファイルの
マージ・pull の失敗を診断・対処する役目を負うことになった**(L-036「私が PC を使ってあなたの
バッチをデバックしているこの状況は異常です」)。
