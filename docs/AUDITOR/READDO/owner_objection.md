# read-do: オーナーが否定的な語を出したとき

<!-- ⑤ 危機時の read-do(2026-09-14、L-169 で承認)
 形式: **read-do**。1 項目ずつ読んで、その場で実行してから次へ行く。
 まとめて読んでから一括で「やった」にしない(Degani & Wiener 1990/1993 の do-list 堕落)。
 根拠: Arriaga et al., NEJM 2013 — 危機時の read-do で救命手順の不遵守 6% 対 23%、P<0.001。
 応答は「確認した」ではなく **何が見えたか** を書く(FAA AC 120-71B §5.4)。
 **この手順書は作業を起動しない。検証だけである**(FAA AC 120-71B §5.2.2.5(5))。 -->

1. **弁解を書き始めない。**まずオーナーの原文を、1 文字も変えずに引く。
2. **その原文の中で、リードが自分の語彙に置き換えていた語を探す。**
   - A-1「オーナーの原文を自分の語彙に置き換えて実行する」は 2026-09-13 の破綻の中心だった。
   - 例: 「事前に煮詰めておきたいこと」を「段 0a」と呼び替えた(L-166)。
3. **指摘が当たっているかを、実物で確かめる。**`grep` / `sed` / `git diff` の出力を貼る。
4. **当たっていたら、そう書く。**「ただし」「一方で」を付けない。
5. **当たっていない部分があるなら、範囲を限って書く。**全体を否定しない。
6. **自分が止めていた作業がないかを確かめる。**
   - オーナーが承認済みの作業を、リードの判断で止めていないか(A-18 / L-019)。
   - 2026-09-14 に、未特定の否定的観測 1 件で承認済みの 4 件を止めていた。
7. **オーナーに聞き返す前に、自分で確かめられることかを判定する**(A-2「**自分で確認しろ**」)。
8. **聞くなら、選択肢にして出す。**仕様を書き下ろしてもらわない(§0.1)。
9. `docs/OWNER_LOG.md` に逐語で記録する。**その回のうちに**(§7)。

10. **直したと書く前に、実物を開いて差分を出し、その出力をここに貼る。**
    - 2026-09-14 の最も重い誤り: 「片方だけ塞いで、両方塞いだと台帳に書いた」。
      監査役の言葉: 「**報告の内容の誤りより重い。**」
    - 貼るもの: `git diff` の該当部分、または `sed -n` で開いた実物の行。
    - **「直した」という文だけを書いて終わらせない。**
