# read-do: 押し出しの関門が止めたとき

<!-- ⑤ 危機時の read-do(2026-09-14、L-169 で承認)
 形式: **read-do**。1 項目ずつ読んで、その場で実行してから次へ行く。
 まとめて読んでから一括で「やった」にしない(Degani & Wiener 1990/1993 の do-list 堕落)。
 根拠: Arriaga et al., NEJM 2013 — 危機時の read-do で救命手順の不遵守 6% 対 23%、P<0.001。
 応答は「確認した」ではなく **何が見えたか** を書く(FAA AC 120-71B §5.4)。
 **この手順書は作業を起動しない。検証だけである**(FAA AC 120-71B §5.2.2.5(5))。 -->

1. **拒否の理由をそのまま読む。**要約しない。不足として名指しされた項目を書き出す。
2. **止めたのがどちらかを確かめる。**
   - `[pre-push]` の行があれば **git 側**(`githooks/pre-push`)。
   - それが無く Bash が実行されていなければ **PreToolUse 側**。
   - 2026-09-14 の段 0 で、**この実行環境ではプロジェクト側のフックが 1 本も走っていなかった**
     ことが分かっている。**git 側だけが効いていた。**
3. **関門を直して通そうとしない。**`.claude/hooks/**` と `settings.json` は A-16 の対象で、
   オーナーの指示があったときだけ変える。
4. **不足を実際に埋める。**記録が足りないなら記録を書く。監査が無いなら監査を回す。
5. `sh .claude/hooks/_require_action_audit.sh "<range>"` を**手で走らせて**、
   不足が消えたことを実測する(押し出しを繰り返して試さない)。
6. **終了コードを貼る。**「通るはず」と書かない。
7. もう一度押し出す。
8. **通ったら、何が足りなかったのかを `ACTION_LOG` に 1 行残す。**
   関門が捕まえたものは、監査役 3 人が見逃していることがある(2026-09-14 に実例)。
9. `--no-verify` を使わない。**使ったら、その事実を `OWNER_LOG` に書く。**

10. **直したと書く前に、実物を開いて差分を出し、その出力をここに貼る。**
    - 2026-09-14 の最も重い誤り: 「片方だけ塞いで、両方塞いだと台帳に書いた」。
      監査役の言葉: 「**報告の内容の誤りより重い。**」
    - 貼るもの: `git diff` の該当部分、または `sed -n` で開いた実物の行。
    - **「直した」という文だけを書いて終わらせない。**
