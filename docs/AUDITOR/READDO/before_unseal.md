# read-do: 判定区間を開ける直前

<!-- ⑤ 危機時の read-do(2026-09-14、L-169 で承認)
 形式: **read-do**。1 項目ずつ読んで、その場で実行してから次へ行く。
 まとめて読んでから一括で「やった」にしない(Degani & Wiener 1990/1993 の do-list 堕落)。
 根拠: Arriaga et al., NEJM 2013 — 危機時の read-do で救命手順の不遵守 6% 対 23%、P<0.001。
 応答は「確認した」ではなく **何が見えたか** を書く(FAA AC 120-71B §5.4)。
 **この手順書は作業を起動しない。検証だけである**(FAA AC 120-71B §5.2.2.5(5))。 -->

1. **止まる。**開封は一度きりで、取り返しがつかない。
2. **事前登録を開いて、判定バーを声に出すつもりで書き写す。**記憶から書かない。
3. **MDE が書いてあるかを確かめる。**無ければ開けない(§5.2)。
4. **意図マップ(`INTENT_MAP.md`)の △ と ✕ を数える。**残っていれば、出る陰性は
   **陰性ではなく不明**である。数を書く。
5. **測定器の検証が閉じているかを確かめる。**
   2026-09-14 時点で `REPORT_2026-09-14.md` §0 は「**改良点は残っている。閉じない。**」と書いている。
6. **判定区間が一度も開いていないことを、コマンドで確かめて出力を貼る。**
7. **監査役を通す。**事前登録と生の出力の**両方**を渡す(§5.0 の 2)。
8. **開封の直前に、何を測って何を測らないかを 2 列で書く**(棄却の射程。§5.2)。
9. 開ける。**開けた事実と時刻を `OWNER_LOG` に書く。**

10. **直したと書く前に、実物を開いて差分を出し、その出力をここに貼る。**
    - 2026-09-14 の最も重い誤り: 「片方だけ塞いで、両方塞いだと台帳に書いた」。
      監査役の言葉: 「**報告の内容の誤りより重い。**」
    - 貼るもの: `git diff` の該当部分、または `sed -n` で開いた実物の行。
    - **「直した」という文だけを書いて終わらせない。**
