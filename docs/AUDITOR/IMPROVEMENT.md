# 監査役の改良ループ(本番作業の一部。オーナー条件 2026-09-11、L-116)

**目的関数**: オーナーの負荷を減らし、品質を上げ、コストを下げる。この 3 つを毎週測り、下がった指標があれば手を打つ。**自動で本番の定義を変えることはしない**(変更は全文の提案 → オーナー承認 → 適用)。

## 週次の手順(定期実行 = Routine が毎週月曜 09:00 JST に新しいセッションで実行。人手は不要)

1. **既知解の更新**: 前回以降の `docs/OWNER_LOG.md` の行を読み、指摘・差し戻し・却下・欠陥を露わにした問いを `docs/AUDITOR/COVERAGE_*.md` に追記し、新しい事例を `KNOWN_ANSWERS_ADDENDUM.md` と `before/`(訂正前の本文だけ)・`answers/` に追加する。**納品後にオーナーが訂正した件数**(= 実際の負荷)を数え、該当の納品の `VERDICTS/` に「見逃し」として結び付ける。
2. **検査集合の衛生**: `before/` の全ファイルを広い型(指摘・訂正・修正・誤り・正しくは・本来・後日・→・自案件の L-/I- id・抽出元コミット等の出所ヘッダ)で再検査し、漏れを `answers/` へ移す。
3. **盲検測定**: 本番の定義(`.claude/agents/owner-auditor.md`)と、あれば候補版(`.claude/agents/owner-auditor-candidate.md`)を、全事例 + 対照 3 節に 1 回ずつ当てる(事例名を伏せる)。厳密に採点(捕捉 / 部分 / 見逃し)。
4. **指標**: 品質 = 捕捉率(型別)/ 負荷 = 1 成果物あたりオーナーに届く項目数(止める + 聞く)と要旨の有無、納品後の訂正件数 / コスト = 1 回あたりの $ とトークン、対照節の問い数。`docs/AUDITOR/TREND.md` に 1 行追記(日付、定義の版、事例数、捕捉率、負荷、$/回)。
5. **コスト削減の手**(毎週 1 つ試して候補版に入れる): 入力の絞り込み(原則 + 該当型の既知解だけを渡す)、安定した入力の順序固定(プロンプトキャッシュ)、効果レベルの引き下げ、決定的検査のスクリプト化(LLM を使わない段を増やす)。
6. **提案**: 候補版が本番を品質で上回り、負荷とコストが悪化していなければ、差分の**全文**と両版の指標を `PROPOSED_CHANGES_<date>.md` に書き、`docs/OWNER_STATUS.md` の監査行に「承認待ち」と載せる。オーナーが承認した変更だけをリードが本番へ適用し、`TREND.md` に版を上げて記録する。
7. **報告**: 週次の結果は `EVAL_<date>.md`。オーナーへは状態板の 1 行(捕捉率・負荷・$)だけで足りる形にし、承認が要るときだけ提案を出す。

## 止める条件

- 捕捉率が 2 週続けて下がる、または納品後の訂正が増える → リードが原因を書き、オーナーに報告する(改良を止めるのではなく、方法を変える)。
- 週次の費用が $20 を超える → 事例の抽出(型ごとに代表を選ぶ)に切り替える。
