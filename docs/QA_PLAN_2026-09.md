## 1. データ管理(第 1 優先、`DATA_GOVERNANCE_PLAN.md` を実装に落とす)

### 1-1. 原則
- **全保管**: 取得・受領・生成した全ファイル(生 HTML/JSON/PDF/zip、中間 CSV、ログ、リスト)を保管する。
  削除は禁止。容量対策は gzip とオーナー PC の `data/archive/`(git 外、無期限)で行う。
- **単一の真実**: オーナー PC が原本。研究側(VM)は共有コピーと台帳・ハッシュだけを持つ。研究側は必ず
  共有コピーを読み、どのコピーを読んだかを出力に書く。
- **台帳が数字の唯一の出所**: 「何日分あるか」「何行あるか」はリードの手計算ではなく台帳から引く。

### 1-2. 実装(この順)
1. `scripts/intake_ledger.py`: `data/`, `paper_logs/`, `backtest_data/`, `data/archive/` 配下の全ファイルを走査し、
   `data/INTAKE.jsonl` に 1 行/ファイル(パス、サイズ、MD5、行数、先頭/末尾の時刻、取得経路、初回登録日、最終更新日)
   を追記・更新する。削除されたファイルは「missing」として残す(消えたことも記録)。
   `fetch_all.bat` と `share_logs.bat` の末尾で実行し、台帳自体を共有する。
2. `schema/*.json`: データセットごとに列の意味・単位・時刻基準(UTC/JST/収集時刻 vs 約定時刻)・既知の欠陥
   (メンテ窓の合成バー、交差板、誤プリント、出来高ゼロ日)を宣言。読み手はこれを読んでから使う。
3. `scripts/data_quality.py`: 取り込み時の自動点検(重複、欠測、ギャップ、交差板、メンテ窓、極端リターン、
   出来高ゼロ、時刻順序)→ `data/QUALITY.json`。除外は**しない**(印を付けるだけ)。
4. `config/constants.yaml`: 手数料・スプレッド実測・ティック・乗数・JPX 手数料など全定数を、値 + 一次資料 URL +
   確認日 + 実測なら測定スクリプトと期間、で登録。値だけの定数を禁止(既存 config の定数もここに移す)。
5. 保持期限の先回り: bitFlyer 31 日、OKX OI 1H 30 日 / 5 分 2〜3 日、L/S 比 60 日 → 期限の半分で自動スナップショット
   (`fetch_all.bat` に組込み、`backtest_data/` へ MD5 付き)。
6. ダッシュボード「データ蓄積」を台帳駆動に変更(期間・行数・最終更新・ギャップ・品質フラグ)。
7. `share_logs.bat` に `data/archive/` の**リスト**(内容はサイズ上共有しない)と台帳の共有を追加。

## 2. 監査の質を測ってから恒久化する(第 2 優先)

### 2-1. なぜ今の監査を信じ切れないか
- 監査者同士の不一致が実在した(コスト床・maker: E と E2 が逆符号 → 裁定で E の 2 つの誤りが判明)。
- リードの異論が 4 件残っている(入替反転の現代性、優待の実行可能性、cap 延長の片脚評価、週末ギャップの新規性)。
- 監査者自身のバグ(秒グリッド reindex、P&L 符号反転、`t`/`ts` 取り違え)が自己申告で複数回あった。
- 監査手続きの**感度と特異度が未測定**: 本物の効果を「再現」と言え、無い効果を「棄却」と言えるかを、
  正解が分かっている問題で試していない。

### 2-2. 監査の質の測定(既知正解テスト)
1. **合成データによる既知正解パケット**を作る(`scripts/qa/make_known_answer.py`):
   - 効果の大きさを埋め込んだ日足(夜間プレミアム +X bps、X ∈ {0, 2, 5})、
   - 効果ゼロのモメンタム 1 分足(ランダムウォーク)、
   - 既知の手数料・スプレッドを持つ合成テープ(コスト床の正解が分かる)、
   - 意図的な罠(交差板、メンテ窓の合成バー、`t`/`ts` の入替、分割未調整)。
   正解は封印ファイルに保存し、監査者には渡さない。
2. 盲検監査者(下位モデル 2 名 + 上位モデル 1 名)に本番と同じ PROTOCOL で判定させ、**感度(真の効果を再現と言う率)・
   特異度(ゼロ効果を棄却/判定不能と言う率)・罠の検出率・MDE の妥当性**を採点する。
3. 採点結果から、監査者数(1/2/3)、モデル、予算(呼び出し数)ごとの信頼度を表にし、**本番の判定に必要な最小構成**
   (例: 上位モデル 1 + 下位 1 の一致)を決める。
4. **監査者間一致率**: 本番の 45 パケットから無作為に 20% を第 2 監査に回し、判定の一致率と数値の一致率を出す。
   一致率が既知正解テストの水準を下回る型(例: maker 系)は、その型の手続きを直してから使う。

### 2-3. リードの異論の処理(残さない)
- 異論 4 件は、事前に決めた裁定規則で第 3 者に判定させる: (a) 現代性 = 直近 5 年の効果が MDE を超えるか、
  (b) 実行可能性 = 本プロジェクトの制約(現物ロング、資本)で取れるか、(c) 片脚/往復 = 往復での再計算、
  (d) 新規性 = 事前登録の有無。裁定結果で順位表を更新し、異論欄を空にする。

### 2-4. 恒久化の条件
- 既知正解テストで 感度 ≥ 0.9、特異度 ≥ 0.9、罠の検出率 ≥ 0.9 を満たす構成のみを標準手続きにする。
- 満たすまでは、判定は「暫定」表示とし、実弾判断に使わない。

## 3. 報告様式(即時適用)
- 戦略・法則は記号や ID でなく名前で書く。率には分母を添える。判定の変転は「前 → 後 → 誤りの型」で書く。
- 監査結果を報告する際は、必ず「平文まとめ」(`99_summary_plain.md` 形式)を添える。

## 4. 順序
1. データ管理 1-2 の 1〜7(実装、下位モデルに委任、リードがレビュー)
2. 既知正解テストの作成と採点(2-2)、異論の裁定(2-3)
3. 恒久化の可否判断(2-4)→ その後に再判定(`99_master.md` の優先順位)
