## 2. NautilusTrader — 唯一「思想として」検討に値したもの

紹介文の「**回測と実盤が同じ執行モデルを共有する**」は、当プロジェクトの再発する失敗様式そのものを突いている。
実際、監査 AR-18/42 では PAPER スリッページが実測の 4〜5 倍過大と判明し、P2-08 でも「モデル約定 vs PAPER 実約定」の差を反復として扱う必要があった。【事実】

しかし導入は成立しない。一次資料(README、2026-09-08 確認)で:
- 対応 18 統合は Binance / Bybit / OKX / Kraken / Coinbase / BitMEX / Deribit / IB / dYdX / Hyperliquid / Polymarket / Databento / Tardis ほか。
  **bitFlyer は無い。JPX・大阪取引所・kabuステーションも無い。**【事実】
- ライセンス LGPL-3.0、**Python 3.12 以上**。当リポジトリは 3.11(`requires-python = ">=3.11"`、実行環境 3.11.15)。【事実】

つまり採用するには **bitFlyer アダプタと kabu アダプタを自作**した上で Python を上げ、既存の 1,600 件超のテスト・封印プロトコル・
per-pair 費用モデルを移植することになる。得られるものは「執行モデルの共有」1 点で、それは移植せずとも解ける。【推定】

**代替(採用)**: 執行モデルの一致は *フレームワークの乗り換えではなく検査で* 担保する。既に P2-08 で導入した
「既知正解テスト(手計算 5 件と 1e-9 一致)」と「PAPER 台帳とモデル約定の差を実測して保守側に反映」を、**全単位の凍結条件として標準に格上げする**
(`docs/PHASE2_TEMPLATES.md` の凍結条件に既出。新規実装は不要)。

参考として、Nautilus に **Tardis アダプタ**がある点は P2-08b と重なる。当方は既に Tardis 無料サンプル 85 日を取得済みで、
形式の参照先として README のみ見れば足りる(コードの導入は不要)。【推定】

## 3. オンチェーンデータ = 「情報源」としての可能性(道具ではなく仮説)

**初版(2026-09-08 午前)の記述を撤回して差し替えた**。当初は「オンチェーンは日次で遅いから筋が悪い」と書いたが、根拠が弱く、
入手経路の判定(有料前提)も誤りだった。オーナーの再質問(同日)を受けて実測し直した結果が以下。

### 3.1 入手経路(実測 2026-09-08)
| 経路 | 結果 | 内容 |
|---|---|---|
| Coin Metrics **community** API(鍵不要) | **HTTP 200** | `FlowInExNtv` / `FlowOutExNtv`(取引所の流入・流出、native)・`AdrActCnt`・`PriceUSD` を**日次で 2015-11-01〜2026-09-07 の 3,964 日**取得。無料 |
| api.blockchain.info/charts | HTTP 200 | 日次のネットワーク統計。無料 |
| mempool.space API | HTTP 200 | メンプール・手数料のリアルタイム。無料。ただし**アドレスの帰属は無い** |
| api.glassnode.com | **HTTP 401** | 有料。CryptoQuant・Arkham も同様(取引所アドレスの帰属が有料部分) |
→ **無料で長期履歴は取れる。制約はデータの入手性ではない。**

### 3.2 効くかどうか(当方の費用と検出力で判定)
- BTC の**日次対数リターンの σ = 350 bps**、n = 3,963 日(Coin Metrics `PriceUSD` 2015-11〜2026-09 で実測)。【事実】
- FX_BTC_JPY で 1 日保有する費用 = 資金調達 0.06%/日(6bps)+ 往復 2.6bps(実測)= **約 8.6bps/日**。【事実】
- MDE(2.8016 σ/√n): 発火率 100% → **15.6**、30% → **28.5**、10% → **49.3**、5% → **69.7 bps/日**。【事実】

**構造的な問題**: 「儲かる水準 ≈ 9bps/日」と「検出できる水準 16〜70bps/日」の間に空白がある。
10〜15bps/日の本物の効果は 11 年のデータでも雑音と区別できず、50bps/日級なら明白すぎて既に裁定されている。
これが日次集計のオンチェーン指標が筋の悪い**本当の理由**(「遅いから」ではない)。【推定】
対照として、生存中の JPX 夜間(P2-03)は 1 イベント σ が 100bps 級で MDE ≈ 8bps。だから 7〜12bps の効果を検出できた。【事実】

### 3.3 筋が通る唯一の形
日次集計ではなく **時刻付きイベント(大口の取引所入金など)× 短い保有(1 時間級)**。σ ≈ 71bps に下がり n=400 でも MDE ≈ 10bps、
資金調達はほぼゼロ、費用は往復 2.6bps。**費用の壁を越える余地がある唯一の形状**。【推定】
必要なのは「どのアドレスがどの取引所か」の帰属で、そこが有料(§3.1)か公開ラベルからの自前構築。ブロックとメンプール自体は無料。

### 3.4 決めたこと
トリアージ #69 を「後回しの 1 行」から**独立した小さな単位**に格上げする。最初にやるのは**無料の日次フロー(3,964 日)で日次版を測り切ること**。
MDE が不利なのは承知の上で、実行費用がほぼゼロであり、結果は (a) 大きな効果を検出(考えにくいが決定的)か
(b) 効果の上限を数値で確定して族ごと閉じる、のどちらかになる。当方の規律は「議論で閉じず、測って閉じる」。
その結果しだいで、有料の帰属データ(イベント版)を週次要約の判断項目に載せるかを決める。着手は P2-08b の後。

## 4. TradingAgents — 規律と正面から衝突するので採らない

「基本面・情緒・技術・取引・リスクの各 Agent が討論して投資判断を出す」枠組みは、当プロジェクトの原則と逆を向いている。
当方は **事前登録した規則が判定し、モデルの語りは判定に使わない**(`.claude/skills/research-protocol`、フェーズ2 の判定区分)。
討論の出力は反証可能な事前登録ではなく、後付けの物語を生みやすい。委任モデルで既に採っている「盲検の監査人が独立に再現し、
判定区分(再現 / 数値差異 / 結論変更)で裁定する」方式の方が、同じ「複数の視点」を規律の内側で得られる。【推定】
**採らない。** ただし「監査人を複数立てて不一致を裁定する」構造は既に導入済み(`99b_dissent_adjudication.md`)。

## 5. Prometheus — 問題は実在するが、先に軽量版がある

24 時間運転の無言の失敗を検知したい、という動機は正当で、実際にインシデント I-002(`backtest_data/auto_*` が数週間共有されていなかった)は
**誰も気付かなかった**ことが本質だった。【事実】
一方で Prometheus 導入はオーナー PC に常駐サービスと exporter と設定を増やす。I-002 の対応時に既に
「PC 側台帳と研究環境側の差分を表示する」軽量案を出して**未実装のまま**にしてある。【事実】
→ **順序**: 軽量版(鮮度・心拍の欠落を既存ダッシュボードで表示し、閾値超過を Discord に通知)を先に実装する。
それでも取りこぼすなら Prometheus を再検討する。今回は導入しない。

## 6. 結論

**導入するものは無い。** 14 本中 8 本は格子の外、2 本(Hummingbot・Freqtrade/Jesse)は既に棄却済みの戦略族か bitFlyer 非対応、
1 本(ccxt)は導入済みで限界も測定済み、1 本(Nautilus)は bitFlyer/JPX 非対応でライセンスと Python 要件も合わない、
1 本(TradingAgents)は規律と衝突、1 本(Prometheus)は軽量版が先。

**この検討から実際に生まれた作業は 2 件**(いずれも小さい):
1. 既存ダッシュボードに鮮度・心拍の欠落表示を追加する(I-002 の未実装分。Prometheus の代替)。
2. トリアージ #69(オンチェーン情報源)を独立単位に格上げし、無料の日次フローで測り切る(§3.4。着手は P2-08b の後)。
